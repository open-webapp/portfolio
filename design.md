# Design — Ledger (Portfolio Dashboard)

See also: [product-behavior.md](product-behavior.md), [schema-spec.md](schema-spec.md)

## Stack

React 19.2 + TypeScript + Vite 8, no state library (single `useReducer`), no CSS framework, oxlint, vitest 4 + jsdom + fake-indexeddb + @testing-library/react. Dependencies: `@open-webapp/drive-sync` for Google Drive backup content ops, `@open-webapp/drive-connect` (v0.1.0) for the Drive auth handle + connect/disconnect widget, `papaparse` for CSV, `lucide-react` for icons. Published to GitHub Pages at `/portfolio/` via `.github/workflows/deploy.yml` (auto-triggers on push to `main`, builds `dist` and deploys with `actions/deploy-pages`); `vite.config.ts` sets `base: '/portfolio/'` to match the repo's Pages path. `vite-plugin-pwa` (devDependency, `generateSW` strategy, `registerType: 'autoUpdate'`, `devOptions.enabled: true`) makes the app installable; `npm run build` additionally emits `dist/sw.js` (service worker) + `dist/manifest.webmanifest`, generated build artifacts not source-controlled.

## State management

Single `useReducer(appReducer, initialState())` in `App.tsx`. No Redux/Zustand/Context split.

### AppState interface

```ts
interface AppState {
  // Data collections/fields (13)
  accounts: Account[]
  positions: Position[]
  closedPositions: ClosedPosition[]
  transactions: Transaction[]
  snapshots: PortfolioSnapshot[]
  csvMappings: SavedCsvMapping[]
  customInstitutions: string[]
  priceSync: PriceSyncState
  mutualFundSync: MutualFundSyncState
  balanceEntries: BalanceEntry[]
  budgetIncomeByYear: Record<string, { monthly: number; yearly: number }>
  budgetExpensesByYear: Record<string, Expense[]>
  budgetTransactions: BudgetTransaction[]

  // UI state
  view: 'settings' | 'accounts' | 'quotes' | 'register' | 'budget'
  sortKey: keyof Position
  sortDir: 'asc' | 'desc'
  txTypeFilter: string
  txSearch: string
  selectedAccountId: string | null
  selectedCategoryKey: TaxCategory | 'closedPositions' | null
  expandedCategories: Record<string, boolean>
  acctAssetClassFilter: string
  acctPosSearch: string
  regAccountId: string | null           // selected account on RegisterPage
  regExpanded: Record<string, boolean>  // category expansion state on RegisterPage

```

- `src/lib/state.ts` — `AppState` interface (13 data fields: 8 collections/objects + 5 Budget fields) and one pure helper per mutation (`addAccount`, `updateAccount`, `deleteAccount`, `updatePosition`, `closePosition`, `deleteClosedPosition`, `restoreClosedPosition`, `setSort`, `toggleSort`, `setTransactionsSearch`, `setTransactionTypeFilter`, `upsertCsvMapping`, `addCustomInstitution`, `selectAccount(accountId, categoryKey?)`, `toggleCategoryExpanded`, `setAcctAssetClassFilter`, `setAcctPosSearch`, `setView`, `setPriceSyncApiKey`, `recordPriceSyncRun`, `setMutualFundSyncApiKey`, `recordMutualFundSyncRun`, `addBalanceEntries`, `updateBalanceEntry`, `deleteBalanceEntry`, `setRegAccount`, `toggleRegCategoryExpanded`, `setRegActivityFilter`, `addBudgetExpense`, `updateBudgetExpense`, `deleteBudgetExpense`, `setBudgetIncome`, `addBudgetTransaction`, `updateBudgetTransaction`, `deleteBudgetTransaction`, `importBudgetTransactions`, `reapplyCategoryMappingsToState`). `selectAccount` accepts an optional `categoryKey` parameter to set `selectedCategoryKey` to a tax category or `'closedPositions'`. `deleteAccount` cascades `balanceEntries` alongside positions/closedPositions/transactions/snapshots/csvMappings. `addBalanceEntries(state, entries)` upserts by `(accountId, date)` key: any incoming entry replaces an existing entry sharing that key; new keys are appended.
  - **Year-scoped Budget data**: `budgetExpensesByYear: Record<string, Expense[]>` and `budgetIncomeByYear: Record<string, {monthly, yearly}>` key each year's data by its 4-digit year string (`currentBudgetYear(now)`). Monthly mode always reads/writes the current calendar year's entry; Yearly mode reads/writes whichever year is selected (`selectedYear`, `BudgetPage`-local state). Shared helper `nearestYearKey` (private) picks the numerically-closest existing year (ties toward the earlier year) for seeding.
    - `resolveBudgetExpensesForYear(byYear, year)` / `resolveBudgetIncomeForYear(byYear, year)` — read-only lookup: exact year if present, else falls back to `nearestBudgetExpensesYear`/`nearestBudgetIncomeYear`'s pick, else `[]`/`{monthly:0, yearly:0}`. Used for display (never mutates).
    - `resolveBudgetExpensesForAnalyticsYear` / `resolveBudgetIncomeForAnalyticsYear` — same fallback shape, used by `BudgetAnalytics`'s selectors when reading a specific year out of the by-year maps.
    - `seedBudgetExpensesForYear(state, year)` / `seedBudgetIncomeForYear(state, year)` — no-op if `year` already has an entry; otherwise clones the nearest existing year's data (deep-copied) into `year`, or `[]`/`{monthly:0, yearly:0}` if no years exist yet at all. Called on first edit of a not-yet-seeded year (`addBudgetExpense`/`updateBudgetExpense`/`deleteBudgetExpense`/`setBudgetIncome` all seed via this before applying their own mutation).
    - `rolloverBudgetExpensesIfNeeded(state, now)` / `rolloverBudgetIncomeIfNeeded(state, now)` — no-op if the current year already has an entry or if `byYear` is empty (nothing to roll over yet); otherwise seeds the current year from the nearest existing year. Dispatched as `ROLLOVER_BUDGET_EXPENSES_IF_NEEDED`/`ROLLOVER_BUDGET_INCOME_IF_NEEDED` once per app load (see product-behavior.md) so a returning user's new calendar year starts pre-populated from their last budget rather than empty.
    - `addBudgetExpense(state, year, expense)`/`updateBudgetExpense(state, year, id, patch)`/`deleteBudgetExpense(state, year, id)` — all operate on `budgetExpensesByYear[year]`, seeding that year first via `seedBudgetExpensesForYear`. `addBudgetExpense` generates an id (`uid('expense')`). `update`/`delete` match by id, no-op if not found.
    - `setBudgetIncome(state, year, patch: Partial<{monthly, yearly}>)` — seeds `year` via `seedBudgetIncomeForYear`, then merges `patch` into that year's `{monthly, yearly}`, clamping each field to `>= 0`. Replaces the old mutually-exclusive monthly/yearly scalar model — both fields can now hold independent non-zero values simultaneously for the same year.
  - `addBudgetTransaction(state, tx)` generates an id (`uid('budgettx')`); `update`/`delete` match by id, no-op if not found — `budgetTransactions` itself is NOT year-scoped (flat array, filtered by month/year at read time via `budgetTransactionsForPeriod`). `Expense.category`/`BudgetTransaction.category` (both formerly `string`) are `categoryId: string`, an FK into `Category.id` — but `Category`/`CategoryMapping` themselves no longer live on `AppState` (see "Global Categories" below). `state.ts`'s only remaining category-adjacent surface is two explicit-param functions: `importBudgetTransactions(state, rows, categories, categoryMappings)` — rows no longer carry a category; it resolves `categoryId` internally via `resolveCategoryIdForDescription(categoryMappings, description)` (imported from `categoryStore.ts`), falling back to the category named `'Other'` in the passed-in `categories` (or `categories[0]` if none is named `'Other'`), then dedups on natural key `date|description|categoryId|amount|accountName` against existing `budgetTransactions` and against earlier rows in the same batch, silently dropping duplicates — and `reapplyCategoryMappingsToState(state, categoryMappings)`, a thin wrapper that rewrites `state.budgetTransactions` via `categoryStore.ts`'s `reapplyMappingsToTransactions(state.budgetTransactions, categoryMappings)`. All other category CRUD (`addCategory`, `renameCategory`, `deleteCategory`, `upsertCategoryMapping`, `updateCategoryMapping`, `addCategoryMapping`, `deleteCategoryMapping`, `resolveCategoryIdForDescription`) has moved to `src/lib/categoryStore.ts` and operates on `GlobalCategoryState`, not `AppState`.
  - **Migration** (`persist.ts`'s `coalesceWithDefaults` path): a raw pre-coalesce blob with a flat `budgetExpenses: Expense[]` array (pre-multi-year shape) is folded into `budgetExpensesByYear[currentBudgetYear()]`; a blob with flat `budgetIncomeMonthly`/`budgetIncomeYearly` scalars is folded into `budgetIncomeByYear[currentBudgetYear()] = {monthly, yearly}`. Both old flat fields are stripped after migration. This runs once per load, ahead of the normal `?? {}` default-fill for `budgetExpensesByYear`/`budgetIncomeByYear`.
- `src/lib/reducer.ts` — `appReducer(state, action)` switches on `action.type` (string) and calls the matching `state.ts` helper, or the import logic in `positionsImport.ts`/`transactionsImport.ts`. `default: return state`. Special case `__SET_STATE` replaces the whole state (used by hydration).
- Components never mutate state directly; they `dispatch({ type: '...', ...payload })`.

### Global Categories (`useGlobalCategories`)

`Category`/`CategoryMapping` are NOT part of `AppState` — they live in a standalone, cross-portfolio store, independent of the per-portfolio `useReducer`/hydrate/debounce-save/`persist.ts` flow described above:

- `src/hooks/useGlobalCategories.ts` — `useGlobalCategories(driveAuth: DriveAuth | null, driveConnected: boolean, driveProjectId: string | null)`. `App.tsx` calls it with the active portfolio's OWN `getDriveAuthFor(activePortfolio)` / `connected` / `driveAuthProjectIdFor(activePortfolio)` (see "Drive sync" below) — categories reuse whichever Drive connection the user already established for the active portfolio (via the Settings Sync widget) rather than requiring a separate one of their own; there is no UI affordance to interactively `connect()` a category-only project, so a from-scratch connection would only ever fire as an unprompted background `connect()`, which browsers block. Called unconditionally (tolerates `driveAuth`/`driveProjectId === null`, staying local-only). Own `useReducer(categoryStoreReducer, initialGlobalCategoryState())` over `GlobalCategoryState = { categories: Category[]; categoryMappings: CategoryMapping[] }` (`src/lib/categoryStore.ts`). Returns `{ categories, categoryMappings, dispatch, hydrated, seedGlobalCategoriesIfNeeded }` — `categories`/`categoryMappings` are pre-filtered to non-tombstoned records (`visibleCategories`/`visibleMappings`).
- `categoryStoreReducer` action union (`CategoryAction`, `src/lib/categoryStore.ts`): `ADD_CATEGORY{id,name}`, `RENAME_CATEGORY{id,name}`, `SET_CATEGORY_EXCLUDE_FROM_SPEND{id,exclude}` (sets `Category.excludeFromSpend`, stamps `updatedAt`; no-op if id not found), `DELETE_CATEGORY{id}`, `UPSERT_CATEGORY_MAPPING{description,categoryId}`, `UPDATE_CATEGORY_MAPPING{id,patch}`, `ADD_CATEGORY_MAPPING{categoryId,substring}`, `DELETE_CATEGORY_MAPPING{id}`, plus two private actions used only by the hook's own effects: `__REPLACE{state}` (returns the given state verbatim — hydrate/merge/seed results) and `__MERGE_IMPORTED{imported}` (merges via `mergeCategoryState`, used by Settings' file-import control). Delete = tombstone (`deletedAt`+`updatedAt` stamped, record kept, no delete UI exists).
- **Persistence**: `src/lib/categoryPersist.ts` — own IndexedDB `ledger_global_categories_v1` (independent of any per-portfolio db), object stores `state` (single doc, key `'current'`, `GlobalCategoryState`) and `meta` (`'migration'` → `{seeded: boolean}`, `'driveSync'` → `{lastKnownRemoteModifiedTime?: string}`). Hydrate is a one-shot effect on mount (`loadGlobalCategoryState()` → `dispatch({type:'__REPLACE'})` → `hydrated=true`); local edits after hydration debounce-save 500ms via `saveGlobalCategoryState`.
- **Seed migration** (`src/lib/categoryMigration.ts`, `seedGlobalCategoriesIfNeeded`): the global store can't be pre-seeded at boot (a portfolio's `AppState` is encrypted per-portfolio, no plaintext until unlocked). Instead, `App.tsx` calls the hook's `seedGlobalCategoriesIfNeeded(portfolio, rawBlob)` once per portfolio hydrate, right after obtaining that portfolio's raw pre-coalesce blob. If the global store's `meta`/`'migration'` marker is not yet `true`: `computeSeedFromPortfolio(rawBlob)` copies that portfolio's `categories`/`categoryMappings` into the global store **verbatim** (same ids, no dedupe, no merge — there's nothing else in the store yet), then marks `seeded: true`. Every subsequent portfolio hydrate (this session or later) finds the marker already `true` and no-ops — a single boolean, not a per-portfolio list, since only the first-ever unlocked portfolio after upgrade seeds the store. Every other portfolio's own old `categories`/`categoryMappings` are left behind, never merged in; that portfolio's `BudgetTransaction.categoryId` values that don't resolve in the global store display as uncategorized (see product-behavior.md).
- **Drive sync** (`src/lib/categoryDrive.ts`, unencrypted): `category-mappings.json` at the shared Drive root `OpenWebApp/Portfolio/` (sibling to per-portfolio subfolders), via `legacyDriveSync.project(projectId)` (exported from `drive.ts`, not the per-portfolio `driveSyncForPortfolio`) — the file itself is not portfolio-scoped, only the connection used to reach it is. `pullGlobalCategoriesFromDrive`/`pushGlobalCategoriesToDrive`/`getGlobalCategoriesModifiedTime` all take a `projectId: string` alongside `driveAuth`, and it MUST be `driveAuthProjectIdFor(activePortfolio)` (`drive.ts`) — the same project id that `driveAuth` (from `getDriveAuthFor(activePortfolio)`) was authenticated under; drive-sync stores/looks up tokens keyed by `(appId, projectId)`, so scoping the file I/O to any other id (e.g. a fixed id of its own, never separately `connect()`-ed) finds no valid token and every push/pull silently fails (errors swallowed). `App.tsx` passes `getDriveAuthFor(activePortfolio)`, its own portfolio `connected` flag, and `driveAuthProjectIdFor(activePortfolio)` into `useGlobalCategories`, which forwards `driveProjectId` to all three `categoryDrive.ts` calls. pull swallows "no file"/malformed content to `null` (never throws), an auth/connection failure propagates uncaught from all three. The hook auto-pushes (fire-and-forget, no debounce) on every local edit once connected; does one pull-once on the first `driveConnected` flip to `true` post-hydrate (ref-guarded, once per session); and polls every 60s (gated on `hydrated`, re-checks connection each tick) — a poll tick calls `getGlobalCategoriesModifiedTime` first and only does a full pull+merge if it's newer than the `meta`/`'driveSync'` bookmark. Fully local/offline when never connected.
- **Merge** (`src/lib/categoryMerge.ts`, `mergeCategoryState(a, b): GlobalCategoryState`): applied identically to initial pull, poll pull, and manual JSON import. Per record (by `id`, across `categories` and `categoryMappings` independently): union of both sides; for an id on both sides, the record with the larger `deletedAt ?? updatedAt` wins; ties keep `a`'s copy.
- **Manual export/import** (Settings backup card, gated on `categoriesHydrated`): "Download Category Mapping" writes `{categories, categoryMappings}` as unencrypted JSON via `downloadJsonAsFile` (`importExport.ts`); "Import Category Mapping" reads a JSON file via `parseCategoryMappingImportFile` (throws `CategoryMappingImportError` on malformed content, shown inline) and dispatches `categoryDispatch({type:'__MERGE_IMPORTED', imported})` — merges, never replaces.
- Consumers (`BudgetPage`, `Settings`) never touch the store directly — `App.tsx` prop-drills `categories`/`categoryMappings`/`categoryDispatch` (plus `categoriesHydrated` to `Settings`) from `globalCategories`, the same prop-drilling convention already used for `state`/`dispatch`. No React context.

### Action types (reducer.ts)

## Data flow

**Budget** — All of `BudgetPage`'s UI state (`period`, `filterCategory`, `sortBy`/`sortDir`, dialog/form drafts, `editingId`/`editCategoryIdDraft`, `selectedYear`, Spend-records `recordSearch`/`recSortBy`/`recSortDir`/`recPage`/`showExcludedRecords`/`editingCell`/`cellDraft`, `recCategoryTouchedManually`, import-dialog state) lives entirely in component-local `useState`, never `AppState`. Persisted budget data that DOES live in `AppState` is `budgetIncomeByYear: Record<string, {monthly, yearly}>`, `budgetExpensesByYear: Record<string, Expense[]>`, `budgetTransactions: BudgetTransaction[]` — `Category`/`CategoryMapping` themselves are sourced from the global category store (`App.tsx`'s `useGlobalCategories`, see "Global Categories" above), not `AppState`, and reach `BudgetPage` as the `categories`/`categoryMappings`/`categoryDispatch` props.

**Year-scoping** (both expense and income data, mirrored logic): `BudgetPage` computes `effectivePeriod: 'monthly' | 'yearly'` (`'monthly'` iff `period === 'monthly'`, else `'yearly'` — also used when `period === 'analytics'`, since Monthly/Yearly derived values still compute unconditionally though unrendered) and `activeYear` (`currentBudgetYear()` in Monthly mode, `selectedYear` in Yearly mode). `activeYearExpenses = resolveBudgetExpensesForYear(state.budgetExpensesByYear, activeYear)` / `activeYearIncome = resolveBudgetIncomeForYear(state.budgetIncomeByYear, activeYear)` read whichever year is active, falling back to the nearest existing year (never seeding on read — pure display fallback). The first *edit* of a not-yet-seeded year (`ADD_BUDGET_EXPENSE`/`UPDATE_BUDGET_EXPENSE`/`DELETE_BUDGET_EXPENSE`/`SET_BUDGET_INCOME`, all dispatched with `year: activeYear`) seeds that year from the nearest existing year first (`seedBudgetExpensesForYear`/`seedBudgetIncomeForYear` inside the `state.ts` helper), so editing a brand-new year starts from a copy of the last one instead of blank. On app load/hydrate, `App.tsx` dispatches `ROLLOVER_BUDGET_EXPENSES_IF_NEEDED`/`ROLLOVER_BUDGET_INCOME_IF_NEEDED` once — these no-op unless the current calendar year has no entry yet (and at least one other year already exists), in which case they seed it from the nearest year exactly like an on-edit seed, so a returning user's new year is pre-populated on first view rather than only on first edit. `BudgetAnalytics` reads across ALL years at once (via `availableBudgetYears`/the by-year maps directly) rather than a single `activeYear`, since its charts compare years side by side.

**Analytics tab**: `BudgetPage`'s `period` toggle has a third option, `'analytics'`; when selected, `BudgetPage` renders `<BudgetAnalytics state={state} categories={categories} />` in place of everything below the period toggle (summary cards, Spend records, Expenses/Breakdown grid, Year picker are all Monthly/Yearly-only). `BudgetAnalytics` is read-only (no `dispatch`/`categoryDispatch`) and derives its 7 sections from `selectors.ts` functions fed `state.budgetTransactions`/`categories`/`state.budgetExpensesByYear`/`state.budgetIncomeByYear` — see its Component-tree entry below for the per-section selector list. `Expense.categoryId`/`BudgetTransaction.categoryId` are FKs into `Category.id`; every category `<select>` on the page reads the `categories` prop directly (no derived list, no `AppState` read). Auto-categorization: `CategoryMapping { id, substring, categoryId, updatedAt }` rows map a description substring (case-insensitive) to a category; `resolveCategoryIdForDescription(mappings, description)` (`categoryStore.ts`) resolves the latest-`updatedAt` match, or `null`. Import (`importBudgetTransactions(state, rows, categories, categoryMappings)`) resolves each row's `categoryId` via that match against the passed-in `categories`/`categoryMappings`, falling back to the "Other" category, before the existing dedup-on-natural-key logic runs; `BudgetPage` supplies its own `categories`/`categoryMappings` props in the `IMPORT_BUDGET_TRANSACTIONS` dispatch. Manual entry gets the same auto-fill live in the UI: as the user types a description on the Manual Add Record form, `recCategoryId` prefills from `resolveCategoryIdForDescription` against the `categoryMappings` prop, unless `recCategoryTouchedManually` is set (user picked a category by hand since the description last changed). Manual Add Record and the Spend-records per-cell Category edit's `onChange` each teach the mapping back by following their `ADD_BUDGET_TRANSACTION`/`UPDATE_BUDGET_TRANSACTION` dispatch (main `dispatch`) with a `categoryDispatch({type:'UPSERT_CATEGORY_MAPPING', description, categoryId})` call (case-insensitive dedup by exact trimmed description, latest-wins, applied to the global store); Expense code paths (Add-Expense dialog, Expenses-table edit) never do this. `computations.ts`'s `toPeriod` converts each `Expense.amount` between `'monthly'`/`'yearly'` for the summary cards and table; `selectors.ts`'s `visibleExpenses(expenses, filterCategoryId, sortBy, period, categoriesById)` filters+sorts the Expenses table (BudgetPage reverses the result locally for descending column-header sort; `categoriesById` resolves id→name for alpha sort, built from the `categories` prop), `actualByCategory(transactions)` sums transaction amounts per `categoryId` for the table's Actual/Variance columns, and `categoryBreakdown(expenses, transactions, period, categories)` aggregates both (keyed by `categoryId`, `categories` — the prop — resolves display names) for the breakdown panel. Income editor (pencil-icon click-to-edit) dispatches `SET_BUDGET_INCOME { year: activeYear, patch: { [period === 'monthly' ? 'monthly' : 'yearly']: amount } }` on Enter (writes only the edited field for `activeYear`; the other field for that year is left untouched — see product-behavior.md). Add-expense dialog validates locally then dispatches `ADD_BUDGET_EXPENSE`. Inline Expenses-table edits dispatch one `UPDATE_BUDGET_EXPENSE` per field change (category staged, dispatched on "Done"); pencil/trash icon buttons trigger edit-mode/delete (`window.confirm`-guarded). Spend records table shares `period`/`selectedYear` with the rest of the page (`periodFilteredTransactions`, no filter of its own) and dispatches `ADD_BUDGET_TRANSACTION`/`UPDATE_BUDGET_TRANSACTION`/`DELETE_BUDGET_TRANSACTION`; rows are edited per-cell (click a cell → inline input/select → commit on Enter/blur, revert on Escape via `skipBlurCommitRef`) rather than as a whole row, `recordSearch` filters (Description/Category/Account substring match) before `recSortBy`/`recSortDir` sorting and `recPage` pagination (100/page, active past 500 rows) apply, plus import (CSV paste via `parseBudgetTransactionsCsv` — 3-column `date,description,amount`, no category column — or OFX/QFX file via `parseOfxTransactions`, neither of which emits a category field; both require an account name and dispatch `IMPORT_BUDGET_TRANSACTIONS { rows, categories, categoryMappings }`). New categories are dispatched immediately via `categoryDispatch({type:'ADD_CATEGORY', ...})` from the "+ Add new category…" `<select>` option (id pre-generated by the caller via `uid('category')`), selecting the new id right away — unlike the old derived-category model, a newly typed category does not wait for the referencing record to be saved.

**Register** — `RegisterBalanceDialog`'s draft rows (`DraftRow[]`, both manual and paste modes) live entirely in component-local state, never `AppState`. "Save" converts valid draft rows to `BalanceEntry[]` and dispatches `ADD_BALANCE_ENTRIES`; editing an existing entry (`editingEntry` set) dispatches `UPDATE_BALANCE_ENTRY` instead — together these are the two write paths into `state.balanceEntries`. `RegisterPage` never reads component-local dialog state directly — after either dispatch, `selectors.ts`'s `registerCategoryCards`/`registerAllAccountsTotal` and `register.ts`'s `accountLedger`/`scopeLedger`/`registerChartSeries` re-derive the ledger rows, stats strip, and chart from the updated `state.balanceEntries` on next render, the same "selectors re-derive from raw collections" pattern used elsewhere.

**CSV import** — synchronous 2-step wizard inside `ImportDialog` (positions or transactions). Dialog-open state is component-local (`isOpen`), not in `AppState`. Paste mode maintains additional component-local state: `pasteHeaderClipboard`, `pasteValuesClipboard`, `pasteIssues`.
1. **Setup** (`step === 1`): pick data type (`.seg`: Transactions / Positions — default Positions), destination account (existing `<select>` or new-account form: name, number, category, retirement checkbox), and entry mode for positions (`upload`/`paste`/`manual`, default `upload`). Upload mode uses `.csv` file parsing (`parseCsvFile` from `csv.ts` -> `{ headers, rows }`). Paste mode feeds two clipboard paste zones (headers + values) into `tableToCsv()` (`pastedTable.ts`) to produce the same `csvHeaders`/`csvRows` state as upload, then shares Step 2's mapping/prefill/commit logic with no changes. Manual mode enters Step 2 with blank rows (no CSV parsing). Continue requires account resolution; upload and paste modes additionally require ≥1 parsed row, manual mode does not.
2. **Review** (`step === 2`):
   - Upload mode: `headers` drive one mapping `<select>` per non-asset-class field (`{ csvColumn: targetField }`, required then optional).
   - Manual positions mode: entering Step 2 seeds exactly 10 blank rows and renders no mapping selects for non-asset-class fields.
   - Positions `Asset Class` header is always a free-text `<input>` that broadcasts to rows not yet touched in their own `assetClass` cell.
   - Existing-account mapping prefill applies only in upload mode (`csvMappings` filtered to headers present in current file).
   - `applyFieldMap(row, fieldMap)` + `importEdits[rowIdx]` produce editable rows; `validatePreviewRow` handles required-field validation (with avgCost/purchaseAmount and price/marketValue alternatives). Fully-empty rows are valid and excluded at commit via `isBlankRow`.
   - Primary button gating: upload mode includes `isReviewValid(dataType, fieldMap)`; manual mode bypasses `isReviewValid` and additionally requires at least one valid non-blank row.
   - Row delete (`handleDeleteRow`) removes row + re-keys row-indexed edits/touched state.
3. **Commit**: primary button dispatches `ADD_ACCOUNT` first when new-account mode (capturing the new account id), then `IMPORT_POSITIONS` or `IMPORT_TRANSACTIONS` with `accountId`, valid non-blank edited rows, and fresh mapping profile saved. For positions, `IMPORT_POSITIONS` also carries `mode: entryMode === 'upload' ? 'replace' : 'merge'` (see `importPositions` below). `UPSERT_CSV_MAPPING` runs only in upload mode. "Import complete" renders in the same step-2 slot; "Done" closes and resets local state.

All steps are **synchronous**; no async queue beyond the debounce-save to IndexedDB.

**Password gate & hydration**: on mount, `App.tsx` calls `peekEnvelopeShape()` (`persist.ts`) to classify the stored IndexedDB record as `'absent' | 'legacy-plaintext' | 'encrypted'`, without decrypting anything (renders "Loading..." while this resolves). While `sessionKey` is `null`, `App` renders `PasswordGate` instead of the accounts/settings tree:
1. `shape === 'encrypted'` → enter-password screen: derives a key from the typed password against `peekStoredSalt()`, calls `loadPersistedApp(key)`; a decrypt failure (wrong password) surfaces as `OperationError` and shows "Incorrect password".
2. `shape === 'absent'` → set-password screen with an optional "Restore" tab-seg: offers "New Setup" (today's generate-key-and-set-password form) vs. "Restore" — which stacks a Google Drive card and a Backup file card — (temporary dummy key `generateSalt()` + `deriveKey(crypto.randomUUID(), dummySalt)` that guarantees the first `restoreBackupFromFileId(fileId, dummyKey)` call always throws `DriveDecryptError`, reusing the cross-password-prompt code path verbatim with no special branching). On restore success (direct pick or cross-password retry), calls `onUnlock(restoredKey, restoredSalt, restoredState)` just as the New Setup form does. Tab switching is free (no validation, state preserved per tab).
3. `shape === 'legacy-plaintext'` → set-password screen (no tab-seg): generates a fresh salt via `generateSalt()`, derives a key, and calls `loadLegacyPlaintextApp()` to read the old plaintext blob so it can be migrated.
4. Either path calls `onUnlock(key, salt, loadedState?)`: `App.tsx` sets `sessionKey`/`sessionSalt` React state, dispatches `__SET_STATE` with `loadedState` if present (decrypted, restored, or migrated data), and sets `isHydrated = true`. This is the **only** point `AppState` is populated from storage — no separate hydration effect.
5. "Back to portfolios" (text link/button, both screens) calls `onBackToPicker()` directly — no confirm dialog — which navigates away to `PortfolioPicker` without touching any persisted data. Recovery from a forgotten password is now: click "Back to portfolios", then use the picker's "Delete" action on that locked-out portfolio (works without needing that portfolio's password).
6. **Auto-lock on inactivity**: while `sessionKey !== null`, two `useEffect`s in `App.tsx` (same `if (sessionKey === null) return` gating as the Drive effects) drive re-locking: an activity listener (document-level `mousedown`/`keydown`/`touchstart`/`scroll`, deliberately not `mousemove`) updates `lastActivityTimeRef`; a periodic-check effect runs `checkAndMaybeLock()` every `LOCK_CHECK_INTERVAL_MS` (30s, via `setInterval`) and on every `visibilitychange`-to-`'visible'` (so a long-backgrounded tab locks immediately on refocus rather than waiting for the next tick). `checkAndMaybeLock()` calls `lockNow()` iff `(now - passwordEntryTimeRef.current >= LOCK_ABSOLUTE_MS) AND (now - lastActivityTimeRef.current >= LOCK_IDLE_MS)` — wall-clock `Date.now()` comparisons, so sleep/suspend gaps are handled correctly without tick-counting. `passwordEntryTimeRef` is set to `Date.now()` on every `onUnlock` (new setup, password entry, Drive restore) and on a successful Change-Password (`onPasswordEntryTimeReset`, see Password change below). Constants: `LOCK_ABSOLUTE_MS` (2h), `LOCK_IDLE_MS` (5min), `LOCK_CHECK_INTERVAL_MS` (30s) — hardcoded in `App.tsx`, not exposed in any Settings UI. `lockNow()` (1) fire-and-forget flushes `savePersistedApp(latestStateRef.current, key, salt)` (`.catch(console.error)`) using the still-valid key/salt refs, (2) sets `sessionKey`/`sessionSalt` to `null`, (3) dispatches `__SET_STATE` with `initialState()` — reusing the same `__SET_STATE`-to-`initialState()` mechanism as `handleBackToPicker` for a non-destructive purpose. Unlike `handleBackToPicker`, `lockNow()` does **not** navigate to `PortfolioPicker` (stays on `gateShape === 'encrypted'`) and does **not** touch any persisted data, so `PasswordGate`'s existing `EnterPasswordScreen` simply reappears — same screen as a fresh page load, no lock-specific UI or messaging.

**Persistence**: once unlocked, every state change schedules `savePersistedApp(state, sessionKey, sessionSalt)` 500ms later (debounced via `setTimeout` in a `useEffect`, cleared/reset on each state change; skipped entirely while `sessionKey`/`sessionSalt` are null). A separate effect flushes the pending save on `pagehide`, `visibilitychange → hidden`, and unmount (via refs holding the latest state, key, and salt — `latestStateRef`, `sessionKeyRef`, `sessionSaltRef` — so the flush sees values from an unlock that happened after the listener was registered) so a refresh/reload within the debounce window never loses the newest state (e.g. a just-finished import). `savePersistedApp` encrypts the whole state into an envelope (`encryptState`) before the IndexedDB write, and rethrows IndexedDB open/write failures so callers' `.catch` fires (no silent success).

**Load normalization** (`coalesceWithDefaults` in `persist.ts`): the single path every stored blob passes through, on both local unlock and Drive restore. Missing collections/fields fall back to `initialState()` defaults (`budgetExpensesByYear`/`budgetIncomeByYear` default to `{}`, `budgetTransactions` defaults to `[]`, like every other collection) — this runs after the flat-shape migration described above, so a modern blob's `budgetExpensesByYear`/`budgetIncomeByYear` pass through untouched. `categories`/`categoryMappings` are no longer part of `AppState` at all, so `coalesceWithDefaults` no longer defaults or migrates them — any `category`/`categoryId` rewriting a blob might still need is out of scope for this function; a blob's raw (pre-coalesce) `categories`/`categoryMappings`, if present, are read once by the separate global-store seed migration (`categoryMigration.ts`'s `seedGlobalCategoriesIfNeeded`, via `persist.ts`'s `loadRawPersistedBlob`) instead. `view` is whitelisted rather than defaulted — a blob written before the Dashboard was removed carries the retired `view: 'dashboard'`, and anything other than `'accounts'`/`'settings'`/`'quotes'`/`'register'`/`'budget'` is coerced to the default `'accounts'`.

**Drive sync**: `drive.ts` exports a `drive` singleton (`createDriveSync({ appId: 'portfolio', clientId: VITE_GOOGLE_CLIENT_ID, folderPath: ['OpenWebApp','Portfolio'] })`, wrapped so `drive.project(id).pickFile(options)` resolves apiKey/appId/parentFolderId and delegates to `@open-webapp/drive-sync`'s own Picker-backed `pickFile`) plus `syncBackup(state, key, salt)` (encrypts state into an envelope, writes it as the Drive JSON file, resolves with the written file id)/`restoreBackupFromFileId(fileId, key)` (reads+parses the Drive JSON envelope for a specific file id, decrypts with `key`; throws `DriveDecryptError` — carrying the envelope's decoded `salt` and the raw `EncryptedEnvelope` — specifically on an auth-tag mismatch so a caller can retry with a different password without a second network round-trip)/`getBackupFileId()` (resolves the existing backup file id or null, for the "View backup in Google Drive" link only — not used to find what to restore; its own internal `NeedsReauthError` catch is a silent passive probe), all operating on `drive.project('app')`.

**Drive auth** (`@open-webapp/drive-connect`, `driveAuth` co-located in `drive.ts` to avoid an import cycle — a separate module would import `drive.ts` and vice-versa): `driveAuth = createDriveAuth({ drive: driveSync, projectId: 'app', tokenBufferMs: 5*60*1000 })`. Handle API: `getStatus()` (sync), `subscribe(fn)`, `refresh()`, `connect()`, `disconnect()`, `ensureFresh()`, `activate()`. **App.tsx wiring**: `App.tsx` holds NO Drive auth state. It reads `const { connected } = useDriveConnection(driveAuth)` and passes `connected` to `<Nav>`. `backupFileId`/`syncing` remain lifted App state. `onDriveConnected` (fetches `getBackupFileId()` → `setBackupFileId` in its own try/catch — a failed lookup leaves `backupFileId` null, does NOT forget the connection) and `onDriveDisconnected` (`setBackupFileId(null)`) are passed to both `<PasswordGate>` and `<SettingsPage>`, which mount `<GoogleDriveWidget auth={driveAuth} onConnected={onDriveConnected} onDisconnected={onDriveDisconnected}>` themselves. Hosts call `driveAuth.refresh()` (fire-and-forget, control flow unchanged) on a caught `NeedsReauthError` at five sites: `App.tsx` `handleSync` / `handleConflictTakeRemote` / `handleConflictPushLocal`, `Settings.tsx` `handleChangePassword` re-sync, and `DriveRestorePanel.tsx` `DriveFilePickerDialog.onSelect` (non-`DriveDecryptError` branch). **Password change** (`SettingsPage.handleChangePassword`): verifies the typed current password by deriving a key against `sessionSalt` and attempting `loadPersistedApp(candidateKey)` (a real decrypt, not a stored-hash check); on success generates a brand-new salt (`generateSalt()`, never reuses the old one), derives a new key, and calls `savePersistedApp(state, newKey, newSalt)`. If Drive is connected (`driveAuth.getStatus().connected`, sync), also calls `syncBackup(state, newKey, newSalt)` — a failure here is caught and shown as a non-blocking warning (byte-identical copy: "…Sync manually from Google Drive Sync above."), a `NeedsReauthError` additionally fires `driveAuth.refresh()`; it does not undo the already-completed local `savePersistedApp`. On success calls `onKeyChange(newKey, newSalt)` to update `App.tsx`'s session state, and also calls the new `onPasswordEntryTimeReset` prop (resets `passwordEntryTimeRef` to `Date.now()` in `App.tsx`, same as `onUnlock` — restarts the 2h auto-lock window).

## Key Invariants

- **Account cascade delete**: Deleting an `Account` cascade-deletes all its `Position`s, `ClosedPosition`s, `Transaction`s, `PortfolioSnapshot`s, `SavedCsvMapping`s, and `BalanceEntry`s.
- **importPositions replace vs merge mode**: `importPositions(state, accountId, mappedRows, importDate, mode)` (`mode: 'replace' | 'merge'`, default `'replace'`). `'replace'` (CSV-upload, a full broker export) replaces the account's entire position list; symbols missing from the new rows become `ClosedPosition`s. `'merge'` (manual entry / Copy-Paste, inherently partial batches) upserts new rows by symbol into the account's existing positions — untouched symbols are left alone and nothing is closed. `ImportDialog` dispatches `mode: entryMode === 'upload' ? 'replace' : 'merge'`.
- **Position delete = close, not hard delete**: deleting a position from `PositionGroupOverlay` (`CLOSE_POSITION` action) converts it to a `ClosedPosition` with `realizedGL: null`, `realizedGLBasis: 'unknown'` (never transaction-matched, unlike the reimport-driven auto-close path in `positionsImport.ts`) — same target shape, different trigger and always-unknown basis.

## Design patterns

- **Computed-not-stored**: `marketValue`/`costBasis`/`gl`/`glPct` are never persisted on `Position`; always derived via `computations.computePosition()`.
- **Category filter is compositional**: every selector re-derives "accounts in category" via a local `getAccountsForCategory`/inline filter rather than storing a filtered account list.
- **Effective asset class**: anywhere a position's asset class is displayed or grouped, code reads `p.assetClassManualOverride || p.assetClass`, never `p.assetClass` alone.
- **Natural-key upsert**: `positionsImport.ts` (snapshot) and `transactionsImport.ts` (transaction) both dedup by recomputing a string key and filtering pre-existing entries out before appending, rather than mutating in place.
- **Session-key lifecycle**: the derived `CryptoKey` + PBKDF2 salt (`sessionKey`/`sessionSalt`) live only as React state in `App.tsx`, set once by `PasswordGate`'s `onUnlock` (or rotated by `SettingsPage`'s `onKeyChange`) and threaded down via props to `SettingsPage` — they are explicitly **not** fields on `AppState` and never flow through the reducer or `__SET_STATE`. They are additionally mirrored into `sessionKeyRef`/`sessionSaltRef` (plain refs, updated on every render) purely so the pagehide/unmount flush-save listener — registered once on mount — can read the latest values without re-registering. Losing this state (refresh, tab close) is by design: it is what makes the password required every session. Two more refs follow the same mirroring pattern to drive auto-lock without re-registering effects: `lastActivityTimeRef` (updated by the document-level activity listener) and `passwordEntryTimeRef` (set on `onUnlock` and on a successful Change Password via `onPasswordEntryTimeReset`) — read by the periodic/`visibilitychange` lock-check effect (see "Auto-lock on inactivity" in Data flow) to decide when to call `lockNow()`, which clears `sessionKey`/`sessionSalt` the same way losing them on refresh/tab-close does, just triggered proactively instead of by navigation.
- **Styling**: components use inline `style={{ ... }}` extensively alongside the design-system classes (`.card.blueprint.elev-sm`, `.tag`/`.tag-accent`, `.seg`/`.seg-opt`, `.table`, `.nav`, `.field`/`.input`, `.dialog-backdrop`/`.dialog`) — this is a live deviation from the CLAUDE.md styling rule ("Components consume the existing class vocabulary ... rather than inline styles"); most layout/spacing (flex, gap, padding, modal positioning) is inline today, only the visual vocabulary (colors, card chrome, tags, table borders) comes from `styles.css` classes.
- **Hand-mirrored dual artifact**: `src/lib/pastedTable.ts` (typed ES module) is paired with a root-level `pastedTable.js` (classic-script, `window.PastedTable` global, no `import`/`export`) — one hand-maintained copy of the same logic per runtime, no build step generates one from the other. `pastedTable.js` sits outside `tsconfig.app.json`'s `include`, so it is never typechecked or bundled; parity between the two is enforced entirely at test time by one shared vitest case table (`src/lib/pastedTable.test.ts`) run against both implementations. Editing one copy without the other does not fail `tsc -b` — it only fails that shared-case test suite, so the two files can silently drift until tests are run.
