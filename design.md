# Design — Ledger (Portfolio Dashboard)

See also: [product-behavior.md](product-behavior.md), [schema-spec.md](schema-spec.md)

## Stack

React 19.2 + TypeScript + Vite 8, no state library (single `useReducer`), no CSS framework, oxlint, vitest 4 + jsdom + fake-indexeddb + @testing-library/react. Dependencies: `@open-webapp/drive-sync` for Google Drive backup content ops, `@open-webapp/drive-connect` (v0.1.0) for the Drive auth handle + connect/disconnect widget, `papaparse` for CSV, `lucide-react` for icons. Published to GitHub Pages at `/portfolio/` via `.github/workflows/deploy.yml` (auto-triggers on push to `main`, builds `dist` and deploys with `actions/deploy-pages`); `vite.config.ts` sets `base: '/portfolio/'` to match the repo's Pages path. `vite-plugin-pwa` (devDependency, `generateSW` strategy, `registerType: 'autoUpdate'`, `devOptions.enabled: true`) makes the app installable; `npm run build` additionally emits `dist/sw.js` (service worker) + `dist/manifest.webmanifest`, generated build artifacts not source-controlled.

## Click-To-Edit Convention

- Click the displayed editable value itself to enter inline edit mode; do not add a separate pencil affordance.
- Save with Enter only, then return to read-only text. Blur keeps the editor open.
- Invalid values leave the persisted value unchanged.
- Escape cancels the active inline edit without saving. In an overlay, a subsequent Escape closes the overlay.

## State management

Single `useReducer(appReducer, initialState())` in `App.tsx`. No Redux/Zustand/Context split.

- `src/lib/state.ts` — `AppState` interface (14 data fields: 8 collections/objects + 6 Budget fields) and one pure helper per mutation (`addAccount`, `updateAccount`, `deleteAccount`, `updatePosition`, `closePosition`, `deleteClosedPosition`, `restoreClosedPosition`, `setSort`, `toggleSort`, `setTransactionsSearch`, `setTransactionTypeFilter`, `upsertCsvMapping`, `addCustomInstitution`, `selectAccount(accountId, categoryKey?)`, `toggleCategoryExpanded`, `setAcctAssetClassFilter`, `setAcctPosSearch`, `setView`, `setPriceSyncApiKey`, `recordPriceSyncRun`, `setMutualFundSyncApiKey`, `recordMutualFundSyncRun`, `addBalanceEntries`, `updateBalanceEntry`, `deleteBalanceEntry`, `setRegAccount`, `toggleRegCategoryExpanded`, `setRegActivityFilter`, `addExpenseDefinition`, `updateExpenseDefinition`, `deleteExpenseDefinition`, `expenseDefinitionInUse`, `setExpenseAmount`, `clearExpenseAmount`, `setBudgetIncome`, `addBudgetTransaction`, `updateBudgetTransaction`, `updateBudgetTransactionsBulk`, `deleteBudgetTransaction`, `resolveBudgetImportRows`, `importBudgetTransactions`, `reapplyCategoryMappingsToState`). `selectAccount` accepts an optional `categoryKey` parameter to set `selectedCategoryKey` to a tax category or `'closedPositions'`. `deleteAccount` cascades `balanceEntries` alongside positions/closedPositions/transactions/snapshots/csvMappings. `addBalanceEntries(state, entries)` upserts by `(accountId, date)` key: any incoming entry replaces an existing entry sharing that key; new keys are appended.
  - **`budgetExpenseDefinitions: ExpenseDefinition[]`** — global, year-independent list (`{id, name, categoryId, frequency}`, no `amount`), shared across every year. `addExpenseDefinition(state, def, amount)` generates an id (`uid('expense')`), appends the definition, and seeds `amount` for the CURRENT calendar year only in `budgetExpenseAmountsByYear`. `updateExpenseDefinition(state, id, patch)` patches name/categoryId/frequency by id — affects all years at once, no-op if not found. `expenseDefinitionInUse(state, id)` checks whether any `BudgetTransaction` (in any year) still references `id` via `spendExpenseId`. `deleteExpenseDefinition(state, id)` removes the definition and its `amount` entry from every year in `budgetExpenseAmountsByYear`; callers (`BudgetExpensesTab`) must check `expenseDefinitionInUse` first and block/alert if referenced, and on success pair it with `categoryDispatch({type:'DELETE_CATEGORY_MAPPINGS_FOR_EXPENSE', spendExpenseId: id})` (hard-delete).
  - **`budgetExpenseAmountsByYear: Record<string, Record<string, number>>`** and **`budgetIncomeByYear: Record<string, number>`** — amounts-only, keyed by 4-digit year string (`currentBudgetYear(now)`). `budgetIncomeByYear` is a single plain yearly figure per year (collapsed from the old `{monthly, yearly}` pair). The Expenses tab (`BudgetExpensesTab`) reads/writes across an arbitrary set of years at once (own local `breakdownYear` for the Category Breakdown panel, plus a union-of-years column set for the Expense table); the Spend tab (`BudgetPage`) reads/writes whichever single year is selected via its own Year dropdown (`selectedYear`, local state). Shared helper `nearestYearKey<T>(byYear, targetYear, isEmpty?)` (private, generic) picks the numerically-closest existing year (ties toward the earlier year); with an `isEmpty` predicate passed, expands outward ring-by-ring (target-dist before target+dist at each ring) skipping candidates `isEmpty` flags, still tie-breaking toward the earlier year among non-empty candidates at a ring, and returns `null` if no non-empty candidate exists or the map is empty. `isEmptyExpenseAmountsSnapshot(v: Record<string, number>)` / `isEmptyIncomeSnapshot(v: number)` (exported) are the two predicates, passed into `nearestExpenseAmountsYear`/`nearestBudgetIncomeYear`.
    - `resolveExpenseAmountsForYear(byYear, year)` / `resolveBudgetIncomeForYear(byYear, year)` — read-only lookup: exact year if present AND non-empty; an empty snapshot at `year` itself is treated as absent for fallback purposes (same skip-empty nearest search as the persist paths below), else `{}`/`0`. Used for display (never mutates).
    - `resolveExpenseAmountsForAnalyticsYear` / `resolveBudgetIncomeForAnalyticsYear` — same fallback shape, used by `BudgetAnalytics`'s selectors when reading a specific year out of the by-year maps.
    - `ensureExpenseAmountsSnapshotForYear(state, year)` / `ensureBudgetIncomeSnapshotForYear(state, year)` — eagerly clones the nearest non-empty year's data into `year` if `year` is absent; no-ops (year stays virtual, no key created) if no non-empty year exists anywhere. Dispatched together via `ENSURE_BUDGET_YEAR_SNAPSHOT` (see Action types below).
    - `rolloverBudgetExpenseAmountsIfNeeded(state, now)` / `rolloverBudgetIncomeIfNeeded(state, now)` — first runs the one-time-per-load `stripEmptyBudgetSnapshots` migration cleanup (strips any pre-existing persisted empty snapshots), then: no-op if the current year already has a (non-empty) entry or if `byYear` is empty (nothing to roll over yet); otherwise seeds the current year from the nearest non-empty existing year. Dispatched as `ROLLOVER_BUDGET_EXPENSE_AMOUNTS_IF_NEEDED`/`ROLLOVER_BUDGET_INCOME_IF_NEEDED` once per app load (see product-behavior.md) so a returning user's new calendar year starts pre-populated from their last budget rather than empty.
    - `setExpenseAmount(state, year, expenseId, amount)`/`clearExpenseAmount(state, year, expenseId)` — set/remove `budgetExpenseAmountsByYear[year][expenseId]`, scoped to that one `(year, expenseId)` pair only. `clearExpenseAmount`: if the post-clear result is empty (`{}`), the year's key is removed from `budgetExpenseAmountsByYear` entirely rather than left as `{}` (never-persist-empty).
    - `setBudgetIncome(state, year, amount)` — sets `budgetIncomeByYear[year]` to a single plain yearly figure, clamped `>= 0`. If the result is `0`, the year's key is removed from `budgetIncomeByYear` entirely rather than left storing `0` (never-persist-empty).
  - `addBudgetTransaction(state, tx)` generates an id (`uid('budgettx')`); `update`/`delete` match by id, no-op if not found — `budgetTransactions` itself is NOT year-scoped (flat array, filtered by year at read time via `budgetTransactionsForPeriod`). `ExpenseDefinition.categoryId`/`BudgetTransaction.categoryId` are FKs into `Category.id` — but `Category`/`CategoryMapping` themselves no longer live on `AppState` (see "Global Categories" below). `state.ts`'s only remaining category-adjacent surface is two explicit-param functions: `importBudgetTransactions(state, rows, categories, categoryMappings, budgetExpenseDefinitions)` — rows no longer carry a category; it resolves `spendExpenseId` internally via `resolveSpendExpenseIdForDescription(categoryMappings, description)` (imported from `categoryStore.ts`); on a hit whose id resolves against `budgetExpenseDefinitions`, `categoryId` is derived from the linked definition, else falls back to the category named `'Other'` in the passed-in `categories` (or `categories[0]` if none is named `'Other'`) with `spendExpenseId` unset (`resolveSpendExpenseForCategory` now migration-only, see below), then dedups on natural key `date|description|amount|accountName` (no `categoryId`) against existing `budgetTransactions` and against earlier rows in the same batch, silently dropping duplicates — and `reapplyCategoryMappingsToState(state, categoryMappings)`, a thin wrapper that rewrites `state.budgetTransactions` via `categoryStore.ts`'s `reapplyMappingsToTransactions(state.budgetTransactions, categoryMappings, state.budgetExpenseDefinitions)`. `reapplyMappingsToTransactions` takes a 3rd param, `budgetExpenseDefinitions`: for each transaction it resolves `resolvedSpendExpenseId = resolveSpendExpenseIdForDescription(mappings, description)`; on a hit whose id resolves to a definition it sets `spendExpenseId` to the hit and `categoryId` to the definition's `categoryId`, otherwise leaves the row untouched (never clears — no-match and dangling-definition both no-op; the import-time fallback-to-Other applies only to fresh rows, never here). There is no manual "Re-apply mappings" button anywhere in the UI — every call site that mutates a `CategoryMapping` (Settings' mapping add/edit/substring handlers, CSV/JSON mapping import merge, BudgetPage's per-cell Spend Category edit and Add Record form) dispatches `REAPPLY_CATEGORY_MAPPINGS` to the main store immediately after the mapping mutation. All other category CRUD (`addCategory`, `renameCategory`, `deleteCategory`, `upsertCategoryMapping`, `updateCategoryMapping`, `addCategoryMapping`, `deleteCategoryMapping`, `deleteCategoryMappingsForExpense`, `resolveSpendExpenseIdForDescription`) has moved to `src/lib/categoryStore.ts` and operates on `GlobalCategoryState`, not `AppState`.
  - **Migration** (`src/lib/persist.ts`, run on every load ahead of `coalesceWithDefaults`): `migrateBudgetExpensesByYearIfNeeded` folds a legacy flat `budgetExpenses: Expense[]` array into `budgetExpensesByYear[currentBudgetYear()]`; `migrateBudgetIncomeByYearIfNeeded`/`collapseBudgetIncomeByYearShapeIfNeeded` fold legacy flat `budgetIncomeMonthly`/`budgetIncomeYearly` scalars, or a per-year `{monthly, yearly}` shape, into the collapsed plain-number `budgetIncomeByYear[year]` (`yearly !== 0 ? yearly : monthly * 12`, else `0`); `migrateBudgetExpenseDefinitionsIfNeeded` then splits the now-migrated year-scoped `budgetExpensesByYear: Record<year, Expense[]>` into `budgetExpenseDefinitions` + `budgetExpenseAmountsByYear` — scanning years **descending** so each expense id's **most-recent year** wins for name/categoryId/frequency, while every `(year, id)` pair's `amount` is preserved under `budgetExpenseAmountsByYear[year][id]`. All superseded flat/legacy fields are stripped after migration. See `schema-spec.md`'s Budget storage section for full detail.
- `src/lib/reducer.ts` — `appReducer(state, action)` switches on `action.type` (string) and calls the matching `state.ts` helper, or the import logic in `positionsImport.ts`/`transactionsImport.ts`. `default: return state`. Special case `__SET_STATE` replaces the whole state (used by hydration).
- Components never mutate state directly; they `dispatch({ type: '...', ...payload })`.

### Global Categories (`useGlobalCategories`)

`Category`/`CategoryMapping` are NOT part of `AppState` — they live in a standalone, cross-portfolio store, independent of the per-portfolio `useReducer`/hydrate/debounce-save/`persist.ts` flow described above:

- `src/hooks/useGlobalCategories.ts` — `useGlobalCategories(driveAuth, driveConnected, driveProjectId, budgetExpenseDefinitions = [])`. `App.tsx` calls it with the active portfolio's OWN `getDriveAuthFor(activePortfolio)` / `connected` / `driveAuthProjectIdFor(activePortfolio)` (see "Drive sync" below) — categories reuse whichever Drive connection the user already established for the active portfolio (via the Settings Sync widget) rather than requiring a separate one of their own; there is no UI affordance to interactively `connect()` a category-only project, so a from-scratch connection would only ever fire as an unprompted background `connect()`, which browsers block. Called unconditionally (tolerates `driveAuth`/`driveProjectId === null`, staying local-only). Hydrate is one-shot and deferred while `budgetExpenseDefinitions === undefined` (pre-unlock) so the `categoryId`→`spendExpenseId` migration resolves against real definitions instead of dropping every legacy row. Own `useReducer(categoryStoreReducer, initialGlobalCategoryState())` over `GlobalCategoryState = { categories: Category[]; categoryMappings: CategoryMapping[] }` (`src/lib/categoryStore.ts`). Returns `{ categories, categoryMappings, dispatch, hydrated, seedGlobalCategoriesIfNeeded }` — `categories`/`categoryMappings` are pre-filtered to non-tombstoned records (`visibleCategories`/`visibleMappings`).
- `categoryStoreReducer` action union (`CategoryAction`, `src/lib/categoryStore.ts`): `ADD_CATEGORY{id,name}`, `RENAME_CATEGORY{id,name}`, `SET_CATEGORY_EXCLUDE_FROM_SPEND{id,exclude}`, `DELETE_CATEGORY{id}`, `UPSERT_CATEGORY_MAPPING{description,spendExpenseId}`, `UPDATE_CATEGORY_MAPPING{id,patch}`, `ADD_CATEGORY_MAPPING{spendExpenseId,substring}`, `DELETE_CATEGORY_MAPPING{id}`, `DELETE_CATEGORY_MAPPINGS_FOR_EXPENSE{spendExpenseId}`, `__REPLACE{state}`, and `__MERGE_IMPORTED{imported}`. `DELETE_CATEGORY` is an unconditional tombstone action (`deletedAt`/`updatedAt` stamped, record retained); Budget > Category Mapping alone provides its guarded delete UI. `DELETE_CATEGORY_MAPPINGS_FOR_EXPENSE` hard-deletes mappings for one expense.
- **Persistence**: `src/lib/categoryPersist.ts` — own IndexedDB `ledger_global_categories_v1` (independent of any per-portfolio db), object stores `state` (single doc, key `'current'`, `GlobalCategoryState`) and `meta` (`'migration'` → `{seeded: boolean}`, `'driveSync'` → `{lastKnownRemoteModifiedTime?: string}`). Hydrate is a one-shot effect on mount (`loadGlobalCategoryState(budgetExpenseDefinitions)` → `dispatch({type:'__REPLACE'})` → `hydrated=true`); load runs the one-time `categoryId`→`spendExpenseId` migration (`resolveSpendExpenseForCategory` per legacy row; match rewrites to `spendExpenseId`, no match drops the row, persisting only when changed). Local edits after hydration debounce-save 500ms via `saveGlobalCategoryState`.
- **Seed migration** (`src/lib/categoryMigration.ts`, `seedGlobalCategoriesIfNeeded`): the global store can't be pre-seeded at boot (a portfolio's `AppState` is encrypted per-portfolio, no plaintext until unlocked). Instead, `App.tsx` calls the hook's `seedGlobalCategoriesIfNeeded(portfolio, rawBlob)` once per portfolio hydrate, right after obtaining that portfolio's raw pre-coalesce blob. If the global store's `meta`/`'migration'` marker is not yet `true`: `computeSeedFromPortfolio(rawBlob)` copies that portfolio's `categories`/`categoryMappings` into the global store **verbatim** (same ids, no dedupe, no merge — there's nothing else in the store yet), then marks `seeded: true`. Every subsequent portfolio hydrate (this session or later) finds the marker already `true` and no-ops — a single boolean, not a per-portfolio list, since only the first-ever unlocked portfolio after upgrade seeds the store. Every other portfolio's own old `categories`/`categoryMappings` are left behind, never merged in; that portfolio's `BudgetTransaction.categoryId` values that don't resolve in the global store display as uncategorized (see product-behavior.md).
- **Drive sync** (`src/lib/categoryDrive.ts`, unencrypted): `category-mappings.json` at the shared Drive root `OpenWebApp/Portfolio/` (sibling to per-portfolio subfolders), via `legacyDriveSync.project(projectId)` (exported from `drive.ts`, not the per-portfolio `driveSyncForPortfolio`) — the file itself is not portfolio-scoped, only the connection used to reach it is. `pullGlobalCategoriesFromDrive`/`pushGlobalCategoriesToDrive`/`getGlobalCategoriesModifiedTime` all take a `projectId: string` alongside `driveAuth`, and it MUST be `driveAuthProjectIdFor(activePortfolio)` (`drive.ts`) — the same project id that `driveAuth` (from `getDriveAuthFor(activePortfolio)`) was authenticated under; drive-sync stores/looks up tokens keyed by `(appId, projectId)`, so scoping the file I/O to any other id (e.g. a fixed id of its own, never separately `connect()`-ed) finds no valid token and every push/pull silently fails (errors swallowed). `App.tsx` passes `getDriveAuthFor(activePortfolio)`, its own portfolio `connected` flag, and `driveAuthProjectIdFor(activePortfolio)` into `useGlobalCategories`, which forwards `driveProjectId` to all three `categoryDrive.ts` calls. pull swallows "no file"/malformed content to `null` (never throws), an auth/connection failure propagates uncaught from all three. The hook auto-pushes (fire-and-forget, no debounce) on every local edit once connected; does one pull-once on the first `driveConnected` flip to `true` post-hydrate (ref-guarded, once per session); and polls every 60s (gated on `hydrated`, re-checks connection each tick) — a poll tick calls `getGlobalCategoriesModifiedTime` first and only does a full pull+merge if it's newer than the `meta`/`'driveSync'` bookmark. Fully local/offline when never connected.
- **Merge** (`src/lib/categoryMerge.ts`, `mergeCategoryState(a, b): GlobalCategoryState`): applied identically to initial pull, poll pull, and manual JSON import. Per record (by `id`, across `categories` and `categoryMappings` independently): union of both sides; for an id on both sides, the record with the larger `deletedAt ?? updatedAt` wins; ties keep `a`'s copy.
- **Manual export/import** (Budget > Category Mapping, gated on `categoriesHydrated`): "Download Category Mapping" writes `{categories, categoryMappings}` as unencrypted JSON via `downloadJsonAsFile` (`importExport.ts`); "Import Category Mapping" parses and merges via `categoryDispatch({type:'__MERGE_IMPORTED', imported})`, never replaces.
- `App.tsx` prop-drills `categories`/`categoryMappings`/`categoryDispatch`/`categoriesHydrated` from `globalCategories` to `BudgetPage`; no React context.

## Data flow

**Budget** — All of `BudgetPage`'s UI state (`period`, `selectedYear`, Spend-records `recordSearch`/`recSortBy`/`recSortDir`/`recPage`/`showExcludedRecords`/`editingCell`/`cellDraft`/`selectedRowIds`/`bulkCategoryId`/`bulkExpenseId`, `recCategoryTouchedManually`, import-dialog state), `BudgetExpensesTab`'s own UI state, and `CategoryMappingTab`'s edit/import drafts live entirely in component-local `useState`, never `AppState`. Persisted budget data in `AppState` is `budgetIncomeByYear`, `budgetExpenseDefinitions`, `budgetExpenseAmountsByYear`, and `budgetTransactions`; `Category`/`CategoryMapping` come from the global category store as `BudgetPage` props. `CategoryMappingTab` derives each category's all-year effective Spend count from the currently open portfolio's `state.budgetTransactions` plus `state.budgetExpenseDefinitions`, using `effectiveCategoryId`; it receives and reads no other portfolio data.

**Year-scoping** (amounts-only, not the definitions themselves — mirrored logic between expense amounts and income): `BudgetPage`'s Spend tab reads/writes a single `selectedYear` at a time (Year `<select>`, default `availableBudgetYears(state.budgetTransactions, new Date())[0]`); `BudgetExpensesTab` reads/writes across an arbitrary set of years at once — its own independent `breakdownYear` for the Category Breakdown panel, and a locally-computed union-of-years column set (every year in `budgetTransactions`/`budgetIncomeByYear`/`budgetExpenseAmountsByYear`, plus always the real current calendar year) for the multi-year Expense table. `resolveExpenseAmountsForYear(state.budgetExpenseAmountsByYear, year)` / `resolveBudgetIncomeForYear(state.budgetIncomeByYear, year)` read whichever year is needed, falling back to the nearest existing non-empty year (never seeding on read — pure display fallback). Switching `BudgetPage`'s `selectedYear` to a not-yet-seeded year dispatches `ENSURE_BUDGET_YEAR_SNAPSHOT { year }`, which eagerly persists a real snapshot cloned from the nearest existing year (via `ensureExpenseAmountsSnapshotForYear`/`ensureBudgetIncomeSnapshotForYear`) — not a purely virtual/display-only fallback. `BudgetExpensesTab`'s per-cell Amount edits (`SET_EXPENSE_AMOUNT`/`CLEAR_EXPENSE_AMOUNT`) write directly into whichever year's column was clicked, with no separate seed step (each `(year, expenseId)` pair is independent). On app load/hydrate, `App.tsx` dispatches `ROLLOVER_BUDGET_EXPENSE_AMOUNTS_IF_NEEDED`/`ROLLOVER_BUDGET_INCOME_IF_NEEDED` once — these no-op unless the current calendar year has no entry yet (and at least one other year already exists), in which case they seed it from the nearest year, so a returning user's new year is pre-populated on first view. `BudgetAnalytics` reads across ALL years at once (via `availableBudgetYears`/the by-year maps directly), same as `BudgetExpensesTab`'s multi-year table, since both compare years side by side.

**Expenses tab**: `BudgetPage`'s `period` toggle has three options — `'expenses' | 'spend' | 'analytics'`; selecting `'expenses'` renders `<BudgetExpensesTab state={state} dispatch={dispatch} categories={categories} categoryDispatch={categoryDispatch} />` below the toggle row (no page-level Year select in this row — the tab owns its own, scoped only to its Category Breakdown panel). `ExpenseDefinition.categoryId`/`BudgetTransaction.categoryId` are FKs into `Category.id`; every category `<select>` on either component reads the `categories` prop directly (no derived list, no `AppState` read). Auto-categorization: `CategoryMapping { id, substring, spendExpenseId, updatedAt }` rows map a description substring (case-insensitive) to an expense; `resolveSpendExpenseIdForDescription(mappings, description)` (`categoryStore.ts`) resolves the latest-`updatedAt` hit, or `null`. Import (`importBudgetTransactions(state, rows, categories, categoryMappings, budgetExpenseDefinitions)`) resolves each row's `spendExpenseId` via that hit (verified against `budgetExpenseDefinitions`, else `spendExpenseId` unset) and derives `categoryId` from the linked definition, falling back to the "Other" category (`resolveSpendExpenseForCategory` is now migration-only, not the live path), before the dedup-on-natural-key (`date|description|amount|accountName`, no `categoryId`) logic runs; `BudgetPage` supplies its own `categories`/`categoryMappings` in the `IMPORT_BUDGET_TRANSACTIONS` dispatch, while the reducer reads `budgetExpenseDefinitions` off `AppState` directly. Manual entry gets the same auto-fill live in the UI: as the user types a description on the Add Record form, `resolveSpendExpenseIdForDescription` against the `categoryMappings` prop prefills `recExpenseId` (hit) and `recCategoryId` (the hit definition's category), unless `recCategoryTouchedManually` is set (user picked a category by hand since the description last changed). Add Record and the Spend-records per-cell Category edit's `onChange` each teach the mapping back by following their `ADD_BUDGET_TRANSACTION`/`UPDATE_BUDGET_TRANSACTION` dispatch (main `dispatch`) with a `categoryDispatch({type:'UPSERT_CATEGORY_MAPPING', description, spendExpenseId})` call (case-insensitive dedup by exact trimmed description, latest-wins, applied to the global store), immediately followed by computing the resulting mapping list locally (via `categoryStore.ts`'s `upsertCategoryMapping`) and dispatching `{ type: 'REAPPLY_CATEGORY_MAPPINGS', categoryMappings: nextMappings }` (main `dispatch`) so any other existing transaction sharing that description picks up the new/changed mapping right away — there is no manual "Re-apply mappings" button anywhere in the app; every mapping-mutating call site self-triggers this. `ExpenseDefinition` code paths (Add-Expense dialog, Expenses-table per-cell edit) never do either of these. The Spend-records read-only cell (not being edited) renders via `selectors.ts`'s `formatSpendCategoryLabel(spendExpenseId, effectiveCategoryId(row, budgetExpenseDefinitions), budgetExpenseDefinitions, categoriesById)` — `"{expense name} ({category name})"` when `spendExpenseId` resolves (global lookup, no year needed), else `"Uncategorized ({category name})"`. `computations.ts`'s `toPeriod` converts a raw amount between `'monthly'`/`'yearly'` display units, no longer against a stored `Expense.amount` field (which no longer exists — see `## ExpenseDefinition` in schema-spec.md); `selectors.ts`'s `visibleExpenses(definitions, {}, filterCategoryId, sortBy, categoriesById)` filters+sorts the Expense table's rows (`BudgetExpensesTab` reverses the result locally for descending column-header sort; `categoriesById` resolves id→name for alpha sort, built from the `categories` prop), and `categoryBreakdown(definitions, amountsForYear, transactions, categories)` aggregates budget-vs-actual per category (keyed by `categoryId`, `categories` — the prop — resolves display names) for the breakdown panel. Income editor (pencil-icon click-to-edit, on the Spend tab) dispatches `SET_BUDGET_INCOME { year: selectedYear, amount }` on Enter — a single plain yearly figure per year, no monthly/yearly split. Add-expense dialog (on `BudgetExpensesTab`) validates locally then dispatches `ADD_EXPENSE_DEFINITION`. Expense-table rows are edited per-cell, mirroring the Spend-records pattern below: clicking Name/an Amount cell opens a text/number input (Enter or blur commits `UPDATE_EXPENSE_DEFINITION`/`SET_EXPENSE_AMOUNT`/`CLEAR_EXPENSE_AMOUNT`, Escape reverts via `skipBlurCommitRef`); clicking Frequency/Category opens a `<select>` that commits immediately on `onChange` (Category's `__add_new` option opens the shared new-category dialog, applying the new id the same way); an unconditional trash-icon button triggers delete — first checking `expenseDefinitionInUse(state, id)` across ALL years' `budgetTransactions` (blocks with `window.alert` if referenced, see product-behavior.md), else `window.confirm`-guarded — there is no pencil button or edit-mode gating. Spend records table (on the Spend tab) is scoped to `selectedYear` only (`periodFilteredTransactions`) and dispatches `ADD_BUDGET_TRANSACTION`/`UPDATE_BUDGET_TRANSACTION`/`DELETE_BUDGET_TRANSACTION`; rows are edited per-cell (click a cell → inline input/select → commit on Enter/blur, revert on Escape via `skipBlurCommitRef`) rather than as a whole row, `recordSearch` filters (Description/Category/Account substring match) before `recSortBy`/`recSortDir` sorting and `recPage` pagination (50/page, active past 50 rows) apply, plus import (Copy-Paste tab: CSV via `parseBudgetTransactionsCsv` — 3-column `date,description,amount`, no category column; Upload file tab: CSV, OFX, or QFX, extension-selected between `parseBudgetTransactionsCsv` (`.csv`) and `parseOfxTransactions` (`.ofx`/`.qfx`) — none of these emit a category field; all require an account name and dispatch `IMPORT_BUDGET_TRANSACTIONS { rows, categories, categoryMappings }`). New categories are dispatched immediately via `categoryDispatch({type:'ADD_CATEGORY', ...})` from the "+ Add new category…" `<select>` option (id pre-generated by the caller via `uid('category')`), selecting the new id right away — unlike the old derived-category model, a newly typed category does not wait for the referencing record to be saved.

**Register** — `RegisterBalanceDialog`'s draft rows (`DraftRow[]`, both manual and paste modes) live entirely in component-local state, never `AppState`. "Save" converts valid draft rows to `BalanceEntry[]` and dispatches `ADD_BALANCE_ENTRIES`; editing an existing entry (`editingEntry` set) dispatches `UPDATE_BALANCE_ENTRY` instead — together these are the two write paths into `state.balanceEntries`. `RegisterPage` never reads component-local dialog state directly — after either dispatch, `selectors.ts`'s `registerCategoryCards`/`registerAllAccountsTotal` and `register.ts`'s `accountLedger`/`scopeLedger`/`registerChartSeries` re-derive the ledger rows, stats strip, and chart from the updated `state.balanceEntries` on next render, the same "selectors re-derive from raw collections" pattern used elsewhere.

**CSV import** — synchronous 2-step wizard inside `ImportDialog` (positions or transactions). Dialog-open state is component-local (`isOpen`), not in `AppState`. Paste mode maintains additional component-local state: `pasteHeaderClipboard`, `pasteValuesClipboard`, `pasteIssues`.
1. **Setup** (`step === 1`): pick data type (`.seg`: Transactions / Positions — default Positions), destination account (existing `<select>` or new-account form: name, number, category, retirement checkbox), and entry mode for positions (`upload`/`paste`/`manual`, default `upload`). Upload mode uses `.csv` file parsing (`parseCsvFile` from `csv.ts` -> `{ headers, rows }`). Paste mode feeds two clipboard paste zones (headers + values) into `tableToCsv()` (`pastedTable.ts`) to produce the same `csvHeaders`/`csvRows` state as upload, then shares Step 2's mapping/prefill/commit logic with no changes. Manual mode enters Step 2 with blank rows (no CSV parsing). Continue requires account resolution; upload and paste modes additionally require ≥1 parsed row, manual mode does not.
2. **Review** (`step === 2`):
   - Upload mode: `headers` drive one mapping `<select>` per non-asset-class field (`{ csvColumn: targetField }`, required then optional).
   - Manual positions mode: entering Step 2 seeds exactly 10 blank rows and renders no mapping selects for non-asset-class fields.
   - Positions `Asset Class` header is always a free-text `<input>` that broadcasts to rows not yet touched in their own `assetClass` cell.
   - Existing-account mapping prefill applies only in upload mode (`csvMappings` filtered to headers present in current file).
   - `applyFieldMap(row, fieldMap)` + `importEdits[rowIdx]` produce editable rows; `validatePreviewRow` handles required-field validation (with avgCost/purchaseAmount and price/marketValue alternatives). Fully-empty rows are valid and excluded at commit via `isBlankRow`.
   - Primary button gating: upload mode includes `isReviewValid(dataType, fieldMap)`; manual mode bypasses `isReviewValid` and additionally requires at least one valid non-blank row.
   - Row delete (`handleDeleteRow`) removes row + re-keys row-indexed edits/touched state.
3. **Commit**: primary button dispatches `ADD_ACCOUNT` first when new-account mode (capturing the new account id), then `IMPORT_POSITIONS` or `IMPORT_TRANSACTIONS` with `accountId`, valid non-blank edited rows, and fresh mapping profile saved. For positions, `IMPORT_POSITIONS` also carries `mode: entryMode === 'upload' ? 'replace' : 'merge'` (see `importPositions` below). `UPSERT_CSV_MAPPING` runs only in upload mode. "Import complete" renders in the same step-2 slot; "Done" closes and resets local state.

All steps are **synchronous**; no async queue beyond the debounce-save to IndexedDB.

**Password gate & hydration**: on mount, `App.tsx` calls `peekEnvelopeShape()` (`persist.ts`) to classify the stored IndexedDB record as `'absent' | 'legacy-plaintext' | 'encrypted'`, without decrypting anything (renders "Loading..." while this resolves). While `sessionKey` is `null`, `App` renders `PasswordGate` instead of the accounts/settings tree:
1. `shape === 'encrypted'` → enter-password screen: derives a key from the typed password against `peekStoredSalt()`, calls `loadPersistedApp(key)`; a decrypt failure (wrong password) surfaces as `OperationError` and shows "Incorrect password".
2. `shape === 'absent'` → set-password screen with an optional "Restore" tab-seg: offers "New Setup" (today's generate-key-and-set-password form) vs. "Restore" — which stacks a Google Drive card and a Backup file card — (temporary dummy key `generateSalt()` + `deriveKey(crypto.randomUUID(), dummySalt)` that guarantees the first `restoreBackupFromFileId(fileId, dummyKey)` call always throws `DriveDecryptError`, reusing the cross-password-prompt code path verbatim with no special branching). On restore success (direct pick or cross-password retry), calls `onUnlock(restoredKey, restoredSalt, restoredState)` just as the New Setup form does. Tab switching is free (no validation, state preserved per tab).
3. `shape === 'legacy-plaintext'` → set-password screen (no tab-seg): generates a fresh salt via `generateSalt()`, derives a key, and calls `loadLegacyPlaintextApp()` to read the old plaintext blob so it can be migrated.
4. Either path calls `onUnlock(key, salt, loadedState?)`: `App.tsx` sets `sessionKey`/`sessionSalt` React state, dispatches `__SET_STATE` with `loadedState` if present (decrypted, restored, or migrated data), and sets `isHydrated = true`. This is the **only** point `AppState` is populated from storage — no separate hydration effect.
5. "Back to portfolios" (text link/button, both screens) calls `onBackToPicker()` directly — no confirm dialog — which navigates away to `PortfolioPicker` without touching any persisted data. Recovery from a forgotten password is now: click "Back to portfolios", then use the picker's "Delete" action on that locked-out portfolio (works without needing that portfolio's password).
6. **Auto-lock on inactivity**: while `sessionKey !== null`, two `useEffect`s in `App.tsx` (same `if (sessionKey === null) return` gating as the Drive effects) drive re-locking: an activity listener (document-level `mousedown`/`keydown`/`touchstart`/`scroll`, deliberately not `mousemove`) updates `lastActivityTimeRef`; a periodic-check effect runs `checkAndMaybeLock()` every `LOCK_CHECK_INTERVAL_MS` (30s, via `setInterval`) and on every `visibilitychange`-to-`'visible'` (so a long-backgrounded tab locks immediately on refocus rather than waiting for the next tick). `checkAndMaybeLock()` calls `lockNow()` iff `(now - passwordEntryTimeRef.current >= LOCK_ABSOLUTE_MS) AND (now - lastActivityTimeRef.current >= LOCK_IDLE_MS)` — wall-clock `Date.now()` comparisons, so sleep/suspend gaps are handled correctly without tick-counting. `passwordEntryTimeRef` is set to `Date.now()` on every `onUnlock` (new setup, password entry, Drive restore) and on a successful Change-Password (`onPasswordEntryTimeReset`, see Password change below). Constants: `LOCK_ABSOLUTE_MS` (2h), `LOCK_IDLE_MS` (5min), `LOCK_CHECK_INTERVAL_MS` (30s) — hardcoded in `App.tsx`, not exposed in any Settings UI. `lockNow()` (1) fire-and-forget flushes `savePersistedApp(latestStateRef.current, key, salt)` (`.catch(console.error)`) using the still-valid key/salt refs, (2) sets `sessionKey`/`sessionSalt` to `null`, (3) dispatches `__SET_STATE` with `initialState()` — reusing the same `__SET_STATE`-to-`initialState()` mechanism as `handleBackToPicker` for a non-destructive purpose. Unlike `handleBackToPicker`, `lockNow()` does **not** navigate to `PortfolioPicker` (stays on `gateShape === 'encrypted'`) and does **not** touch any persisted data, so `PasswordGate`'s existing `EnterPasswordScreen` simply reappears — same screen as a fresh page load, no lock-specific UI or messaging.

**Persistence**: once unlocked, every state change schedules `savePersistedApp(state, sessionKey, sessionSalt)` 500ms later (debounced via `setTimeout` in a `useEffect`, cleared/reset on each state change; skipped entirely while `sessionKey`/`sessionSalt` are null). A separate effect flushes the pending save on `pagehide`, `visibilitychange → hidden`, and unmount (via refs holding the latest state, key, and salt — `latestStateRef`, `sessionKeyRef`, `sessionSaltRef` — so the flush sees values from an unlock that happened after the listener was registered) so a refresh/reload within the debounce window never loses the newest state (e.g. a just-finished import). `savePersistedApp` encrypts the whole state into an envelope (`encryptState`) before the IndexedDB write, and rethrows IndexedDB open/write failures so callers' `.catch` fires (no silent success).

**Load normalization** (`coalesceWithDefaults` in `persist.ts`): the single path every stored blob passes through, on both local unlock and Drive restore. Missing collections/fields fall back to `initialState()` defaults (`budgetExpenseDefinitions` defaults to `[]`, `budgetExpenseAmountsByYear`/`budgetIncomeByYear` default to `{}`, `budgetTransactions` defaults to `[]`, like every other collection) — this runs after the flat-shape/definitions-split migrations described above, so a modern blob's `budgetExpenseDefinitions`/`budgetExpenseAmountsByYear`/`budgetIncomeByYear` pass through untouched. `categories`/`categoryMappings` are no longer part of `AppState` at all, so `coalesceWithDefaults` no longer defaults or migrates them — any `category`/`categoryId` rewriting a blob might still need is out of scope for this function; a blob's raw (pre-coalesce) `categories`/`categoryMappings`, if present, are read once by the separate global-store seed migration (`categoryMigration.ts`'s `seedGlobalCategoriesIfNeeded`, via `persist.ts`'s `loadRawPersistedBlob`) instead. `view` is whitelisted rather than defaulted — a blob written before the Dashboard was removed carries the retired `view: 'dashboard'`, and anything other than `'accounts'`/`'settings'`/`'quotes'`/`'register'`/`'budget'` is coerced to the default `'accounts'`.

**Drive sync**: `drive.ts` exports a `drive` singleton (`createDriveSync({ appId: 'portfolio', clientId: VITE_GOOGLE_CLIENT_ID, folderPath: ['OpenWebApp','Portfolio'] })`, wrapped so `drive.project(id).pickFile(options)` resolves apiKey/appId/parentFolderId and delegates to `@open-webapp/drive-sync`'s own Picker-backed `pickFile`) plus `syncBackup(state, key, salt)` (encrypts state into an envelope, writes it as the Drive JSON file, resolves with the written file id)/`restoreBackupFromFileId(fileId, key)` (reads+parses the Drive JSON envelope for a specific file id, decrypts with `key`; throws `DriveDecryptError` — carrying the envelope's decoded `salt` and the raw `EncryptedEnvelope` — specifically on an auth-tag mismatch so a caller can retry with a different password without a second network round-trip)/`getBackupFileId()` (resolves the existing backup file id or null, for the "View backup in Google Drive" link only — not used to find what to restore; its own internal `NeedsReauthError` catch is a silent passive probe), all operating on `drive.project('app')`.

**Drive auth** (`@open-webapp/drive-connect`, `driveAuth` co-located in `drive.ts` to avoid an import cycle — a separate module would import `drive.ts` and vice-versa): `driveAuth = createDriveAuth({ drive: driveSync, projectId: 'app', tokenBufferMs: 5*60*1000 })`. Handle API: `getStatus()` (sync), `subscribe(fn)`, `refresh()`, `connect()`, `disconnect()`, `ensureFresh()`, `activate()`. It owns the connection-status store, the single `connectInFlight` guard (shared by `<GoogleDriveWidget>`'s Connect button and `ensureFresh()` — this is what prevents a double Google popup), and the visibility/pageshow token warm-up. The four content ops (`syncBackup`, `restoreBackupFromFileId`, `overwriteLocalWithRemote`, `overwriteRemoteWithLocal`) each `await driveAuth.ensureFresh()` before Drive I/O — a still-valid cached token is reused without prompting, an expired/missing one runs the interactive connect flow.

**App.tsx wiring**: `App.tsx` holds NO Drive auth state. It reads `const { connected } = useDriveConnection(driveAuth)` and passes `connected` to `<Nav>`. `backupFileId`/`syncing` remain lifted App state. `onDriveConnected` (fetches `getBackupFileId()` → `setBackupFileId` in its own try/catch — a failed lookup leaves `backupFileId` null, does NOT forget the connection) and `onDriveDisconnected` (`setBackupFileId(null)`) are passed to both `<PasswordGate>` and `<SettingsPage>`, which mount `<GoogleDriveWidget auth={driveAuth} onConnected={onDriveConnected} onDisconnected={onDriveDisconnected}>` themselves. A single effect gated on `sessionKey !== null` calls `driveAuth.activate()` (host-called — the widget never self-activates on mount) to start the background token warm-up only after local unlock; pre-unlock activation let a stale cached token surface a Google reauth prompt while the password screen was still showing. `Nav`'s sync-icon button is always rendered, `disabled={!connected || syncing}`, and calls the lifted `handleSync`. Hosts call `driveAuth.refresh()` (fire-and-forget, control flow unchanged) on a caught `NeedsReauthError` at five sites: `App.tsx` `handleSync` / `handleConflictTakeRemote` / `handleConflictPushLocal`, `Settings.tsx` `handleChangePassword` re-sync, and `DriveRestorePanel.tsx` `DriveFilePickerDialog.onSelect` (non-`DriveDecryptError` branch). Connect/disconnect no longer flip `syncing` (which now means only "a sync/restore content op is running") and no longer grey out the Restore button.

**Restore flow (shared `DriveRestorePanel` component)**: both `SettingsPage` and `PasswordGate`'s restore tab mount `<GoogleDriveWidget>` above `DriveRestorePanel`, and render the panel with different success callbacks (`onRestored`). The panel owns no connect/disconnect — `useDriveConnection(auth).connected` gates its "Restore from Drive" button and the "View backup in Google Drive" link. Restore (via a `DriveFilePickerDialog` "Pick a file" button that opens the Google Picker) and cross-password-prompt logic are identical in both contexts — the only difference is what fires on success. On `DriveDecryptError` from `restoreBackupFromFileId()`, the panel hides its picker dialog and shows an inline cross-password prompt: `deriveKey(typedPassword, error.salt)` + `decryptState(error.envelope, retryKey)` decrypt locally, then calls `onRestored(decryptedState, retryKey, error.salt)`. A wrong backup password renders a second `DriveFilePickerDialog` inline as a fallback, so the user can pick a different file without leaving the prompt. Requires `VITE_GOOGLE_CLIENT_ID` in `.env` (repo root, tracked in git) or OAuth connect fails (`token.ts` sends `client_id: undefined`); pinned by a test in `drive.test.ts`.

**Widget styling**: `src/index.css` does `@import '@open-webapp/drive-connect/styles.css'` and maps the package's `--owa-drive-*` custom props (`gap/font/fg/muted/accent/accent-fg/danger/radius`) onto portfolio design tokens under `:root` — `--owa-drive-danger` → `--color-text` (portfolio has no error-color token, so widget inline errors are not red). `src/styles/styles.css` untouched. Portfolio's Drive card buttons are no longer `.btn.btn-primary.blueprint` (accepted appearance change).

**Restoring a backup shared by another account**: there is no by-name lookup of a default backup at all — `restoreBackupFromFileId(fileId, key)` always operates on a file id the user explicitly picked via Google Picker (`DriveFilePickerDialog` → `drive.project('app').pickFile({ includeFolders: true })`), which starts scoped to the app's own `OpenWebApp/Portfolio` folder (via `ensureFolderPath()`) but lets the user navigate anywhere in their Drive using Picker's built-in UI — including a file merely shared with this Google account by another (not synced from it), which would otherwise sit outside the `drive.file` OAuth scope's visibility to a by-name `files.list` lookup. Picking a file server-side grants the app access to exactly that file, and `restoreBackupFromFileId` reads and decrypts it, throwing the same `DriveDecryptError` on a wrong-password mismatch as any other restore.

**Backup download & restore-from-file**: Download still happens in Settings — `buildExportableState(state)` (`importExport.ts`) picks the 8 array fields + the 4 Budget fields (`budgetIncomeByYear`/`budgetExpenseDefinitions`/`budgetExpenseAmountsByYear`/`budgetTransactions` — `categories`/`categoryMappings` are no longer part of `AppState`/`ExportableState`; they have their own "Download/Import Category Mapping" controls, see "Global Categories" above) + `priceSync`/`mutualFundSync` `{apiKey, lastRun}` into an `ExportableState`, `exportBackup(state, sessionKey, sessionSalt)` encrypts it into an `EncryptedEnvelope` (same `crypto.ts` primitives as the app-state envelope), `downloadEnvelopeAsFile()` triggers a Blob download named `ledger-backup-YYYY-MM-DD.json` — no password prompt, uses the live session key/salt silently. `SettingsPage`'s Backup tab (`settingsSection === 'backup'`), second card (Download), no longer has any upload/restore UI. Restore-from-file now happens only at the password gate, pre-unlock, via `GateRestoreFromFilePanel` (the Restore tab's "Backup file" card): file read → `parseImportFile(fileText)` validates JSON/envelope shape, throwing `ImportMalformedFileError` inline ("This file isn't a valid backup") before any password prompt is shown → password prompt (decryption uses the **file's own embedded salt**, not any session salt, since no session exists yet) → `decryptImportEnvelope(envelope, password)`, wrong password throws `ImportDecryptError` shown inline ("Incorrect password", retryable without re-picking the file) → on decrypt success, `replaceImportedState(initialState(), decrypted)` (`state.ts`) merges the `ExportableState` onto a blank `initialState()` and the panel calls `onUnlock(key, salt, mergedState)` directly — no `window.confirm`, since there is nothing pre-unlock to overwrite. `replaceImportedState` is called directly by `GateRestoreFromFilePanel` now (not dispatched through the reducer — there is no corresponding reducer action). No Drive/network interaction anywhere in this flow — pure local file I/O.

**Back to portfolios**: `PasswordGate`'s `GateShell` (both gate screens) renders a plain "Back to portfolios" link/button, `onBackToPicker` prop, that navigates to `PortfolioPicker` without touching any persisted data — no confirmation dialog, no data wipe. Settings > Encryption no longer has any destructive-reset card. Recovery from a forgotten password is now: click "Back to portfolios", then use the picker's "Delete" action on that locked-out portfolio.

**Password change** (`SettingsPage.handleChangePassword`): verifies the typed current password by deriving a key against `sessionSalt` and attempting `loadPersistedApp(candidateKey)` (a real decrypt, not a stored-hash check); on success generates a brand-new salt (`generateSalt()`, never reuses the old one), derives a new key, and calls `savePersistedApp(state, newKey, newSalt)`. If Drive is connected (`driveAuth.getStatus().connected`, sync), also calls `syncBackup(state, newKey, newSalt)` — a failure here is caught and shown as a non-blocking warning (byte-identical copy: "…Sync manually from Google Drive Sync above."), a `NeedsReauthError` additionally fires `driveAuth.refresh()`; it does not undo the already-completed local `savePersistedApp`. On success calls `onKeyChange(newKey, newSalt)` to update `App.tsx`'s session state, and also calls the new `onPasswordEntryTimeReset` prop (resets `passwordEntryTimeRef` to `Date.now()` in `App.tsx`, same as `onUnlock` — restarts the 2h auto-lock window).

**Selectors** (`selectors.ts`) are the only place that reads+filters+sorts raw `AppState` collections for display; components call them instead of re-deriving:
- `visibleTransactions(state)` — type filter → search (symbol/date) → always sorted by `date desc` (not user-sortable).
- `allocationBars(positions)` — wraps `computations.allocationByAssetClass` over an explicit `positions` array (caller scopes it), respecting `assetClassManualOverride`; returns `pctNum` alongside the formatted `pct` string.
- `assetClassOptions(state)` — Deduplicates and sorts effective asset classes (manual override or original) across all positions (global, not selection-scoped).
- `filteredPortfolioTotal(state)` — Sum of market values across every position (unfiltered); denominator for `PositionGroupOverlay`'s `% of Portfolio` display.
- `categoryCards(state)` — one card per tax category (Taxable/Non-Taxable/Tax-Deferred) for the Accounts page's left column: per-account total/`updatedStr`/selection state, category total, `expanded` from `state.expandedCategories`.
- `acctScopedPositions(state)` — `state.selectedAccountId`'s positions, or all positions if none selected.
- `acctAssetClassOptions(positions)` — distinct effective asset classes among the given positions (used with `acctScopedPositions` to build the Accounts page's asset-class filter options).
- `acctFilteredPositions(state)` — `acctScopedPositions(state)` further filtered by `state.acctAssetClassFilter`/`state.acctPosSearch`; denominator for the Accounts page's `% of Selection` display.
- `acctAllocationTitle(state)` — `"Allocation — {account.name}"` or `"Allocation — All Accounts"`, based on `state.selectedAccountId`.
- `registerCategoryCards(state)` — one card per tax category for RegisterPage's left column: per-account `totalStr`/`asOfStr`/`entryCount`/selection state (via `latestBalance`), category `totalStr`, `expanded` from `state.regExpanded`, `hasAccounts`.
- `registerAllAccountsTotal(state)` — `fmtUSD` sum of every account's latest `BalanceEntry.balance` (via `latestBalance`), for RegisterPage's "All Accounts" card.
- `acctAllAccountsTotal(state)` — unscoped `fmtUSD` sum of `shares*price` across all of `state.positions` (never closed positions), for the Accounts page's "All Accounts" pill.
- `mappingsForExpense(mappings, spendExpenseId)` — `CategoryMapping[]` for one expense, sorted by `substring`; used by Budget > Category Mapping.
- `visibleExpenses(definitions, amountsForYear, filterCategoryId, sortBy, categoriesById)` — filters `ExpenseDefinition[]` by `categoryId` (or all) and sorts by name/category/amount (category-name sort resolved via the `categoriesById: Map<string, string>` id→name lookup; amount sort reads `amountsForYear[id]`, a single year's `Record<string, number>` — `BudgetExpensesTab` passes `{}` here since its own sort options are just `'category' | 'name'`, not `'amount'`). `BudgetExpensesTab` additionally reverses this array locally to support descending sort per column-header click.
- `categoryBreakdown(definitions, amountsForYear, transactions, categories)` — aggregates `ExpenseDefinition[]` by `categoryId` against a single year's `amountsForYear: Record<string, number>`, joined against `actualByCategory(transactions, definitions)` for the Actual/Variance figures, with `categories: Category[]` resolving each entry's display `name`; `budgetPct`/`actualPct` per entry are relative to the largest category's budget/actual total (not the sum of all categories); sorted by budget amount descending.
- `actualByCategory(transactions, definitions)` — sums `BudgetTransaction.amount` per effective `categoryId` (via `effectiveCategoryId(t, definitions)`) into a `Record<string, number>`; used by `categoryBreakdown`. Does not itself filter by `excludeFromSpend` — callers filter transactions first (see below).
- `effectiveCategoryId(tx, budgetExpenseDefinitions)` — returns the linked `ExpenseDefinition.categoryId` when `tx.spendExpenseId` is set and resolves against `budgetExpenseDefinitions` (global, no year matching); otherwise falls back to `tx.categoryId` (legacy). Used by every actual-spend-derived selector (`categoryBreakdown`'s transaction pass, per-period/per-category transaction filtering, exclusion checks) instead of reading `tx.categoryId` directly.

## Key Invariants

- **Account cascade delete**: Deleting an `Account` cascade-deletes all its `Position`s, `ClosedPosition`s, `Transaction`s, `PortfolioSnapshot`s, `SavedCsvMapping`s, and `BalanceEntry`s.
- **importPositions replace vs merge mode**: `importPositions(state, accountId, mappedRows, importDate, mode)` (`mode: 'replace' | 'merge'`, default `'replace'`). `'replace'` (CSV-upload, a full broker export) replaces the account's entire position list; symbols missing from the new rows become `ClosedPosition`s. `'merge'` (manual entry / Copy-Paste, inherently partial batches) upserts new rows by symbol into the account's existing positions — untouched symbols are left alone and nothing is closed. `ImportDialog` dispatches `mode: entryMode === 'upload' ? 'replace' : 'merge'`.
- **Position delete = close, not hard delete**: deleting a position from `PositionGroupOverlay` (`CLOSE_POSITION` action) converts it to a `ClosedPosition` with `realizedGL: null`, `realizedGLBasis: 'unknown'` (never transaction-matched, unlike the reimport-driven auto-close path in `positionsImport.ts`) — same target shape, different trigger and always-unknown basis.

## Design patterns

- **Computed-not-stored**: `marketValue`/`costBasis`/`gl`/`glPct` are never persisted on `Position`; always derived via `computations.computePosition()`.
- **Category filter is compositional**: every selector re-derives "accounts in category" via a local `getAccountsForCategory`/inline filter rather than storing a filtered account list.
- **Effective asset class**: anywhere a position's asset class is displayed or grouped, code reads `p.assetClassManualOverride || p.assetClass`, never `p.assetClass` alone.
- **Natural-key upsert**: `positionsImport.ts` (snapshot) and `transactionsImport.ts` (transaction) both dedup by recomputing a string key and filtering pre-existing entries out before appending, rather than mutating in place.
- **Session-key lifecycle**: the derived `CryptoKey` + PBKDF2 salt (`sessionKey`/`sessionSalt`) live only as React state in `App.tsx`, set once by `PasswordGate`'s `onUnlock` (or rotated by `SettingsPage`'s `onKeyChange`) and threaded down via props to `SettingsPage` — they are explicitly **not** fields on `AppState` and never flow through the reducer or `__SET_STATE`. They are additionally mirrored into `sessionKeyRef`/`sessionSaltRef` (plain refs, updated on every render) purely so the pagehide/unmount flush-save listener — registered once on mount — can read the latest values without re-registering. Losing this state (refresh, tab close) is by design: it is what makes the password required every session. Two more refs follow the same mirroring pattern to drive auto-lock without re-registering effects: `lastActivityTimeRef` (updated by the document-level activity listener) and `passwordEntryTimeRef` (set on `onUnlock` and on a successful Change Password via `onPasswordEntryTimeReset`) — read by the periodic/`visibilitychange` lock-check effect (see "Auto-lock on inactivity" in Data flow) to decide when to call `lockNow()`, which clears `sessionKey`/`sessionSalt` the same way losing them on refresh/tab-close does, just triggered proactively instead of by navigation.
- **Styling**: components use inline `style={{ ... }}` extensively alongside the design-system classes (`.card.blueprint.elev-sm`, `.tag`/`.tag-accent`, `.seg`/`.seg-opt`, `.table`, `.nav`, `.field`/`.input`, `.dialog-backdrop`/`.dialog`) — this is a live deviation from the CLAUDE.md styling rule ("Components consume the existing class vocabulary ... rather than inline styles"); most layout/spacing (flex, gap, padding, modal positioning) is inline today, only the visual vocabulary (colors, card chrome, tags, table borders) comes from `styles.css` classes.
- **Hand-mirrored dual artifact**: `src/lib/pastedTable.ts` (typed ES module) is paired with a root-level `pastedTable.js` (classic-script, `window.PastedTable` global, no `import`/`export`) — one hand-maintained copy of the same logic per runtime, no build step generates one from the other. `pastedTable.js` sits outside `tsconfig.app.json`'s `include`, so it is never typechecked or bundled; parity between the two is enforced entirely at test time by one shared vitest case table (`src/lib/pastedTable.test.ts`) run against both implementations. Editing one copy without the other does not fail `tsc -b` — it only fails that shared-case test suite, so the two files can silently drift until tests are run.
