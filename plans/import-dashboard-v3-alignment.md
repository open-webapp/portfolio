# Import Dashboard v3 Alignment

## Overview

Two independent goals, diffed `design/v2/project/Portfolio Dashboard.dc.html` vs `design/v3/project/Portfolio Dashboard.dc.html` (untracked, new handoff). All markup/JS diffs are confined to the CSV import dialog (HTML ~118-296, JS ~946-1086); the dashboard markup (nav, summary cards, chart grid, allocation, tabs) is byte-identical v2↔v3, so goal 2 is a drift-audit against v3 alone (equivalently v2), not a v2→v3 migration.

1. **Rebuild CSV import as a 2-step wizard** (Setup → Review), replacing the current bespoke 4-step flow in `src/components/import/ImportDialog.tsx` (1566 lines, uses `use-existing`/`create-new` profile branching + "Enter a value…" constants — neither exists in v3's rendered UI). Mapping profiles are removed **entirely** from the codebase, not just the dialog.
2. **Fix dashboard layout drift**: chart row `1fr 1fr` → `2fr 1fr`; Positions/Transactions tab selector → `.seg`/`.seg-opt`; "Import CSV" button moved into the same row as the tabs (`justify-content:space-between`); full pass for other structural mismatches.

## Key facts gathered while planning

- **Mapping profiles have no dependents outside the obvious set.** `grep -n "mappingProfile\|MappingProfile"` across `src/` hits exactly: `state.ts` (field + import + default), `reducer.ts` (3 cases), `types.ts` (interface), `mappingProfiles.ts` (whole module), `persist.ts` (1 migration line), `Settings.tsx` (whole "Saved Mappings" section + modal), `App.test.tsx` (several test blocks, some already marked as superseded-but-not-deleted), `ImportDialog.tsx`/`ImportDialog.test.tsx`/`MappingProfileEditor.tsx`/`MappingProfileEditor.test.tsx`. **`src/lib/accounts.ts` has zero references** — confirmed via grep, so account-resolution logic is untouched by this removal. There is no standalone `src/lib/accounts.test.ts` file (checked, doesn't exist).
- **`App.test.tsx` already contains dead test blocks**: lines ~446-450 have a comment "These tests are for the old import flow and have been superseded by C11's ImportDialog.test.tsx" but the tests were apparently never deleted — they still build `MappingProfile` fixtures and assert on `state.mappingProfiles`. These must be deleted, not just re-commented.
- **`persist.ts` migration tolerance already handles this correctly by construction**: `loadPersistedApp` explicitly whitelists known `AppState` keys into a fresh `migrated` object (`accounts: loaded.accounts ?? defaults.accounts`, etc.) rather than spreading `loaded` — so once `mappingProfiles` is removed from `AppState` and from this whitelist, a stale persisted blob with a leftover `mappingProfiles` array is simply never read into the new state. No special "drop the key" code needed, just delete the one line (`mappingProfiles: loaded.mappingProfiles ?? defaults.mappingProfiles,`).
- **Current `ImportDialog.tsx` does not use the design's CSS vocabulary at all** — no `.dialog`/`.dialog-backdrop`/`.seg` classes, everything is inline `style={{...}}` with ad hoc colors (`rgba(200, 50, 50, ...)` for errors instead of `var(--color-accent-2-800)` used consistently, though it does use that var in a few spots). The v3 rebuild is a full rewrite of the render tree, not a patch — plan tasks below treat it that way rather than trying to preserve the current JSX shape.
- **v3 Review step column headers double as mapping selects**: each `<th>` contains the field label + a `<select>` bound to that field's mapping (`onMapChange`), directly above the preview `<td>` cells for that column — this is a materially different DOM shape than today's separate "mapping grid" `<table>` + "preview" `<table>`. The plan below has the Review step render one `<table>` where `previewCols`/`reviewCols` drives both `<thead>` (label + select) and `<tbody>` (editable cells), per column.
- **No "Enter a value…" in v3's rendered markup** — the mock's `<select>` in the Review `<th>` only has `— Not mapped —` + CSV header options, no constant-value option, even though leftover `isConstant`/`onConstantChange` JS fields exist in the v2 diff remnants. Confirmed: v3's `reviewCols` mapping (`stepLabels`, `reviewCols` builder in JS ~980) has no `constants`/`isConstant` references at all — this was fully dropped, not just hidden.
- **v3 primary button behavior**: `step === 2` → label is `st.importDone ? 'Done' : 'Import'`, disabled `!st.importDone && (!step2Valid || hasImportErrors)`. `step2Valid` = every required field mapped (equivalent to today's `validateProfile`-style check, now inlined since there's no profile object). No separate "Review Import" state.
- **Existing-account label picked up an account-number suffix in v3**: `importDestinationLabel` for existing-account mode is now `name + (' • #' + number)` when a number exists (v2 had just `name`). Small copy change to carry over.
- **`design.md`, `product-behavior.md`, `schema-spec.md` all currently document the old 4-step/profile-based flow** (`design.md` lines ~24, 41, 43-44, 67, 99-100, 113, 120-122; `schema-spec.md` lines ~5, 85, 123, 153-155; `product-behavior.md` lines ~49-61, 90-94) — these need a full rewrite of the affected sections, not incremental edits, since the whole subsystem they describe is being deleted/replaced. Per CLAUDE.md's "Supersede plans" rule, once updated these three files are canonical; `plans/portfolio-dashboard-v1.md`, `plans/portfolio-dashboard-v2-alignment.md`, and all `plans/*mapping-profile*`/`plans/import-step2-profile-flow.md`/`plans/unify-import-dialogs.md` plans become historical-only.
- **No visual regression tooling exists in this repo** (confirmed via `npm run test`/repo scan — vitest + jsdom only, no screenshot/pixel-diff harness). Dashboard layout fixes are verified by reading rendered inline `style` props / class names in the diff and by any DOM-structure assertions already in `App.test.tsx` (e.g. asserting `gridTemplateColumns` or class names) rather than new visual tests — call this out explicitly rather than inventing a testing tool that doesn't exist.

## Judgment calls (flagged, not yet confirmed by user)

1. **Local dialog-open state stays component-local** (`isOpen` in `ImportDialog.tsx`), matching current behavior and v2-plan's precedent — v3's `importOpen`/`openImport` in the mock JS doesn't imply it must move into `AppState`; keeping it local avoids persisting transient UI state. Flag in case `AppState.importOpen` was actually wanted.
2. **`reviewCols`/preview-table cell editing keeps today's `importEdits: Record<rowIdx, Record<field, value>>` overlay model** (edit layer on top of mapped CSV values) rather than v3 JS's implied per-cell `onChange` closures, since the two are behaviorally equivalent and today's shape is simpler to test. Flag in case exact JS-closure-per-cell fidelity was wanted.
3. **`step2Valid` reimplemented as a small local helper** (`isReviewValid(dataType, fieldMap): boolean` checking all `POSITIONS_REQUIRED_FIELDS`/`TRANSACTIONS_REQUIRED_FIELDS`, honoring the avgCost/purchaseAmount and price/marketValue alternative pairs) rather than resurrecting `validateProfile` from the deleted `mappingProfiles.ts` — since profiles are gone, this logic moves into `ImportDialog.tsx` directly (or a new tiny `src/lib/importMapping.ts` if it and `applyMapping`-equivalent logic together exceed ~40 lines, per CLAUDE.md's one-test-per-lib-module convention). Flag: exact home (inline vs. new lib file) is a call made during implementation (task B1 below), not fixed here.
4. **`applyMapping`-equivalent logic is kept but de-profile-ified**: a plain function `applyFieldMap(row: Record<string,string>, fieldMap: Record<string,string>): Record<string,string>` (CSV column → target field rename only, no `constants` merge since constants are removed) replaces `mappingProfiles.ts`'s `applyMapping`. Lives alongside `isReviewValid` per judgment call 3's home decision.
