# Product Behavior — Ledger (Portfolio Dashboard)

See also: [design.md](design.md), [schema-spec.md](schema-spec.md)

Local-first, single-user portfolio tracker. No live price feed — all values come from user-imported CSVs. No Watchlist/Alerts feature (out of scope; must never reappear — grep `watchlist` case-insensitive in `src/` must return nothing).

## Layout

Five views: **Budget**, **Accounts** (nav label "Positions"), **Register**, **Quotes**, and **Settings**. Accounts view, top to bottom: `Nav` → 2-column layout with an "All Accounts" card + collapsible category cards (left, 360px) and a flexible right panel holding the allocation chart, asset-class filter + "Import" button row, and the aggregate positions table (or the closed-positions table) — see "Accounts page" below. Register view: `Nav` → 2-column layout with a scope picker (left, 360px) and stats/chart/activity table (right) — see "Register" below. Budget view: `Nav` → single centered card — see "Budget" below. Settings view: `Nav` → centered settings card (max-width 560px).

**Default landing page**: Accounts. A fresh install opens there; thereafter the last-viewed view is persisted, so an app locked on Settings reopens on Settings. A backup written by an older build that recorded a now-retired view opens on Accounts rather than failing to render.

## Nav

Nav renders on every view. Logo mark (accent-filled square with a plus-icon SVG) + "Ledger" brand, followed by 4 always-visible div-based pills (not radio-input `.seg`), in order:

- **Budget** — the income/expense budget tracker. Active when `state.view === 'budget'`. First pill.
- **Positions** — the Accounts page. Active when `state.view === 'accounts'`.
- **Register** — the balance-history tracker. Active when `state.view === 'register'`.
- **Quotes** — read-only held-symbol price table. Active when `state.view === 'quotes'`.

Each pill shows a grid icon + label; clicking dispatches `SET_VIEW` for that pill's view. The active pill gets accent text color and background; inactive pills are muted with a hover highlight. Settings has no nav pill — it's reached only via the gear icon (below) and is not part of this 4-tab row even though `'settings'` is itself a `view` value.

- **Sync Now icon button** (refresh icon, `title="Sync now"`): always rendered; `disabled` whenever Drive is not connected or a sync/restore is in progress (`!connected || syncing`). Triggers a backup sync to Google Drive.
- **Settings gear** (SVG icon): navigates to the Settings page (resets `settingsSection` to "Backup" on every open).

## Allocation chart

Reusable `.card.blueprint.elev-sm` component taking `positions: Position[]` and `title: string` props. Renders a 2-column grid grouped by *effective* asset class (`assetClassManualOverride || assetClass`), computed via `allocationBars(positions)`. Each cell shows: class label + USD value inline (12px font), percentage right-aligned (muted), and a compact horizontal bar (height 6px, accent color fill) sized to percentage of total portfolio value.

- **Accounts page usage** — the only usage: called with selection-scoped positions (all accounts, a single account, or a single account's closed positions) and a title of `"Allocation — All Accounts"`, `"Allocation — {account.name}"`, or `"Allocation — {account.name} (Closed)"` per selection state.
- Empty positions list → empty grid with no crash.

## Transactions table

(Not rendered in any current view; kept for data-model and future-surface reasons.)

- Type filter tags (`All` + every distinct `Transaction.type` currently in state, alphabetical) + free-text search (symbol or date substring, case-insensitive).
- Always sorted by date descending — no user-controlled sort.
- Columns: Date (formatted `MMM D, YYYY`), Symbol, Type (colored tag: Buy=accent, Sell=outline, Dividend=neutral, anything else=neutral), Shares, Cost Basis, Amount Invested, Position Link.
- **Position Link**: shows an "UNMATCHED" outline tag (with a tooltip explaining "likely fully sold or removed") when the transaction's symbol has no corresponding open `Position`; otherwise shows plain "Linked" text. This is purely derived per render — no stored flag.

## Accounts page

2-column layout accessed via the "Positions" tab in the Nav. Left panel (360px fixed width) shows an "All Accounts" card followed by collapsible category cards; right panel (flexible) shows allocation chart, filter controls, and aggregate positions table.

- **"All Accounts" card** (always first, always visible): shows the sum of market value across ALL positions, unscoped by category/account/filters (`acctAllAccountsTotal`). Click dispatches `CLEAR_ACCOUNT_SELECTION`; highlighted when `state.selectedAccountId === null`.

**Left panel — Category cards** (Taxable / Non-Taxable / Tax-Deferred / Closed Positions order):
- **Card header** (click to toggle expanded state): category/collection label + account-count badge (`.tag.tag-neutral`, unfiltered count for category cards; for Closed Positions, badge is fixed at account count of those with ≥1 closed position).
- **Collapsed state** (default): shows only the header with badge.
- **Expanded state**: lists account rows, each clickable (cursor pointer), styled with:
  - Institution and account name on line 1 (or name only if institution is empty), using institution—name format.
  - Tags on line 2: for Taxable/Non-Taxable/Tax-Deferred cards, total value (formatted USD), account number, updated date (ISO format); for Closed Positions card, realized G/L sum (formatted USD, or `—` if all underlying closed positions have `realizedGLBasis === 'unknown'`), account number, updated date.
  - Click to select: dispatches `state.selectedAccountId` or toggles if already selected (toggle semantics). Global selection state persists across category expansions.
- **Closed Positions card** (4th card, always shown in the card list): visible only if ≥1 account in state has ≥1 closed position. Badge shows total count of such accounts. Expanded list shows only accounts with closed positions. Totals on line 2 are realized G/L sums per account.

**Right panel** (flexible width):
- **Allocation chart** — top: `AllocationChart` component with positions from current selection (all accounts, single account, or single account's closed positions) and title `"Allocation — All Accounts"`, `"Allocation — {account.name}"`, or `"Allocation — {account.name} (Closed)"`.
- **Filter row** — asset-class `.seg` radio control (computed from all positions, not selection-scoped, sorted alphabetically) + "Import" button. Free-text search field for symbol/name filtering. When Closed Positions + account is selected, asset-class filter and search are scoped to that account's closed positions only.
- **Aggregate Positions table** (open positions view; shown when a Taxable/Non-Taxable/Tax-Deferred category account is selected, or "All Accounts" is selected) — sorted by column selection (`state.sortKey`/`state.sortDir`, toggled via `TOGGLE_SORT`). **Columns**: Symbol, Asset Class, Shares, Avg Cost, Current Price, Amount Invested, Market Value, G/L, G/L %, **% of Selection** (percentage of selection total, not whole portfolio), Row-count badge. **% of Selection** reflects only positions in the current selection (account or all). Rows are **aggregate groups** — one row per unique grouping key (`trackingSymbol || symbol`, i.e. a position's tracking symbol takes precedence over its own symbol when set) + effective asset class; tax category and retirement status do not partition groups, so matching positions merge across accounts. Every group, including size-1, renders as one row. Groups aggregate shares, cost basis, and market value; price is derived as summed value / summed shares.
  - **Sorting**: clicking a sortable header (Symbol/Asset Class/Shares/Avg Cost/Current Price) toggles asc/desc via `TOGGLE_SORT`; clicking the active column flips direction, a different column resets to `asc`. An `↑`/`↓` arrow marks the active column. Sorting orders by aggregate/derived group values, computed client-side after grouping. Amount Invested/Market Value/G/L/G/L % are display-only, not sortable.
  - **Row click → overlay**: clicking any row (cursor pointer) opens `PositionGroupOverlay`, a dialog (`.dialog-backdrop`/`.dialog`, closable via Escape/backdrop-click/X button). Title: `` `Symbol — Name — Asset Class` ``, where the "Symbol" slot shows the group's Tracking Symbol instead of its own Symbol when one is set on the group. Lists the underlying positions sorted by account.institution, then account.name, falling back to account.accountNumber. **Overlay columns** (11): Account, Symbol, Tracking Symbol, Name, Shares, Avg Cost, Current Price, Market Value, % of Portfolio, Override, Delete. **Account display (two-line)**: line 1 institution—name (or name alone if no institution); line 2 muted tax-category and retirement labels (e.g. "Taxable • Retirement"). **Editable cells**: Account (dropdown listing all accounts; selecting dispatches `UPDATE_POSITION` with `patch: { accountId }`); Symbol and Name (`<input type="text">`, click-to-edit, empty/whitespace-only reverts silently, trimmed non-empty commits); Tracking Symbol (same input style, but empty is a valid commit — submitting blank clears an existing tracking symbol via `patch: { trackingSymbol: undefined }`, reverting the position to grouping/display by its own Symbol; a no-op submit that doesn't change the effective value dispatches nothing); Shares/AvgCost/Price (`<input type="number">`, click-to-edit; valid non-negative number commits, invalid/empty reverts silently, no error UI). All fields: Enter or blur commits, Escape reverts with no dispatch. % of Portfolio is display-only and uses the whole-portfolio total (every position), not the current selection. **Side effect**: editing Symbol, Tracking Symbol, or Account changes the position's group key, so its row disappears from the open overlay on the next render (the overlay stays open — a natural re-render consequence). **Delete column**: blank header, trash-icon button per row; prompts `window.confirm('Delete this position? It will be moved to Closed Positions.')`; on confirm dispatches `CLOSE_POSITION`, converting the position into a `ClosedPosition` (`realizedGL: null`, `realizedGLBasis: 'unknown'`, `closedDate` = today) rather than hard-deleting it. Override column contains the `AssetClassOverrideSelect` control.
- **Closed Positions table** (closed positions view; shown when Closed Positions card + account is selected) — **Columns**: Security (symbol + name), Closed (date, ISO format), Realized G/L (signed formatted USD, or `"unknown"` if `realizedGLBasis === 'unknown'`), Delete (trash-icon button per row, triggering confirm `"Delete this closed position? This permanently discards its realized G/L history."`, removing on confirm). Asset-class filter and symbol search apply. No `PositionGroupOverlay` interaction. Realized G/L is never a fabricated number — `"unknown"` is shown when the basis is unknown.
- **Empty state**: "No positions to show." when selection has no positions.

**Two-card overlap**: an account with both open and closed positions appears in two cards — one in its tax-category card (Taxable/Non-Taxable/Tax-Deferred) and one in the Closed Positions card. Selecting the account under one card sets `state.selectedAccountId` globally, but the visual selection highlight is scoped to the card it was selected from — the account does not highlight under the other card simultaneously. Switching to view the account's data (in the right panel) toggles between open-positions view (when selected from a tax-category card) and closed-positions view (when selected from Closed Positions card).

**No longer shown**: "Subtotal row", "Cash/Investment/Total" column split, 3-section (Taxable/Non-Taxable/Tax-Deferred) table layout, dividers between sections. **Account CRUD**: remains in CSV import flow only (new-account form at import time).

## Register

Accessed via the Nav's "Register" tab. A manually-recorded balance-history tracker, independent of imported Positions/Transactions — data comes only from user-entered `BalanceEntry` rows via the "Record Balances" dialog.

**Layout**: 2-column, left scope picker (360px) + right balance-history panel.

**Left panel — Scope picker**:
- **"All Accounts" card** (always first, always visible): shows the sum of every account's latest recorded balance (`registerAllAccountsTotal`). Click selects the "All Accounts" scope (`SET_REG_ACCOUNT` with `accountId: null`); highlighted when no account is selected.
- **Category cards** (one per tax category — Taxable/Non-Taxable/Tax-Deferred, via `registerCategoryCards`): header (click toggles expand via `TOGGLE_REG_CATEGORY_EXPANDED`) shows category label, account-count badge, and category total (sum of member accounts' latest balances). Expanded: one row per account showing institution—name, that account's latest balance, an "N entries" tag, and an "As of {date}" tag; empty categories show "No accounts in this category." Clicking an account row selects it (`SET_REG_ACCOUNT`) as the scope; selected row is highlighted.
- Scope selection is a single global `state.regAccountId` (not a toggle — clicking an already-selected row does not deselect; only clicking "All Accounts" or a different account changes scope). Category expand/collapse state is per-category (`state.regExpanded`), independent of scope selection.

**Right panel — Balance history** (scoped to the selected account, or every account when scope is "All Accounts"):
- **Title**: `"{institution} — {name}"` for a single account, or `"All Accounts — Balance History"`.
- **Stats strip** (4 cells, derived from the scoped ledger via `accountLedger`): Current balance (latest recorded balance, summed across scope accounts); Net change recorded (sum of period-over-period balance deltas, `null`/opening entries excluded); From activity (sum of each entry's `activities` amounts, each signed by `ACTIVITY_SIGN[type]`); Unexplained (Net change minus From activity, i.e. the portion of each balance change not attributed to a recorded activity type). Net change / From activity / Unexplained are signed (`+`/`-`) and colored gain/loss green/red by sign.
- **Balance-over-time chart**: SVG line+area chart plotting the scoped total balance at each recorded date (carrying forward each account's last-known balance between its own entries), with Y-axis USD gridline labels and up to 6 X-axis date-tick labels. Each point has a hover tooltip (`{date} — {balance}`). Single-point series render a centered flat line.
- **Activity filter**: `.seg` radio, `All` / `With Activity` (dispatches `SET_REG_ACTIVITY_FILTER`) — `With Activity` hides entries with zero `activities` (`activities.length === 0`).
- **"Record Balances" button**: opens the Record Balances dialog (below); dialog-open state is component-local.
- **Activity table** (newest-first, then by accountId; scoped + filtered via `scopeLedger`): Date, Account (name + institution), Balance, Change (`+`/`-` USD, or "Opening" for an account's first-ever entry), Attributed activity — stacks one tag per activity (type + signed amount + optional note), row grows to fit (no truncation); shows "Not attributed" only when `activities.length === 0`, Unexplained (signed USD, or `—` for an opening entry), Delete. Clicking a row (anywhere but the trash icon) opens the Edit Balance Entry dialog for that entry — see below.
- **Delete**: trash-icon button per row; `window.confirm('Delete this balance entry? This cannot be undone.')`, then dispatches `DELETE_BALANCE_ENTRY`.
- **Empty state**: "No balance entries recorded for this scope yet." when the filtered/scoped row list is empty.

**Record Balances dialog** (`RegisterBalanceDialog`): mode `.seg` — **Enter manually** (default) or **Copy-Paste**.
- **Manual mode**: an editable draft-row table (Date, Account select, Balance, one or more Activity entries, remove-row button), seeded with one blank row (account pre-filled from the current Register scope if one is selected, date pre-filled to today). "+ Add row" appends another blank row. Each activity, rendered as its own row beneath the balance row, has its own "+ Add activity" button to append another activity and a per-activity remove button — available in both add-mode and edit-mode rows.
- **Copy-Paste mode**: two paste zones (Headers, Values), parsed via the same `tableToCsv()` clipboard parser CSV import uses, then mapped to fields by header-hint matching (`BALANCE_FIELD_HINTS`: date/account/balance/activityType/activityAmount/note) — account values are fuzzy-matched to an existing `Account` by id/name/number/institution—name (`matchAccountId`), activity values matched by exact or prefix match against the 7 activity types (`matchActivityType`, defaulting to `None`), dates normalized to `YYYY-MM-DD` (`normalizeDateInput`). Pasting rebuilds the draft-row table from the parsed result; an inline error shows if either zone is empty or parsing yields no headers/rows.
- **Row validity**: a row is valid (`isDraftRowValid`) once it has a date, an account, and a numeric balance — activity fields are optional. Invalid required cells get a red border. Save is disabled at 0 valid rows; its label reads "Save N entries"/"Save 1 entry".
- **Commit**: Save normalizes each activity item on a row (`amount` = `Math.abs(parseFloat(amount)) || 0`; unmatched activity type falls back to `'None'`), converts valid draft rows to `BalanceEntry[]` (activity amounts non-negative — sign is derived at read time via `ACTIVITY_SIGN`) and dispatches `ADD_BALANCE_ENTRIES`, then closes and discards local draft state. Cancel/✕/backdrop-click closes without saving.
- **Replace semantics**: recording a new entry for an `(accountId, date)` pair that already has an existing entry **replaces** it — existing entries matching an incoming `(accountId, date)` key are dropped before the new entries are appended, so re-recording a date does not create a duplicate point. This dedup only applies against *pre-existing* entries: if a single save batch itself contains two draft rows with the same `(accountId, date)`, both are appended (not merged) — the UI doesn't prevent entering duplicate rows within one dialog session.

**Edit Balance Entry**: clicking a row in the Activity table (not its trash icon) opens `RegisterBalanceDialog` pre-filled with that entry's data — single draft row, no mode toggle (Copy-Paste unavailable) and no "+ Add row" (still supports "+ Add activity"/per-activity remove within the row). Primary button reads "Save changes" and dispatches an update to the existing entry (not `ADD_BALANCE_ENTRIES`). The dialog also offers a "Delete" action guarded by the same `window.confirm('Delete this balance entry? This cannot be undone.')` as the table's trash icon, closing the dialog immediately on confirm. Cancel discards all edits and closes without saving.

## Budget

Accessed via the Nav's "Budget" tab (first pill). Persisted data: `AppState.budgetIncomeByYear: Record<string, number>` (a single plain yearly figure per calendar year) / `budgetExpenseDefinitions: ExpenseDefinition[]` (global, year-independent — no `amount` field) / `budgetExpenseAmountsByYear: Record<string, Record<string, number>>` (per-year amounts-only, keyed by expense id) / `budgetTransactions: BudgetTransaction[]`. `categories`/`categoryMappings` are not part of `AppState` — the page receives them as `categories`/`categoryMappings` props sourced from a separate global (cross-portfolio) category store (see "Cross-Portfolio Categories" below). The `categories` prop is the source of truth for the category list (not derived from expense/transaction strings); every category `<select>` on the page is populated from it, plus a trailing "+ Add new category…" option (`window.prompt`, creates a new `Category` — dispatched via a separate `categoryDispatch`, not the page's main `dispatch`; invisible to the user). All UI state (tab, filters, sort, form drafts, selected year(s), Spend records search/sort/pagination/cell-edit state) is component-local, not persisted.

A `.seg` tab toggle — **Expenses** / **Spend** / **Analytics** / **Category Mapping**, default **Spend** — switches the page's content below it. A page-level **Year** `<select>` sits in the same row as the toggle, right-aligned, but only on the **Spend** tab — the Expenses tab has its own independent year selector scoped to just its Category Breakdown panel (see below), and Analytics reads across all years at once.

### Expenses tab

Two stacked cards: **Category Breakdown** on top, the **Expenses** table below.

- **Category Breakdown panel**: its own **Year** `<select>` in the card header, fully independent of the Spend tab's Year and of the Expenses table's own filter/sort — changing one never affects the other. Renders a bar-per-category from `categoryBreakdown(budgetExpenseDefinitions, budgetExpenseAmountsByYear[breakdownYear], transactions for breakdownYear, categories)`. Each category's bar widths are relative to that category's larger Budget or Actual total (so one is always 100%). Empty state (no expense definitions with an amount that year): "Add expenses to see the breakdown."
- **Expenses table**: one row per global `ExpenseDefinition` — Name, Category, Frequency, then one right-aligned **Amount column per year**, spanning every year that appears anywhere in `budgetTransactions`/`budgetIncomeByYear`/`budgetExpenseAmountsByYear` plus always the real current calendar year, ascending, uncapped (so a brand-new install with zero data still shows at least the current year's column). A cell with no stored amount for that `(year, expenseId)` pair shows `—`.
  - **Sorting**: attached to the **Name/Category** column headers (click to sort by that column; click the already-active column to reverse direction — a chevron shows current direction). Default: Category ascending. A separate "Filter by category" select still exists alongside it.
  - **Per-cell edit**, no pencil/Done affordance: clicking the **Name** cell opens a text `<input>`; clicking an **Amount** cell opens a number `<input>` seeded from that column's year's raw stored value (or blank if unset) — Enter or blur on either commits, Escape reverts without dispatching. A Name commit dispatches `UPDATE_EXPENSE_DEFINITION` (patches the shared definition — visible under every year's row at once). An Amount commit dispatches `SET_EXPENSE_AMOUNT` (non-blank value) or `CLEAR_EXPENSE_AMOUNT` (cleared to blank) scoped to that one `(year, expenseId)` pair only — editing 2026's Amount cell never touches 2025's. Clicking **Frequency** or **Category** opens a `<select>` that commits immediately on `onChange` (no separate commit step) and dispatches `UPDATE_EXPENSE_DEFINITION` — Category's "+ Add new category…" option opens the same in-app new-category dialog used elsewhere on the page and applies the new id the same way.
  - **Delete**: a trash-icon button (`aria-label="Delete expense"`), always visible regardless of edit state, first checks whether ANY `BudgetTransaction`, in ANY year, still references this expense via `spendExpenseId` (`expenseDefinitionInUse(state, id)`); if referenced, deletion is blocked entirely with `window.alert('Cannot delete: this expense is used by a Spend record in at least one year.')` (no confirm dialog shown in this case — the alert replaces it) and `DELETE_EXPENSE_DEFINITION` is never dispatched; otherwise it's guarded by `window.confirm('Delete this expense? This cannot be undone.')`. A confirmed delete dispatches `DELETE_EXPENSE_DEFINITION` plus `DELETE_CATEGORY_MAPPINGS_FOR_EXPENSE` (hard-deletes every mapping pointing at the expense — the deliberate tombstone-convention exception). Deletion removes the definition and its stored amount from every year at once — there's no way to delete only one year's amount for an expense while keeping the definition (use the Amount cell's clear-to-blank for that instead).
  - **Add Expense**: opens a modal (Name/Category/Amount/Frequency); invalid submit (blank name, or amount `<= 0`) silently no-ops. A valid submit creates the `ExpenseDefinition` globally and seeds its `Amount` for the CURRENT calendar year ONLY — a newly added expense shows `—` in every other year's column until an amount is entered there too.
  - **Empty state**: "No expenses to show." when the filtered/sorted row set is empty.

### Spend tab

- **Summary cards** (4), scoped to the page-level selected Year: Income (click-to-edit via a pencil-icon button, pre-filled with the raw stored value; Enter commits), Budgeted (sum of that year's `budgetExpenseAmountsByYear` values), Actual spend ({year}), Variance (green when `Budgeted >= Actual`, else red). Categories with `excludeFromSpend` set have their transactions excluded from Actual spend and Variance (and from every other actual-spend-derived figure on the page — Category Breakdown, Analytics, see "Analytics" below); Budgeted is never affected by this flag. Income is now a single plain yearly figure per year (no separate monthly/yearly split) — editing it dispatches `SET_BUDGET_INCOME { year, amount }` (clamped `>= 0`).
- **Spend records** card: shares the page's selected Year — shows that year's `budgetTransactions` (the same underlying set, `periodFilteredTransactions`, as the "Actual spend" summary card). Columns: leftmost row-selection cell (see below), Date, Description, **Spend Category**, **Account**, Amount. The read-only Spend Category cell shows `"{expense name} ({category name})"` when the row is linked to a resolvable `ExpenseDefinition`, else `"Uncategorized ({category name})"`. Account column shows `row.accountName` or `—` when unset. A "Show excluded" checkbox next to the search box (component-local `showExcludedRecords` state, default unchecked) hides rows whose category has `excludeFromSpend` set when unchecked; checking it reveals them. Toggling it resets pagination to page 1. This only controls row visibility in this table — it does not change the Actual-spend/Variance figures elsewhere, which always exclude those transactions regardless of this toggle.
- **Spend records row selection**: each row's leftmost cell (`data-testid="row-select-{id}"`, `tabIndex=0`, `aria-selected`) is a spreadsheet-style selection cell over the currently-visible `pagedRecords` (i.e. selection is always scoped to what's on screen — reflecting search/`showExcludedRecords`/selected year/pagination already). Click selects only that row and sets it as the anchor; ctrl/cmd-click toggles membership without touching the anchor; shift-click selects the contiguous visual range from the anchor; shift+ArrowDown/ArrowUp (while a selection cell has focus) extends the range by one row and moves focus to the new end. Selection (and the bulk category picker below) resets to empty whenever the visible set/order can change out from under it — paging, sort column/direction, search text, or switching the selected year.
- **Bulk category edit action bar**: appears above the Spend records table only when >=1 row is selected, showing `"{n} selected"`, a `SpendCategoryPicker` (`aria-label="Bulk edit spend category"` — see "Spend Category selection is global" below for what it lists), and an "Apply" button (disabled until an expense is chosen, i.e. while `bulkCategoryId` is empty). Choosing an expense sets both `bulkExpenseId` (the picker's `value`) and `bulkCategoryId` (the expense's resolved category, used only for the Apply-disabled guard). Apply dispatches a single `UPDATE_BUDGET_TRANSACTIONS_BULK` (`categoryId` + `spendExpenseId`) for all selected rows, then clears the selection and both picker states. Unlike the per-cell single-row Category edit, bulk Apply does **not** call `categoryDispatch`/`UPSERT_CATEGORY_MAPPING` — bulk category changes are a deliberate one-off action, not a signal to remember a description→category mapping. (Bulk Apply also never triggers `REAPPLY_CATEGORY_MAPPINGS`, for the same reason — no mapping was created.)
  - **Search**: a text box (`aria-label="Search records"`, placeholder "Search records") does a case-insensitive substring match against Description, the resolved Category name, and Account name; applied before sort/pagination, and resets to page 1 on every keystroke. Empty search shows all rows for the selected year.
  - **Sorting**: all 5 columns (Date, Description, Category, Account, Amount) are sortable via column-header click — a chevron (`SortIcon`) marks the active column/direction; clicking the active column reverses direction, clicking a different column switches to it (default direction ascending, except Date which defaults to descending when newly selected). Default sort on load: Date descending.
  - **Pagination**: active only when the search-filtered row count exceeds 50; page size 50 (never more than 50 rows rendered at once); Prev/Next buttons + "Page X of Y" label, right-aligned below the table. Hidden entirely when the filtered set is 50 rows or fewer. The **Total** row always sums Amount across the full filtered set (search-filtered, not just the current page).
  - **Per-cell edit**: clicking any data cell (Date/Description/Spend Category/Account/Amount) turns just that cell into an editable input in place (a `SpendCategoryPicker`, `aria-label="Edit record spend category"`, for Spend Category; `<input type="date">` for Date, `<input type="number">` for Amount, plain text otherwise) — no whole-row pencil/Done affordance. Enter or blur commits a single-field `UPDATE_BUDGET_TRANSACTION` patch; Escape reverts without committing. The Spend Category picker's options always lead with a `— Uncategorized —` choice; selecting it clears the link (`patch: { spendExpenseId: undefined }`, `categoryId` left at its current resolved value) instead of assigning a different expense — use it to unlink a record from an expense without recategorizing it. Committing an actual Spend Category change (via the picker's `onChange`, which fires immediately rather than waiting for blur) patches both `spendExpenseId` and `categoryId` (the chosen expense's own category) and additionally upserts a `CategoryMapping` keyed by the row's exact `description` and the chosen `spendExpenseId` (dispatched via `categoryDispatch` to the global store, not the page's main `dispatch` — invisible plumbing detail); no other field's commit does this, and the "— Uncategorized —" clear does not (it isn't a category assignment). Immediately after that mapping upsert, `BudgetPage` also dispatches `REAPPLY_CATEGORY_MAPPINGS` (main `dispatch`) with the updated mapping list — so matching transactions in the currently open portfolio are instantly recategorized, live, with no button to press. Clearing the Account cell to blank unsets `accountName`.
  - **Mapping overlay**: a description-cell mapping icon appears only when that record's `spendExpenseId` resolves to a live `ExpenseDefinition` with at least one live (non-tombstoned) mapping. It opens a dialog scoped to that selected row id and its linked expense, listing only its live mappings; it never offers an add control. Click a substring to edit it: Enter saves only a trimmed, non-empty changed value and reapplies mappings; blur, empty input, and unchanged input retain inline edit mode; Escape cancels inline edit first, then closes the dialog. Each mapping's delete uses native confirmation, tombstones the mapping, and immediately reapplies mappings to current-portfolio Spend records; an empty post-delete dialog stays open. The X button closes the dialog; there is no backdrop-close behavior.
  - **Delete**: trash-icon button per row (`aria-label="Delete record"`, `window.confirm('Delete "{description}"? This cannot be undone.')`), unchanged.

### Spend Category selection is global — a real behavior change

`SpendCategoryPicker` (used for the per-cell Spend Category editor, the bulk-edit action bar, and the Add Record form, all on the Spend tab) now lists **every `ExpenseDefinition` in the app, regardless of year** — alpha-sorted by name, option label `"{name} ({category})"`, always with a leading `— Uncategorized —` option ahead of them; disabled with a single "No expenses defined" option only when there are zero `ExpenseDefinition`s at all, anywhere. This replaces the prior "same year as this record" filtering: previously, categorizing a January 2025 transaction only offered expenses that had been defined for 2025; now it offers every expense ever defined, no matter which year(s) it has an amount in. In practice this means a user can link ANY spend record to ANY expense definition even if that expense has no budgeted `Amount` for the record's own year (`budgetExpenseAmountsByYear[year][expenseId]` can be unset while the link still resolves fine for categorization purposes — Budgeted-vs-Actual comparisons simply show `—`/`$0` budgeted for that year).

Import auto-link and the mapping-reapply auto-link (see below) follow the same global rule: `resolveSpendExpenseIdForDescription(mappings, description)` returns the latest-`updatedAt` mapping hit's `spendExpenseId` directly, with no year filter at all. (`resolveSpendExpenseForCategory(definitions, categoryId)` — first array-order definition in the same category — now runs only inside the load-time and file-import legacy-`categoryId` migrations, not the live resolve/reapply path.)

### Import auto-categorization & mapping reapply

- **Import auto-categorization**: imported rows (Copy-Paste CSV or Upload CSV/OFX/QFX) never carry a category column. Each row's `spendExpenseId` is resolved automatically: a case-insensitive substring match of the row's `description` against the global store's `categoryMappings[].substring` (latest-`updatedAt` mapping wins on multiple matches) links the expense directly; `categoryId` is derived from the linked definition. No match — or a match whose expense no longer exists — falls back to "Other" with `spendExpenseId` unset. This resolution happens before dedup, but neither resolved field participates in the dedup key (see Dedup key above).
- **Manual Add Record live-prefill**: as the user types into the Description field, the same mapping match live-prefills both `recExpenseId` (the Spend Category picker's own selection — the hit `spendExpenseId`) and `recCategoryId` (the hit definition's category). No match leaves both untouched. Once the user manually picks a Spend Category themselves, further description edits stop overwriting either field (manual pick always wins over the live-match).
- **Re-apply mappings (set on confirmed hit, never clear)**: whenever a `CategoryMapping` is added/edited/deleted anywhere in the app, every existing `budgetTransactions` row is re-resolved (`REAPPLY_CATEGORY_MAPPINGS`, no manual trigger/button — see "Cross-Portfolio Categories" below for call sites). A mapping hit whose `spendExpenseId` resolves to a live `ExpenseDefinition` sets both `spendExpenseId` and `categoryId` (the definition's category); a miss — or a hit pointing at a deleted expense — leaves the row untouched. **Accepted tradeoff**: this can silently re-link a transaction the user had previously and deliberately set to "Uncategorized" via the per-cell picker's `— Uncategorized —` option, if that row's description matches a live mapping — there is no guard against this.

### Year-scoped expense amounts & income

Only the per-year *amounts* are year-scoped — `ExpenseDefinition`s themselves (name/category/frequency) are global and exist independent of any year. Amounts (`budgetExpenseAmountsByYear`) and income (`budgetIncomeByYear`) are each stored per calendar year. The Spend tab's page-level Year select reads/writes whichever year is selected; the Expenses tab's Category Breakdown panel reads/writes whichever year its own selector is on; the Expenses tab's multi-year table reads/writes every year in its column set simultaneously, one `(year, expenseId)` pair per cell. Switching the Spend tab's Year to a year with no existing amounts/income snapshot — either by selecting the Year dropdown directly, or by adding a spend record dated in a different year (which also switches the selected year) — **immediately and permanently persists a real snapshot for that year**, cloned from the nearest existing **non-empty** year (closest by absolute year distance; a tie favors the earlier year; the search keeps expanding outward past any empty candidate years until it finds one with data, or finds none anywhere). This is a real dispatched write (`ENSURE_BUDGET_YEAR_SNAPSHOT`), not just a display-time fallback: the newly-visited year owns its own saved copy from the moment it's selected, so editing the source year afterward does **not** retroactively change it. If no year has data anywhere yet, nothing is persisted — the year stays virtual (resolves to empty via the display-time fallback) so that if data is added to a *different* year afterward, switching back still picks it up on the next `ENSURE_BUDGET_YEAR_SNAPSHOT` rather than being permanently stuck on an empty snapshot taken before any data existed. On app load, if the current calendar year has no snapshot yet but an earlier year does, the most recent prior **non-empty** year's expense amounts and income are **auto-copied forward** ("rollover") as the new current year's starting point. This applies identically and independently to expense amounts and to income. A year is never left with a stored-but-empty budget: an empty snapshot is never persisted as a final value, and clearing a year's last expense amount (or zeroing income for a year) removes that year's stored entry entirely, reverting it to the same virtual/unvisited state it was in before any snapshot existed — so it can still pick up real data cloned from elsewhere on a later visit instead of staying stuck empty. The Expenses tab's per-cell Amount edits (`SET_EXPENSE_AMOUNT`/`CLEAR_EXPENSE_AMOUNT`) write directly into whichever year's column was clicked, without any eager-snapshot step of their own — each `(year, expenseId)` pair is independent, so there's nothing to seed.

### Analytics

Third option on the Budget page's tab toggle (Expenses/Spend/**Analytics**/Category Mapping). Selecting it hides the Year select, the tab's own content (Expenses tab's Category Breakdown + Expense table, Spend tab's summary cards + Spend records, or Category Mapping), and renders `BudgetAnalytics` (read-only, no dispatch) in its place. The tab toggle row itself (left-aligned tabs) stays visible in Analytics mode; only the Year select (Spend-tab-only) drops out of that row. Switching back restores the selected tab's content unchanged.

- **Scope**: computed from ALL years present in `budgetTransactions` (not just the currently-selected Year), most-recent-year-first, soft-capped at 8 years.
- **Empty state**: if there are no budget transactions at all, every section shows "No records for this period." Otherwise, each section renders independently; four sections additionally require 2+ years of data and show their own "No records for this period." message when only 0 or 1 year exists: **Spend trend**, **Savings rate** (shrinking-trend stat), **Category trends year over year**, and **Biggest movers**. The other sections — **Over-budget count**, **Spike month**, **Concentration risk**, **Category share of spend**, **Monthly seasonality**, **Budget accuracy by year** — render normally with just 1 year of data.
- **Excluded categories**: categories with `excludeFromSpend` set are left out of every Analytics figure, identically to the rest of the Budget page (audited across all 7 sections).

Seven sections, in fixed order:
1. **Areas of concern** — up to 5 stat cards: Over budget (count of categories over budget this year + their names, or "None"), Spend trend (% change, colored by direction; 2+ years needed), Spike month (the standout high-spend month, with its total and a z-score-style detail; needs enough monthly history), Savings rate (current rate and whether it's trending up or down vs. the earliest year; 2+ years needed), Concentration risk (the single category taking the largest share of spend, highlighted red if it crosses the high-risk threshold).
2. **Savings rate by year** — a bar chart, one bar per year, labeled with each year's savings-rate percentage.
3. **Category share of spend over time** — a stacked horizontal bar per year (each segment = one category's share of that year's spend, colored, with a hover tooltip showing name + percentage) plus a color-keyed legend below.
4. **Monthly seasonality** — a bar chart of average spend per calendar month (Jan–Dec) across all years, with the peak month's bar highlighted in a different color.
5. **Budget accuracy by year** — one row per year showing a budget-vs-actual overlay bar plus an "Under by $X" / "Over by $X" variance label, colored by direction.
6. **Category trends year over year** — a table (Category, one column per year, YoY % change, "Over budget" pill), sorted by % change; needs 2+ years.
7. **Biggest movers** — two lists side by side, "Biggest increases" and "Biggest decreases," each showing up to 3 categories with their average-monthly-spend change (e.g. "+$120/mo"); needs 2+ years.

### Cross-Portfolio Categories

Categories and category mappings are shared across ALL portfolios opened in this browser, not scoped to a single portfolio — renaming a category (or editing/adding a mapping substring) in one portfolio's Budget > Category Mapping tab changes what every other portfolio sees too, immediately.

**Seeding on upgrade**: the FIRST portfolio the user unlocks after upgrading to this feature has its existing categories and mappings copied verbatim (same ids, no dedup) into the new shared store; this happens once, automatically, invisibly — no prompt, no confirmation. Every OTHER portfolio's own pre-existing categories/mappings are left behind and never merged in: that portfolio's transactions/expenses will show as uncategorized ("Other"/blank) until the user manually recreates matching categories and re-categorizes them. Which portfolio ends up seeding the store is simply whichever one happens to be unlocked first after upgrading — not something the user can choose or control.

Mappings are keyed by `spendExpenseId` (expense, not category): deleting an `ExpenseDefinition` hard-deletes every mapping pointing at it (see Expenses tab above), so no dangling mapping survives its expense.

**Category deletion** exists only in Budget's Category Mapping tab. Each category header shows its all-year effective Spend-record count for the currently open portfolio and a visible delete affordance. `Other` cannot be deleted: clicking its affordance shows a native alert. For every other category, deletion is blocked with a native alert when it has any `ExpenseDefinition`, or when any current-portfolio `BudgetTransaction` resolves to it through `effectiveCategoryId` (including a linked expense's category, across all years). No other portfolio's transactions participate in this count or guard. An unblocked delete uses native confirmation; confirming dispatches `DELETE_CATEGORY`, tombstoning the category (`deletedAt`/`updatedAt`) rather than physically removing it. Category Mapping is the only category-delete surface; Settings has none. Its tab CRUD remains separate from the Spend record's row-scoped mapping overlay; both mapping-delete surfaces use native confirmation and immediately reapply to the current portfolio, while the overlay cannot add mappings.

It fires once **both** are true: at least 2 hours have passed since the last unlock (or password change), **and** at least 5 minutes have passed with no user activity (mouse clicks, key presses, touches, and scrolling all count as activity; moving the mouse without clicking does not). Activity only *defers* the lock by resetting the 5-minute idle window — it never grants a fresh 2-hour window, so e.g. continuous clicking for 3 hours straight still locks at the first 5-minute gap after the 2-hour mark. On lock, any pending unsaved change is flushed to storage first, then the app silently returns to the same password-entry screen shown on a fresh page load — there is no "you were locked out" message and still no manual lock button. Any in-progress, unsaved component-local dialog or form (e.g. a partially-filled Add Transaction dialog) is discarded, not saved. Each open browser tab tracks its own lock timer independently — locking in one tab does not lock another open tab.

## Settings page

A dedicated page accessed via the gear button in the Nav. Three mutually-exclusive sections (Backup / Encryption / Price Sync), switched via a `.seg` tab control at the top of the page's content — only one section's card is visible at a time. The tab-seg is followed by a `.hr` divider.

- **Tab-seg** (top of content): "Backup" / "Encryption" / "Quotes API Key" tabs, active per `settingsSection`, each dispatches `setSettingsSection` on click. Resets to "Backup" every time Settings is opened via the gear button.
- **Backup** (`settingsSection === 'backup'`): stacks TWO cards vertically — the Google Drive Sync card followed by the Download card (the second card on the Backup tab, described further below). See also "Cross-Portfolio Categories" (Budget section) for the category-mapping controls on the Download card. The Google Drive Sync card stacks the `@open-webapp/drive-connect` package widget (`<GoogleDriveWidget>`) ABOVE the shared `DriveRestorePanel` (also used on the password gate's restore tab). The **widget** renders all four connect states itself — disconnected (a Connect button), connecting, connected (shows the Google account), needs-reauth — with errors shown inline via `role="alert"` and no `window.alert` dialogs for connect/disconnect; its buttons use the package's own styling, not `.btn.btn-primary.blueprint`. Connecting no longer greys out the Restore button, and connect/disconnect no longer flip the app's `syncing` flag (`syncing` now means only "a sync/restore content op is running"). The **panel** shows a **Restore from Drive** button when connected. When connected AND a backup file exists (fetched in the widget's `onConnected` callback via `getBackupFileId()`, or set by the last successful sync), a **View backup in Google Drive** link appears below — opens `https://drive.google.com/file/d/{fileId}/view` in a new tab. No link while not connected or before any sync; a failed `getBackupFileId()` lookup just hides the link and does not forget the connection. **Auth-token behavior** (owned by the `@open-webapp/drive-connect` package): a still-valid cached token (not expired, scopes complete) is reused without prompting; only an expired or missing token triggers the interactive Google auth window, and never more than one window at a time (single in-flight guard, shared by the widget's Connect button and the content ops' `ensureFresh()`) even if sync/restore/connect is triggered rapidly. `getBackupFileId()` is a passive probe and never opens Google auth. The Nav **Sync** button is always rendered and `disabled` while Drive is not connected or a sync is in flight (previously hidden while disconnected). **Restore flow**: clicking "Restore from Drive" shows a **Pick a file** (`.btn.btn-secondary`) button which opens the Google Picker dialog — scoped to the app's own `OpenWebApp/Portfolio` folder by default, but the user can navigate anywhere in their Drive (this is how a backup shared by a different account, or one living outside that folder tree, gets restored — there is no separate paste-a-URL flow; Picker is the only restore entry point, with no by-name lookup of a default backup first). Selecting a file triggers a confirm ("Restore will replace all data with the backed-up version. Continue?") then attempts to restore using the current session key. Closing Picker without selecting a file is a no-op — "Restore from Drive" can be clicked again to reopen it. **Cross-password prompt** (reached if current key does not match backup): inline password field, submit/cancel buttons, "Incorrect encryption password" on wrong password (prompt stays open, retryable) — a wrong password also reveals a fallback **Pick a file** button inline, letting the user pick a different backup file without leaving the prompt; submitting the correct password re-derives the session key and adopts the backup's data, updating the session password.
- **Download** (the second card on the Backup tab, card title "Download"): **Download Backup** button (`.btn.btn-primary`) — silent, no password prompt or confirm, downloads an encrypted envelope (`{version, salt, iv, ciphertext}`, encrypted under the current session key/salt) as `ledger-backup-YYYY-MM-DD.json` (today's local date). Download-only — restoring from a backup file is no longer available here; that flow moved to the password gate's Restore tab, "Backup file" card (see Password gate above), reachable only pre-unlock since it now unlocks directly into the restored data.
  - **Category mapping download/import** (below a divider, rendered only once the global category store has hydrated): a **Download Category Mapping** button downloads `{categories, categoryMappings}` as plain unencrypted JSON (`category-mappings-YYYY-MM-DD.json`, today's local date) — no password prompt, no encryption (unlike the backup file above). An **Import Category Mapping** button opens a file picker (`.json`); the selected file is parsed (`parseCategoryMappingImportFile(text, budgetExpenseDefinitions)` — legacy-`categoryId` rows migrated at parse time, unresolvable ones dropped) and merged into the global category store — last-write-wins per record by id (same merge algorithm used for Drive sync), not a wholesale replace, so importing an old export never deletes categories/mappings added since. A malformed or non-JSON/wrong-shape file shows an inline error message below the buttons and does not change anything.
  - **Category Drive sync is a separate channel**: independent of the per-portfolio encrypted backup file above, an unencrypted `category-mappings.json` file at the Drive root syncs the global category store — auto-pushed on every local category/mapping edit while a Google Drive connection is active, and checked for remote changes every 60 seconds via a lightweight metadata-only poll (a full pull only happens if the remote file's modified-time is newer than last seen). This channel works even if no portfolio has ever been connected to Drive — it's independent of any specific portfolio's connection/backup state.
- **Change Password** (`settingsSection === 'encryption'`): "Current Password", "New Password", "Confirm New Password" fields + a "Change Password" button. Verifies the current password by attempting a real decrypt of the stored data; wrong current password shows "Current password is incorrect" and stops. New password follows the same 6-char-minimum/must-match rules as the set-password screen. On success: generates a **fresh salt** (rotated on every change, never reused), re-derives a key, re-encrypts and saves the local IndexedDB copy under the new key+salt, then — only if Google Drive is currently connected — re-syncs the Drive backup under the new key too. If that Drive re-sync fails, a non-blocking inline warning is shown ("Password changed locally, but Drive re-sync failed... Sync manually...") but **the local password change is not rolled back**. On success the app adopts the new key as the session-wide key going forward, and also resets the 2-hour auto-lock clock, same as a fresh unlock.
- **Price Sync** (`settingsSection === 'priceSync'`): Polygon.io API Key field (`type="password"`, commits to state on blur, not on every keystroke). **Fetch prices now** button (`.btn.btn-primary`, disabled while a fetch is in flight or no API key set) + adjacent optional `<input type="date">` date-override (disabled while fetching) for fetching a specific trading date instead of latest. **Last run** summary below: `Never run` if no run yet; otherwise timestamp + either the error in red (`#8a3c2e`) or `{marketTickerCount} tickers fetched from Polygon` (total tickers in that day's market-wide response, not just held symbols) plus `{updatedCount} updated` plus `, not found: {symbols}` when any. **Price table** (below the summary): row set = union of every ticker cached locally (`marketDataDb.getAllBars()`, market-wide — thousands of tickers, loaded async and refreshed after each run), `state.priceSync.heldPrices` keys, and the latest run's `notFound` symbols, deduped, sorted ascending by ticker (no sortable headers). Columns: Ticker, Price, Status, Held, Trading Date, Fetched At. Status is "Not found" (red, `#8a3c2e`) if the symbol is in the latest run's `notFound` list — wins even over a stale held-price entry for that symbol — "OK" if it's a held symbol found in the response, otherwise "Market" for a non-held ticker present only in the local bar cache. Held is "Yes" for a symbol that is (or was) a held Equity/ETF position, "No" for a market-only ticker. Price/Trading Date come from the symbol's held-price entry when one exists, else from its cached bar; Fetched At only ever comes from the held-price entry (the bar cache doesn't track a fetch timestamp) and shows "—" for market-only tickers. All show "—" when no data exists. A live, case-insensitive search box above the table filters rows by ticker substring, status text, or "Yes"/"No" — no submit button, no debounce. Table sits in a scrollable container (`overflowY: auto`, `maxHeight: calc(100vh - 480px)`). Empty state: if there are no held prices, no recorded not-found symbols, and no cached bars, the search box and table are replaced by "No prices fetched yet."
- **Categories** (`settingsSection === 'categories'`): two-level nesting — every `Category` rendered with its `ExpenseDefinition`s (`state.budgetExpenseDefinitions` filtered by `categoryId`), each expense with its `CategoryMapping` substrings (`mappingsForExpense(categoryMappings, expense.id)`) listed indented beneath it; this is display-only and never deletes anything from the store. Each expense's group header (and its "+ add substring" input/button aria-labels) reads `<expense name> (<category name>)`, not just the bare expense name — `ExpenseDefinition.name` isn't guaranteed unique across categories, so the category qualifier disambiguates, mirroring the `<expense name> (<category name>)` format `SpendCategoryPicker`/`formatSpendCategoryLabel` use elsewhere. Each category row's name is inline-rename-editable (click-to-edit text, commits on Enter/blur, dispatched via `categoryDispatch` to the global store rather than the page's main `dispatch` — invisible plumbing detail) — renaming cascades everywhere the category is used, in every portfolio (Expenses, Spend records, Category Breakdown), for free, since those only store the FK `categoryId`. Each row also has an "Exclude from spend tracking" checkbox (`category.excludeFromSpend`, default unchecked) dispatching `SET_CATEGORY_EXCLUDE_FROM_SPEND` via `categoryDispatch` — checking it hides the category's row entirely from the Category Breakdown panel and excludes its transactions from the Actual-spend/Variance summary cards and the Expenses table's per-row Actual/Variance columns, everywhere the category is referenced, in every portfolio; the Budgeted card/column is never affected, and the category remains selectable in every category `<select>` in the app (Expenses form, Add Record, import mapping, per-cell edit — none of them filter it out). Beneath each expense, its `CategoryMapping` substrings are listed indented, each row showing (left to right) a pencil-icon edit button, the substring text, then a trash-icon delete button. Editing is inline the same way as categories (also via `categoryDispatch`). Every expense (even one with zero mappings) shows a "+ add substring" affordance (`ADD_CATEGORY_MAPPING { spendExpenseId, substring }`) to create a new mapping under it — editing or adding a substring here immediately re-resolves every existing `budgetTransactions` row against the updated mappings (dispatched through the page's main `dispatch`, since it mutates this portfolio's own `budgetTransactions`, not the global store), with no button to press and no confirm dialog — the reapply sets on a confirmed live-definition hit and never clears (only reassigns links via existing mapping rules, never deletes/adds rows). **Deleting a mapping**: the trash button prompts `window.confirm('Delete this mapping? This cannot be undone.')`; on confirm, dispatches `DELETE_CATEGORY_MAPPING` (`categoryDispatch`, tombstones the mapping in the global store — `deletedAt` set, not physically removed) and reapplies mappings to this portfolio's `budgetTransactions` (main `dispatch`) so rows that matched the deleted mapping re-resolve against the remaining ones. Declining the confirm is a no-op. **No delete action exists for a `Category` itself** — unused categories simply stop rendering; only individual `CategoryMapping` substrings are deletable. **There is no manual "Re-apply mappings to existing records" button anywhere in the app** (removed) — every action that creates, edits, or deletes a mapping, on this tab or on the Budget page, applies it to existing records automatically and immediately.

Navigation back to the Accounts page occurs via the Nav's Positions tab (no separate Back button or navigation affordance in Settings page content).

## PWA install & offline behavior

- **Install prompt**: relies entirely on the browser's native install affordance — address bar icon on desktop Chrome/Edge, "Add to Home Screen" on Android/mobile browsers. No custom in-app install button or banner.
- **Offline behavior**: app shell (HTML/JS/CSS, icons, manifest) loads from cache when offline. IndexedDB-backed app data (accounts/positions/transactions) already works offline regardless of PWA status. Drive Connect sign-in and Drive sync (Sync button) require network — the gsi/client script and Drive API calls are intentionally NOT cached/proxied by the service worker, so they fail or hang when offline. This is expected, not a bug.
- **Update behavior**: silent auto-update (`registerType: 'autoUpdate'`). No "new version available" prompt. The next reload or navigation after a new deploy picks up the latest service worker and assets automatically.

## Formatting conventions

- USD: `fmtUSD(n)` → `"$1,234.56"` / `"-$1,234.56"` (no leading `+` on positives; callers that want a `+` prepend it themselves for G/L-style fields).
- Percent: `fmtPct(n)` → always signed, `"+1.20%"` / `"-1.20%"` / `"+0.00%"`.
- Shares: `toLocaleString('en-US', {minimumFractionDigits:2, maximumFractionDigits:2})`.
- Dates in Transactions table: `Date.toLocaleDateString('en-US', {month:'short', day:'numeric', year:'numeric'})` (e.g. "Jan 5, 2026"). Dates in Closed Positions "Closed" column are shown as raw ISO strings.
