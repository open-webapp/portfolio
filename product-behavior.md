# Product Behavior — Ledger (Portfolio Dashboard)

See also: [design.md](design.md), [schema-spec.md](schema-spec.md)

Local-first, single-user portfolio tracker. No live price feed — all values come from user-imported CSVs. No Watchlist/Alerts feature (out of scope; must never reappear — grep `watchlist` case-insensitive in `src/` must return nothing).

## Layout

Four views: **Budget**, **Accounts** (rail label "Positions"), **Register**, and **Settings**. Every unlocked view uses the app shell: fixed `RailNav` + `TopBar`, then its content. Accounts: top `.seg`-style tab row (Taxable / Non-Taxable / Tax-Deferred / Closed Positions / Quotes) then, for tabs 1-4, a 2-column layout — left nav (360px) scoped to that tab's accounts + a flexible right panel (allocation chart, asset-class filter + "Import" button row, and the aggregate/closed-positions table); tab 5 (Quotes) is a single full-width right panel, no left nav. Register: 2-column scope picker (left, 360px) and stats/chart/activity table (right). Budget: period-specific content. Settings: centered settings card (max-width 560px).

**Default landing page**: Accounts. A fresh install opens there; thereafter the last-viewed view is persisted, so an app locked on Settings reopens on Settings. A backup written by an older build that recorded a now-retired view opens on Accounts rather than failing to render.

## Shell Navigation

`RailNav` renders on every unlocked view as a fixed left icon rail. It contains a Ledger `L` mark, three main icon buttons, a flexible spacer, and Settings at the bottom. At viewport widths <=480px, it becomes a fixed 64px bottom bar; the mark and spacer are hidden and the main controls distribute horizontally.

- **Budget** — the income/expense budget tracker. Active when `state.view === 'budget'`.
- **Positions** — the Accounts page. Active when `state.view === 'accounts'`.
- **Register** — the balance-history tracker. Active when `state.view === 'register'`.

Quotes has no rail icon — it is the 5th tab inside the Positions page (see "Accounts page" below); its read-only held-symbol price table behavior is unchanged, just relocated.

Each main control is an icon-only button with an accessible label and tooltip. Clicking dispatches `SET_VIEW`; the selected control is accent-filled and exposes `aria-pressed="true"`. Settings is a separate gear button outside the main item stack.

`TopBar` contains an accent-colored portfolio-switch button, the Budget-only period `.seg` control, and a right-aligned accent **Sync Now** icon button (`title`/accessible label `Sync now`). Sync is disabled whenever Drive is disconnected or syncing. The Settings gear opens Settings and resets `settingsSection` to "Backup".

## Allocation chart

Reusable `.card.blueprint.elev-sm` component taking `positions: Position[]` and `title: string` props. Renders a 2-column grid grouped by *effective* asset class (`assetClassManualOverride || assetClass`), computed via `allocationBars(positions)`. Each cell shows: class label + USD value inline (12px font), percentage right-aligned (muted), and a compact horizontal bar (height 6px, accent color fill) sized to percentage of total portfolio value.

- **Accounts page usage** — the only usage: called with selection-scoped positions (all accounts, a single account, or a single account's closed positions) and a title of `"Allocation — All Accounts"`, `"Allocation — {account.name}"`, or `"Allocation — {account.name} (Closed)"` per selection state.
- Empty positions list → empty grid with no crash.

## Transactions table

(Not rendered in any current view; kept for data-model and future-surface reasons.)

- Type filter tags (`All` + every distinct `Transaction.type` currently in state, alphabetical) + free-text search (symbol or date substring, case-insensitive).
- Always sorted by date descending — no user-controlled sort.
- Columns: Date (formatted `MMM D, YYYY`), Symbol, Type (colored tag: Buy=accent, Sell=outline, Dividend=neutral, anything else=neutral), Shares, Cost Basis, Amount Invested, Position Link.
- **Position Link**: shows an "UNMATCHED" outline tag (with a tooltip explaining "likely fully sold or removed") when the transaction's symbol has no corresponding open `Position`; otherwise shows plain "Linked" text. This is purely derived per render — no stored flag.

## Accounts page

Accessed via the "Positions" rail control. Top-level tab row (`.seg`-style, 5 tabs, in order): **Taxable**, **Non-Taxable**, **Tax-Deferred**, **Closed Positions**, **Quotes**. Active tab is component-local `useState<PositionsTab>` in `App.tsx` — not persisted, not part of the reducer/`AppState`; reloading or reopening the app always lands back on the first tab (Taxable).

- **Switching tabs clears selection**: changing tabs always resets `state.selectedAccountId` to null (equivalent to clearing any highlighted account) — a selection never carries over from one tab to another.
- **No "All Accounts" pill**: there is no all-accounts affordance anywhere on this page. Each of tabs 1-3 is inherently scoped to one category; there is no way to view an unscoped cross-category aggregate.
- **No collapse/expand**: category blocks in the left nav always show their accounts — there are no click-to-expand/collapse chevrons or headers-only collapsed state anywhere on this page.

**Tabs 1-3 — Taxable / Non-Taxable / Tax-Deferred**: 2-column layout, left nav (360px fixed width) + flexible right panel.
- **Left nav**: exactly that tab's category — one un-collapsible block listing every account in that category, each row clickable (cursor pointer), styled with:
  - Institution and account name on line 1 (or name only if institution is empty), using institution—name format.
  - Tags on line 2: total value (formatted USD), account number, updated date (ISO format).
  - A category-sum total for the block (all accounts in that category, not scoped to a filter or selection).
  - Click to select: dispatches `state.selectedAccountId`, or toggles off (clears selection) if the same account is already selected — unchanged select/toggle semantics from before.
- **Right panel**, scoped to the active tab's category (all its accounts, or a single selected account within it — never accounts from a different category, even when nothing is selected — this is a fix over the prior nav, which could leak all accounts into the right panel when nothing was selected):
  - **Allocation chart** — top: `AllocationChart` with positions from the current selection (whole category, or a single account) and title `"Allocation — All Accounts"` or `"Allocation — {account.name}"`.
  - **Filter row** — asset-class `.seg` radio control (computed from the tab's positions, sorted alphabetically) + "Import" button. Free-text search field for symbol/name filtering.
  - **Aggregate Positions table** — sorted by column selection (`state.sortKey`/`state.sortDir`, toggled via `TOGGLE_SORT`). **Columns**: Symbol, Asset Class, Shares, Avg Cost, Current Price, Amount Invested, Market Value, G/L, G/L %, **% of Selection** (percentage of selection total, not whole portfolio), Row-count badge. **% of Selection** reflects only positions in the current selection (account or whole tab). Rows are **aggregate groups** — one row per unique grouping key (`trackingSymbol || symbol`, i.e. a position's tracking symbol takes precedence over its own symbol when set) + effective asset class; retirement status does not partition groups, so matching positions merge across accounts within the tab. Every group, including size-1, renders as one row. Groups aggregate shares, cost basis, and market value; price is derived as summed value / summed shares.
    - **Sorting**: clicking a sortable header (Symbol/Asset Class/Shares/Avg Cost/Current Price) toggles asc/desc via `TOGGLE_SORT`; clicking the active column flips direction, a different column resets to `asc`. An `↑`/`↓` arrow marks the active column. Sorting orders by aggregate/derived group values, computed client-side after grouping. Amount Invested/Market Value/G/L/G/L % are display-only, not sortable.
    - **Row click → overlay**: clicking any row (cursor pointer) opens `PositionGroupOverlay`, a dialog (`.dialog-backdrop`/`.dialog`, closable via Escape/backdrop-click/X button). Title: `` `Symbol — Name — Asset Class` ``, where the "Symbol" slot shows the group's Tracking Symbol instead of its own Symbol when one is set on the group. Lists the underlying positions sorted by account.institution, then account.name, falling back to account.accountNumber. **Overlay columns** (11): Account, Symbol, Tracking Symbol, Name, Shares, Avg Cost, Current Price, Market Value, % of Portfolio, Override, Delete. **Account display (two-line)**: line 1 institution—name (or name alone if no institution); line 2 muted tax-category and retirement labels (e.g. "Taxable • Retirement"). **Editable cells**: Account (dropdown listing all accounts; selecting dispatches `UPDATE_POSITION` with `patch: { accountId }`); Symbol and Name (`<input type="text">`, click-to-edit, empty/whitespace-only reverts silently, trimmed non-empty commits); Tracking Symbol (same input style, but empty is a valid commit — submitting blank clears an existing tracking symbol via `patch: { trackingSymbol: undefined }`, reverting the position to grouping/display by its own Symbol; a no-op submit that doesn't change the effective value dispatches nothing); Shares/AvgCost/Price (`<input type="number">`, click-to-edit; valid non-negative number commits, invalid/empty reverts silently, no error UI). All fields: Enter or blur commits, Escape reverts with no dispatch. % of Portfolio is display-only and uses the whole-portfolio total (every position), not the current selection. **Side effect**: editing Symbol, Tracking Symbol, or Account changes the position's group key, so its row disappears from the open overlay on the next render (the overlay stays open — a natural re-render consequence). **Delete column**: blank header, trash-icon button per row; prompts `window.confirm('Delete this position? It will be moved to Closed Positions.')`; on confirm dispatches `CLOSE_POSITION`, converting the position into a `ClosedPosition` (`realizedGL: null`, `realizedGLBasis: 'unknown'`, `closedDate` = today) rather than hard-deleting it. Override column contains the `AssetClassOverrideSelect` control.
  - **Empty state**: "No positions to show." when selection has no positions.

**Tab 4 — Closed Positions**: 2-column layout, left nav (360px) + flexible right panel.
- **Left nav**: accounts-with-closed-positions only — one un-collapsible list of every account in state with ≥1 closed position, each row clickable, showing institution—name (line 1), then realized G/L sum (formatted USD, or `—` if all underlying closed positions have `realizedGLBasis === 'unknown'`), account number, updated date (line 2). A block realized-G/L total sums across all listed accounts, excluding unknown-basis entries; shows `—` only when every entry in scope is unknown-basis.
  - Accounts with no closed positions never appear on this tab. If no account in state has any closed position, the left nav is empty.
  - Click to select: same select/toggle semantics as tabs 1-3, scoped to this tab's account list.
- **Right panel**: always shows the **Closed Positions table** — for the selected account, or (nothing selected) the union across every account with closed positions. This is a fix over the prior nav, which only showed the table under certain selection states.
  - **Allocation chart** — top, positions = current selection's closed positions, title `"Allocation — All Accounts (Closed)"` or `"Allocation — {account.name} (Closed)"`.
  - **Filter row** — asset-class filter + search, scoped to the closed positions in view.
  - **Closed Positions table columns**: Security (symbol + name), Closed (date, ISO format), Realized G/L (signed formatted USD, or `"unknown"` if `realizedGLBasis === 'unknown'`), Delete (trash-icon button per row, triggering confirm `"Delete this closed position? This permanently discards its realized G/L history."`, removing on confirm), Undo (restores the position from its close-time snapshot — shares, avgCost, price, assetClass, lastImportedAt — no dialog, no manual re-entry; the restored position always gets a fresh internal id, not user-visible). Asset-class filter and symbol search apply. No `PositionGroupOverlay` interaction. Realized G/L is never a fabricated number — `"unknown"` is shown when the basis is unknown.
  - **Empty state**: "No positions to show." when selection has no closed positions.

**Tab 5 — Quotes**: no left nav — the right panel is the Quotes table, full width, read-only held-symbol price table. Keyboard/URL/edge-case behavior is the same as the rest of the Positions page's tabs.

**Account CRUD**: remains in CSV import flow only (new-account form at import time). **No longer shown anywhere on this page**: "Subtotal row", "Cash/Investment/Total" column split, 3-section (Taxable/Non-Taxable/Tax-Deferred) stacked table layout, dividers between sections, category collapse/expand chevrons, "All Accounts" pill.

## Register

Accessed via the "Register" rail control. A manually-recorded balance-history tracker, independent of imported Positions/Transactions — data comes only from user-entered `BalanceEntry` rows via the "Record Balances" dialog.

**Layout**: 2-column, left scope picker (360px) + right balance-history panel.

**Left panel — Scope picker**:
- **"All Accounts" card** (always first, always visible): shows the sum of every account's latest recorded balance (`registerAllAccountsTotal`). Click selects the "All Accounts" scope (`SET_REG_ACCOUNT` with `accountId: null`); highlighted when no account is selected.
- **Category cards** (one per tax category — Taxable/Non-Taxable/Tax-Deferred, via `registerCategoryCards`): header (click toggles expand via `TOGGLE_REG_CATEGORY_EXPANDED`) shows category label, account-count badge, and category total (sum of member accounts' latest balances). Expanded: one row per account showing institution—name, that account's latest balance, an "N entries" tag, and an "As of {date}" tag; empty categories show "No accounts in this category." Clicking an account row selects it (`SET_REG_ACCOUNT`) as the scope; selected row is highlighted.
- Scope selection is a single global `state.regAccountId` (not a toggle — clicking an already-selected row does not deselect; only clicking "All Accounts" or a different account changes scope). Category expand/collapse state is per-category (`state.regExpanded`), independent of scope selection.

**Right panel — Balance history** (scoped to the selected account, or every account when scope is "All Accounts"):
- **Title**: `"{institution} — {name}"` for a single account, or `"All Accounts — Balance History"`.
- **Stats strip** (4 cells, derived from the scoped ledger via `accountLedger`): Current balance (latest recorded balance, summed across scope accounts); Net change recorded (sum of period-over-period balance deltas, `null`/opening entries excluded); From activity (sum of each entry's `activities` amounts, each signed by `ACTIVITY_SIGN[type]`); Unexplained (Net change minus From activity, i.e. the portion of each balance change not attributed to a recorded activity type). Net change / From activity / Unexplained are signed (`+`/`-`) and colored gain/loss green/red by sign.
- **Balance-over-time chart**: SVG line+area chart plotting the scoped total balance at each recorded date (carrying forward each account's last-known balance between its own entries), with Y-axis USD gridline labels and up to 6 X-axis date-tick labels. Each point has a hover tooltip (`{date} — {balance}`). Single-point series render a centered flat line.
- **Activity filter**: `.seg` radio, `All` / `With Activity` (dispatches `SET_REG_ACTIVITY_FILTER`) — `With Activity` hides entries with zero `activities` (`activities.length === 0`).
- **"Record Balances" button**: opens the Record Balances dialog (below); dialog-open state is component-local.
- **Activity table** (newest-first, then by accountId; scoped + filtered via `scopeLedger`): Date, Account (name + institution), Balance, Change (`+`/`-` USD, or "Opening" for an account's first-ever entry), Attributed activity — stacks one tag per activity (type + signed amount + optional note), row grows to fit (no truncation); shows "Not attributed" only when `activities.length === 0`, Unexplained (signed USD, or `—` for an opening entry), Delete. Clicking a row (anywhere but the trash icon) opens the Edit Balance Entry dialog for that entry — see below.
- **Delete**: trash-icon button per row; `window.confirm('Delete this balance entry? This cannot be undone.')`, then dispatches `DELETE_BALANCE_ENTRY`.
- **Empty state**: "No balance entries recorded for this scope yet." when the filtered/scoped row list is empty.

**Record Balances dialog** (`RegisterBalanceDialog`): mode `.seg` — **Enter manually** (default) or **Copy-Paste**.
- **Manual mode**: an editable draft-row table (Date, Account select, Balance, one or more Activity entries, remove-row button), seeded with one blank row (account pre-filled from the current Register scope if one is selected, date pre-filled to today). "+ Add row" appends another blank row. Each activity, rendered as its own row beneath the balance row, has its own "+ Add activity" button to append another activity and a per-activity remove button — available in both add-mode and edit-mode rows.
- **Copy-Paste mode**: two paste zones (Headers, Values), parsed via the same `tableToCsv()` clipboard parser CSV import uses, then mapped to fields by header-hint matching (`BALANCE_FIELD_HINTS`: date/account/balance/activityType/activityAmount/note) — account values are fuzzy-matched to an existing `Account` by id/name/number/institution—name (`matchAccountId`), activity values matched by exact or prefix match against the 7 activity types (`matchActivityType`, defaulting to `None`), dates normalized to `YYYY-MM-DD` (`normalizeDateInput`). Pasting rebuilds the draft-row table from the parsed result; an inline error shows if either zone is empty or parsing yields no headers/rows.
- **Row validity**: a row is valid (`isDraftRowValid`) once it has a date, an account, and a numeric balance — activity fields are optional. Invalid required cells get a red border. Save is disabled at 0 valid rows; its label reads "Save N entries"/"Save 1 entry".
- **Commit**: Save normalizes each activity item on a row (`amount` = `Math.abs(parseFloat(amount)) || 0`; unmatched activity type falls back to `'None'`), converts valid draft rows to `BalanceEntry[]` (activity amounts non-negative — sign is derived at read time via `ACTIVITY_SIGN`) and dispatches `ADD_BALANCE_ENTRIES`, then closes and discards local draft state. Cancel/✕/backdrop-click closes without saving.
- **Replace semantics**: recording a new entry for an `(accountId, date)` pair that already has an existing entry **replaces** it — existing entries matching an incoming `(accountId, date)` key are dropped before the new entries are appended, so re-recording a date does not create a duplicate point. This dedup only applies against *pre-existing* entries: if a single save batch itself contains two draft rows with the same `(accountId, date)`, both are appended (not merged) — the UI doesn't prevent entering duplicate rows within one dialog session.

**Edit Balance Entry**: clicking a row in the Activity table (not its trash icon) opens `RegisterBalanceDialog` pre-filled with that entry's data — single draft row, no mode toggle (Copy-Paste unavailable) and no "+ Add row" (still supports "+ Add activity"/per-activity remove within the row). Primary button reads "Save changes" and dispatches an update to the existing entry (not `ADD_BALANCE_ENTRIES`). The dialog also offers a "Delete" action guarded by the same `window.confirm('Delete this balance entry? This cannot be undone.')` as the table's trash icon, closing the dialog immediately on confirm. Cancel discards all edits and closes without saving.

## Budget

Accessed via the "Budget" rail control. Persisted data: `budgetExpenseDefinitions: ExpenseDefinition[]` (global, year-independent — no `amount` field), `budgetExpenseAmountsByYear: Record<string, Record<string, number>>` (per-year amounts keyed by expense id), and `budgetTransactions: BudgetTransaction[]`. Income is derived from active categories named `Income`, their definitions, and their transactions; no manual income field is persisted. `categories` are global-store props. Budget period selection is app-session state in the top bar; remaining filters, drafts, scopes, and cell-edit state are component-local and not persisted.

The top-bar `.seg` control switches **Spend** / **Expenses** / **Analytics**; default **Spend**. Spend has an **All**/transaction-year scope selector; Expenses has its own independent Category Breakdown year selector; Analytics reads all years.

### Expenses tab

Two stacked cards: **Expenses** table on top, **Category Breakdown** below.

- **Category Breakdown panel**: its own **Year** `<select>` in the card header, fully independent of the Spend tab's Year and of the Expenses table's own filter/sort — changing one never affects the other. Renders a bar-per-category from `categoryBreakdown(budgetExpenseDefinitions, budgetExpenseAmountsByYear[breakdownYear], transactions for breakdownYear, categories)`. Each category's bar widths are relative to that category's larger Budget or Actual total (so one is always 100%). Empty state (no expense definitions with an amount that year): "Add expenses to see the breakdown."
  - **Category drilldown**: clicking a category row's chevron expands its details; only one `categoryId` is expanded at a time (`useState<string | null>`). The panel lists linked `ExpenseDefinition` lines with their budget, exact actual from transactions whose `spendExpenseId` matches that definition (never estimated), variance, and bars. An **Unlinked transactions** row appears only when the category's unlinked actual is nonzero, including for a category with no definitions. "No budget lines in this category." appears only when there are no definition lines and no unlinked row.
- **Expenses table**: one row per global `ExpenseDefinition` — Name, Category, Frequency, then one right-aligned **Amount column per year**, spanning every year in `budgetTransactions`/`budgetExpenseAmountsByYear` plus the real current calendar year, ascending and uncapped. A cell with no stored amount for that `(year, expenseId)` pair shows `—`.
  - **Sorting**: attached to the **Name/Category** column headers (click to sort by that column; click the already-active column to reverse direction — a chevron shows current direction). Default: Category ascending. A separate "Filter by category" select still exists alongside it.
  - **Per-cell edit**, no pencil/Done affordance: clicking the **Name** cell opens a text `<input>`; clicking an **Amount** cell opens a number `<input>` seeded from that column's year's raw stored value (or blank if unset) — Enter or blur on either commits, Escape reverts without dispatching. A Name commit dispatches `UPDATE_EXPENSE_DEFINITION` (patches the shared definition — visible under every year's row at once). An Amount commit dispatches `SET_EXPENSE_AMOUNT` (non-blank value) or `CLEAR_EXPENSE_AMOUNT` (cleared to blank) scoped to that one `(year, expenseId)` pair only — editing 2026's Amount cell never touches 2025's. Clicking **Frequency** or **Category** opens a `<select>` that commits immediately on `onChange` (no separate commit step) and dispatches `UPDATE_EXPENSE_DEFINITION` — Category's "+ Add new category…" option opens the same in-app new-category dialog used elsewhere on the page and applies the new id the same way.
  - **Delete**: a trash-icon button (`aria-label="Delete expense"`), always visible regardless of edit state, first checks whether ANY `BudgetTransaction`, in ANY year, still references this expense via `spendExpenseId` (`expenseDefinitionInUse(state, id)`); if referenced, deletion is blocked entirely with `window.alert('Cannot delete: this expense is used by a Spend record in at least one year.')` (no confirm dialog shown in this case — the alert replaces it) and `DELETE_EXPENSE_DEFINITION` is never dispatched; otherwise it's guarded by `window.confirm('Delete this expense? This cannot be undone.')`. A confirmed `DELETE_EXPENSE_DEFINITION` also hard-deletes every portfolio mapping pointing at the expense. Deletion removes the definition and its stored amount from every year at once — there's no way to delete only one year's amount for an expense while keeping the definition (use the Amount cell's clear-to-blank for that instead).
  - **Add Expense**: opens a modal (Name/Category/Amount/Frequency); invalid submit (blank name, or amount `<= 0`) silently no-ops. A valid submit creates the `ExpenseDefinition` globally and seeds its `Amount` for the CURRENT calendar year ONLY — a newly added expense shows `—` in every other year's column until an amount is entered there too.
  - **Empty state**: "No expenses to show." when the filtered/sorted row set is empty.

### Spend tab

- **Summary cards** (3), scoped to the selected Year or All: Spend vs budget, Projected spend, and Savings rate. Savings rate uses Income-category transactions; its pencil editor sets the selected year's annual Income `ExpenseDefinition` amount, creating a yearly `Income` definition when necessary. Categories with `excludeFromSpend` set have their transactions excluded from actual-spend-derived figures; budgeted figures are unaffected.
- **Spend records** card: shares the page's selected Year — shows that year's `budgetTransactions` (the same underlying set, `periodFilteredTransactions`, as the "Actual spend" summary card). Columns: leftmost row-selection cell (see below), Date, Description, **Spend Category**, **Account**, **Tags**, Amount. Tags is display-only-ordered between Account and Amount and is NOT sortable (no `SortIcon`, no sort handler; `recSortBy` stays a 5-key union). The read-only Spend Category cell shows `"{expense name} ({category name})"` when the row is linked to a resolvable `ExpenseDefinition`, else `"Uncategorized ({category name})"`. Account column shows `row.accountName` or `—` when unset. Tags cell shows `.tag-outline` chips (all tags, max 5) or an empty state (em-dash/blank, never "undefined" text) when untagged. A "Show excluded" checkbox next to the search box (component-local `showExcludedRecords` state, default unchecked) hides rows whose category has `excludeFromSpend` set when unchecked; checking it reveals them. Toggling it resets pagination to page 1. This only controls row visibility in this table — it does not change the Actual-spend/Variance figures elsewhere, which always exclude those transactions regardless of this toggle.
- **Spend records row selection**: each row's leftmost cell (`data-testid="row-select-{id}"`, `tabIndex=0`, `aria-selected`) is a spreadsheet-style selection cell over the currently-visible `pagedRecords` (i.e. selection is always scoped to what's on screen — reflecting search/`showExcludedRecords`/selected year/pagination already). Click selects only that row and sets it as the anchor; ctrl/cmd-click toggles membership without touching the anchor; shift-click selects the contiguous visual range from the anchor; shift+ArrowDown/ArrowUp (while a selection cell has focus) extends the range by one row and moves focus to the new end. Selection (and the bulk category picker below) resets to empty whenever the visible set/order can change out from under it — paging, sort column/direction, search text, or switching the selected year.
- **Bulk category edit action bar**: appears above the Spend records table only when >=1 row is selected, showing `"{n} selected"`, a `SpendCategoryPicker` (`aria-label="Bulk edit spend category"` — see "Spend Category selection is global" below for what it lists), a `TagInput` (`aria-label="Bulk edit tags"`, component-local `bulkTags`, default `[]`), and an "Apply" button (disabled until an expense is chosen, i.e. while `bulkCategoryId` is empty — tags are additive-only and never change the enable condition). Choosing an expense sets both `bulkExpenseId` (the picker's `value`) and `bulkCategoryId` (the expense's resolved category, used only for the Apply-disabled guard). Apply dispatches a single `UPDATE_BUDGET_TRANSACTIONS_BULK` (`categoryId` + `spendExpenseId` + `tagsToAdd: bulkTags.length ? bulkTags : undefined`) for all selected rows — `tagsToAdd` unions case-insensitively into each row's existing tags (existing casing wins), appended in order given, capped at 5 per row with overflow silently dropped — then clears the selection and all three input states (`bulkCategoryId`/`bulkExpenseId`/`bulkTags`). Unlike the per-cell single-row Category edit, bulk Apply does not create a mapping, so it is a deliberate one-off action.
  - **Search**: a text box (`aria-label="Search records"`, placeholder "Search records") does a case-insensitive substring match against Description, the resolved Category name, Account name, and tags; applied before sort/pagination, and resets to page 1 on every keystroke. Empty search shows all rows for the selected year.
  - **Tag filter removed**: no combobox; Search substring-matches tags.
  - **Sorting**: all 5 columns (Date, Description, Category, Account, Amount) are sortable via column-header click — a chevron (`SortIcon`) marks the active column/direction; clicking the active column reverses direction, clicking a different column switches to it (default direction ascending, except Date which defaults to descending when newly selected). Tags has no sort handler and is never in the sort key union. Default sort on load: Date descending.
  - **Pagination**: active only when the search-filtered row count exceeds 50; page size 50 (never more than 50 rows rendered at once); Prev/Next buttons + "Page X of Y" label, right-aligned below the table. Hidden entirely when the filtered set is 50 rows or fewer. The **Total** row always sums Amount across the full filtered set (search-filtered, not just the current page).
  - **Per-cell edit**: clicking any data cell (Date/Description/Spend Category/Account/Tags/Amount) turns just that cell into an editable input in place (a `SpendCategoryPicker`, `aria-label="Edit record spend category"`, for Spend Category; a `TagInput` bound to `row.tags ?? []` for Tags; `<input type="date">` for Date, `<input type="number">` for Amount, plain text otherwise) — no whole-row pencil/Done affordance. Enter or blur commits a single-field `UPDATE_BUDGET_TRANSACTION` patch; Escape reverts without committing. The Tags commit sends the full merged array (`patch: { tags: newTags.length ? newTags : undefined }` — removing the last tag clears to `undefined`, never `[]`). The Spend Category picker's options always lead with a `— Uncategorized —` choice; selecting it clears the link (`patch: { spendExpenseId: undefined }`, `categoryId` left at its current resolved value) instead of assigning a different expense. Choosing an expense patches both fields and dispatches portfolio `UPSERT_CATEGORY_MAPPING` keyed by the row's exact description; that one reducer transition reapplies matching transactions in the current portfolio. Clearing the Account cell to blank unsets `accountName`.
  - **Delete**: trash-icon button per row (`aria-label="Delete record"`, `window.confirm('Delete "{description}"? This cannot be undone.')`), unchanged.
  - Manual "Add Record" inline form (Date/Description/Spend Category/Tags/Amount — no Account field; manually-added records never get an `accountName`): the Spend Category field is a `SpendCategoryPicker` (`aria-label="Record spend category"`). Choosing an expense sets both `recExpenseId` (the picker's `value`) and `recCategoryId` (the expense's resolved category) and marks `recCategoryTouchedManually`; choosing "— Uncategorized —" instead clears `recExpenseId` and leaves `recCategoryId` at its current fallback value. The Tags field is a `TagInput` (`aria-label="Record tags"`, component-local `recTags`, default `[]`). Shows an inline error ("Date is required."/"Amount must be greater than 0.") and does not dispatch if date is empty or amount `<= 0`; empty description falls back to `recCategoryId`'s category name. On successful add, `ADD_BUDGET_TRANSACTION` carries `categoryId: recCategoryId`, `spendExpenseId: recExpenseId || undefined`, and `tags: recTags.length ? recTags : undefined`; a chosen expense also dispatches portfolio `UPSERT_CATEGORY_MAPPING` keyed by the exact trimmed description, which reapplies mappings internally. The page-level selected Year jumps to the added record's year (`recDate`'s year) so it's visible immediately even if it falls outside the previously selected year — if that year has no existing snapshot yet, this also dispatches `ENSURE_BUDGET_YEAR_SNAPSHOT { year }` (see "Year-scoped expense amounts & income" below) — and `recExpenseId`/`recCategoryTouchedManually`/`recTags` reset.

The selected name is applied uniformly as `accountName` to every parsed row; it is not parsed per row. Before dedup, import canonicalizes the account name and converts positive-spend statements to canonical negative spend when that account's rule is `positiveSpend`; `negativeSpend` is the permanent silent default. Two mutually exclusive tabs:
  - **Copy-Paste tab**: CSV or TSV — a textarea parsed by a non-RFC-4180 parser (`parseBudgetTransactionsCsv`) that auto-detects the delimiter per line (tab if the line contains one, comma otherwise), so pasting a table copied from a spreadsheet works without a manual format conversion. Fixed column order `date, description, amount, [tags]` — an optional 4th Tags column (`;`-delimited, e.g. `food;weekly`). `;` is the tag separator because the row parser already splits fields on commas and tag values are alphanumeric-only. Per-token import validation: strip non-`[a-zA-Z0-9]` chars, drop tokens empty after stripping, case-insensitive dedupe (first-seen casing wins), truncate to the first 5; an empty/missing tags cell leaves `tags` unset (never `[]`). The header-detection heuristic checks the fixed amount column (index 2), not the last column, so a header row with or without the Tags column is still dropped.
  - **Upload file tab**: accepts CSV, OFX, and QFX files — dashed dropzone (click or drag-drop, `accept=".csv,.ofx,.qfx"`, `aria-label="CSV, OFX, or QFX file"`). The file's extension picks the parser (component-local state `importFileKind: 'csv' | 'ofx' | null`): `.csv` → `parseBudgetTransactionsCsv` (same optional 4th Tags column as Copy-Paste), `.ofx`/`.qfx`/anything else → `parseOfxTransactions` (no tags concept — OFX/QFX imports never set `tags`). Two distinct inline errors show when the file parses to 0 transactions: `"No transactions found in file — check it has date/description/amount columns"` (CSV) or `"No transactions found in file — check it's a valid OFX/QFX export"` (OFX/QFX).
  - **Date parsing (`parseBudgetTransactionsCsv` only — `parseOfxTransactions` and the Positions/Transactions CSV import path are untouched)**: each row's date is normalized to `YYYY-MM-DD` via `normalizeBudgetDate` before dedup. Accepted formats: ISO `YYYY-MM-DD`; `MM/DD/YYYY`, `M/D/YYYY`, `MM-DD-YYYY`, `M-D-YYYY` (slash or dash, 1-2 digit month/day, 4-digit year — always read as MM/DD/YYYY, no locale/ambiguity heuristics); month-name (e.g. "Sep 17 2026"). A comma before the year (e.g. "Sep 17, 2026") does **not** work when the row is comma-delimited — the row parser splits on every comma with no quoting support, so the comma breaks the field boundary before `normalizeBudgetDate` ever sees the date (this doesn't apply to a tab-delimited pasted row). A blank, unparseable, or unrecognized date silently drops the row inside `parseBudgetTransactionsCsv` itself, no error shown, and the row is excluded from the `"{n} row(s) detected"` status line below (that count is taken after date-drop, not before).

  - Dedup key (`importBudgetTransactions`): `date|description|amount|accountName` — `spendExpenseId` is resolved via mapping match (see auto-categorization below) and `categoryId` derived from the linked definition before the dedup check runs, but neither participates in the key, so two rows differing only by category/expense link now dedup as duplicates. `tags` likewise never participate — two rows differing only by tags dedup as duplicates, first row's tags win. Checked against existing transactions and against earlier rows in the same import batch; duplicates silently dropped, no error shown. Including `accountName` means two otherwise-identical transactions differing only by account are no longer treated as duplicates.

The applied convention marker is persisted even when dedup adds no rows. Editing source text or selecting a new file clears the report; Close/Cancel resets the dialog.

### Spend Category selection is global — a real behavior change

`SpendCategoryPicker` (used for the per-cell Spend Category editor, the bulk-edit action bar, and the Add Record form, all on the Spend tab) now lists **every `ExpenseDefinition` in the app, regardless of year** — alpha-sorted by name, option label `"{name} ({category})"`, always with a leading `— Uncategorized —` option ahead of them; disabled with a single "No expenses defined" option only when there are zero `ExpenseDefinition`s at all, anywhere. This replaces the prior "same year as this record" filtering: previously, categorizing a January 2025 transaction only offered expenses that had been defined for 2025; now it offers every expense ever defined, no matter which year(s) it has an amount in. In practice this means a user can link ANY spend record to ANY expense definition even if that expense has no budgeted `Amount` for the record's own year (`budgetExpenseAmountsByYear[year][expenseId]` can be unset while the link still resolves fine for categorization purposes — Budgeted-vs-Actual comparisons simply show `—`/`$0` budgeted for that year).

Import and autoTag-cluster propagation (see Import auto-categorization above, and `propagateSpendLinksByAutoTag` in `schema-spec.md`) follow the same global rule — any `ExpenseDefinition` can be the resolved winner, with no year filter at all.

### Account rules and canonical signs

- `negativeSpend` means negative amounts are spend and is the permanent silent default for accounts without a rule; `positiveSpend` converts positive imported amounts to negative canonical spend.
- Rule changes and removing a rule require native confirmation. A confirmed action updates the global rule and immediately reconciles the currently open portfolio; other portfolios reconcile when opened. Reconciliation compares `budgetAccountAppliedConventions: Record<normalizedAccountName, StatementConvention>` with the current rule/default, flips affected transaction amounts once when conventions differ, canonicalizes rule-backed names, and updates markers.
- Account rules share the global category store, its IndexedDB document, JSON/Drive `category-mappings.json`, merge, and `useGlobalCategories` hook. They are not independently scoped or stored in the per-portfolio encrypted backup.
- **Known limitation:** manual transactions have no provenance. A later convention change also flips matching manual transactions; there is no exclusion.
- CSV/OFX/QFX parsers are unchanged: account selection and sign conversion happen after parsing and before `IMPORT_BUDGET_TRANSACTIONS`.

### Import auto-categorization & mapping reapply

- **Import auto-categorization**: imported rows (Copy-Paste CSV or Upload CSV/OFX/QFX) never carry a category column. Rows are auto-tagged first (LCP-cluster detection), then each row's `spendExpenseId` is resolved by looking at other transactions (existing + same batch) sharing an `autoTag`: the most-common linked `spendExpenseId` among them wins (ties → first in existing state order); `categoryId` is derived from the linked definition. No shared tag, no linked sibling, or a winner whose expense no longer exists — falls back to "Other" with `spendExpenseId` unset. This resolution happens before dedup, but neither resolved field participates in the dedup key (see Dedup key above).
- **Manual Add Record live-prefill**: as the user types into the Description field, the same mapping match live-prefills both `recExpenseId` (the Spend Category picker's own selection — the hit `spendExpenseId`) and `recCategoryId` (the hit definition's category). No match leaves both untouched. Once the user manually picks a Spend Category themselves, further description edits stop overwriting either field (manual pick always wins over the live-match).
- **Re-apply mappings (set on confirmed hit, never clear)**: each portfolio mapping mutation re-resolves that portfolio's `budgetTransactions` in its main-reducer transition. A mapping hit whose `spendExpenseId` resolves to a live `ExpenseDefinition` sets both `spendExpenseId` and `categoryId` (the definition's category); a miss — or a hit pointing at a deleted expense — leaves the row untouched. **Accepted tradeoff**: this can silently re-link a transaction the user had previously and deliberately set to "Uncategorized" via the per-cell picker's `— Uncategorized —` option, if that row's description matches a live mapping — there is no guard against this.

### Year-scoped expense amounts

Only the per-year *amounts* are year-scoped — `ExpenseDefinition`s themselves (name/category/frequency) are global and exist independent of any year. Amounts (`budgetExpenseAmountsByYear`) are stored per calendar year; income is derived from active categories named `Income`, their `ExpenseDefinition`s, and transactions. The Spend tab's page-level Year select reads/writes whichever year is selected; the Expenses tab's Category Breakdown panel reads/writes whichever year its own selector is on; the Expenses tab's multi-year table reads/writes every year in its column set simultaneously, one `(year, expenseId)` pair per cell. Switching the Spend tab's Year to a year with no existing amounts/income snapshot — either by selecting the Year dropdown directly, or by adding a spend record dated in a different year (which also switches the selected year) — **immediately and permanently persists a real snapshot for that year**, cloned from the nearest existing **non-empty** year (closest by absolute year distance; a tie favors the earlier year; the search keeps expanding outward past any empty candidate years until it finds one with data, or finds none anywhere). This is a real dispatched write (`ENSURE_BUDGET_YEAR_SNAPSHOT`), not just a display-time fallback: the newly-visited year owns its own saved copy from the moment it's selected, so editing the source year afterward does **not** retroactively change it. If no year has data anywhere yet, nothing is persisted — the year stays virtual (resolves to empty via the display-time fallback) so that if data is added to a *different* year afterward, switching back still picks it up on the next `ENSURE_BUDGET_YEAR_SNAPSHOT` rather than being permanently stuck on an empty snapshot taken before any data existed. On app load, if the current calendar year has no snapshot yet but an earlier year does, the most recent prior **non-empty** year's expense amounts and income are **auto-copied forward** ("rollover") as the new current year's starting point. This applies identically and independently to expense amounts and to income. A year is never left with a stored-but-empty budget: an empty snapshot is never persisted as a final value, and clearing a year's last expense amount (or zeroing income for a year) removes that year's stored entry entirely, reverting it to the same virtual/unvisited state it was in before any snapshot existed — so it can still pick up real data cloned from elsewhere on a later visit instead of staying stuck empty. The Expenses tab's per-cell Amount edits (`SET_EXPENSE_AMOUNT`/`CLEAR_EXPENSE_AMOUNT`) write directly into whichever year's column was clicked, without any eager-snapshot step of their own — each `(year, expenseId)` pair is independent, so there's nothing to seed.

### Analytics

Third option on the Budget page's **Spend** / **Expenses** / **Analytics** tab toggle. Selecting it hides the Spend scope selector and the selected tab's content, then renders `BudgetAnalytics` (read-only, no dispatch). The tab toggle remains visible; switching back restores the selected tab's local state unchanged.

- **Scope**: computed from ALL years present in `budgetTransactions` (not just the currently-selected Year), most-recent-year-first, soft-capped at 8 years.
- **Empty state**: if there are no budget transactions at all, every section shows "No records for this period." Otherwise, each section renders independently; four sections additionally require 2+ years of data and show their own "No records for this period." message when only 0 or 1 year exists: **Spend trend**, **Savings rate** (shrinking-trend stat), **Category trends year over year**, and **Biggest movers**. The other sections — **Over-budget count**, **Spike month**, **Concentration risk**, **Category share of spend**, **Monthly seasonality**, **Budget accuracy by year** — render normally with just 1 year of data.
- **Excluded categories**: categories with `excludeFromSpend` set are left out of every Analytics figure, identically to the rest of the Budget page (audited across all 7 sections).

Seven sections, in fixed order:
1. **Areas of concern** — up to 5 stat cards: Over budget (count of categories over budget this year + their names, or "None"), Spend trend (% change, colored by direction; 2+ years needed), Spike month (the standout high-spend month, with its total and a z-score-style detail; needs enough monthly history), Savings rate (current rate and whether it's trending up or down vs. the earliest year; 2+ years needed), Concentration risk (the single category taking the largest share of spend, highlighted red if it crosses the high-risk threshold).
2. **Savings rate by year** — a bar chart, one bar per year, labeled with each year's savings-rate percentage.
3. **Category share of spend over time** — a stacked horizontal bar per year (each segment = one category's share of that year's spend, colored, with a hover tooltip showing name + percentage) plus a color-keyed legend below.
4. **Monthly seasonality** — a bar chart of average spend per calendar month (Jan–Dec) across all years, with the peak month's bar highlighted in a different color.
5. **Budget accuracy by year** — one row per year showing a budget-vs-actual overlay bar plus an "Under by $X" / "Over by $X" variance label, colored by direction.
6. **Category trends year over year** — a table (Category, one column per year, YoY % change, "Over budget" pill), sorted by % change; needs 2+ years.
7. **Biggest movers** — two lists side by side, "Biggest increases" and "Biggest decreases," each showing up to 3 categories with their average-monthly-spend change (e.g. "+$120/mo"); needs 2+ years.

## Password gate

Full-replacement gate screen (`PasswordGate`) rendered by `App.tsx` in place of the app shell until the user unlocks the app. Runs on every load (no "remember me" — see in-memory key note below). Layout mirrors `design/v4`'s "Encryption Password" screen: centered card (max-width 440px) on the full-viewport `--color-bg` background, "Ledger" eyebrow, `<h1>` title, muted subtitle, a `.card.blueprint.elev-sm` form card, and below the card a plain "Back to portfolios" text link/button (not a button styled as danger) that navigates away without touching any data.

The gate has no tabs and no restore option of its own — it always renders exactly one of the two screens below, picked by `peekEnvelopeShape()` on the active portfolio's stored data (a legacy pre-encryption plaintext blob is treated the same as "no stored data").

- **First run / no stored data** → **set-password screen**: title "Set Encryption Password", subtitle "Choose a password to encrypt your data on this device." "New password" + "Confirm password" fields, both required; 6-character minimum; must match. Explanatory note inside the card: password encrypts data locally, is never saved anywhere, must be re-entered every session, and is unrecoverable if forgotten. Submit button is a full-width (`.btn-block`) blueprint-cornered "Set password". Submitting derives a fresh key+salt.
- **Returning encrypted user** → **enter-password screen**: title "Encryption Password", subtitle "Your data is encrypted on this device. Enter your password to unlock it." Single "Password" field, full-width blueprint-cornered "Unlock" button. Unlimited retries, no lockout. Wrong password shows an inline "Incorrect password" error below the field and clears it; the field's key is not derivable except by wrong-guessing forever.
- **Restoring from Google Drive or a local backup file does not happen at the gate.** Both restore paths happen earlier, in the `PortfolioPicker`, before a portfolio is opened and the gate ever shows (see `PortfolioPicker.product-behavior.md` Flow 2 — import from a Drive folder — and Flow 3 — import from a local file). Once a portfolio has been opened and unlocked, further Drive backups are reconciled through the Sync button's conflict flow (see Settings page below), not through the gate.
- **Back to portfolios** (either screen): a plain "Back to portfolios" link/button navigates away to the `PortfolioPicker` — no confirmation dialog, no data wipe. This is now the recovery path for a forgotten password: click "Back to portfolios", then use the picker's "Delete" action on that locked-out portfolio (works without needing that portfolio's password). Settings > Encryption no longer has any destructive-reset card or control — see Settings page below.
- **Session key lifetime**: the derived key/salt live only in `App.tsx` React state, never persisted. Lost on refresh, tab close, or navigation away — there is no "remember" option and no manual lock button; the only way back in is re-entering the password on next load.
- **Auto-lock on inactivity**: the app also locks itself proactively, without a refresh or tab close. It fires once **both** are true: at least 2 hours have passed since the last unlock (or password change), **and** at least 5 minutes have passed with no user activity (mouse clicks, key presses, touches, and scrolling all count as activity; moving the mouse without clicking does not). Activity only *defers* the lock by resetting the 5-minute idle window — it never grants a fresh 2-hour window, so e.g. continuous clicking for 3 hours straight still locks at the first 5-minute gap after the 2-hour mark. On lock, any pending unsaved change is flushed to storage first, then the app silently returns to the same password-entry screen shown on a fresh page load — there is no "you were locked out" message and still no manual lock button. Any in-progress, unsaved component-local dialog or form (e.g. a partially-filled Add Transaction dialog) is discarded, not saved. Each open browser tab tracks its own lock timer independently — locking in one tab does not lock another open tab.

Four mutually-exclusive sections (Backup / Encryption / Quotes API Key / Spend Accounts), switched via a `.seg` tab control at the top of the page's content — only one section's card is visible at a time. The tab-seg is followed by a `.hr` divider.

- **Tab-seg** (top of content): "Backup" / "Encryption" / "Quotes API Key" / "Spend Accounts" tabs, active per `settingsSection`, each dispatches `setSettingsSection` on click. Resets to "Backup" every time Settings is opened via the gear button.
- **Backup** (`settingsSection === 'backup'`): stacks TWO cards vertically — the Google Drive Sync card followed by the Download card (the second card on the Backup tab, described further below). The Google Drive Sync card renders only the `@open-webapp/drive-connect` package widget (`<GoogleDriveWidget>`) — there is no restore panel or restore button here; this card is connect/status only. The **widget** renders all four connect states itself — disconnected (a Connect button), connecting, connected (shows the Google account), needs-reauth — with errors shown inline via `role="alert"` and no `window.alert` dialogs for connect/disconnect; its buttons use the package's own styling, not `.btn.btn-primary.blueprint`. When the active portfolio was imported from a shared Drive folder, a badge and an "Unlink" button (confirm `"Unlink this shared Google Drive folder?"`) appear next to the card title. When a backup folder URL is known, a **View in Google Drive** link appears below the widget, opening it in a new tab. **Auth-token behavior** (owned by the `@open-webapp/drive-connect` package): a still-valid cached token (not expired, scopes complete) is reused without prompting; only an expired or missing token triggers the interactive Google auth window, and never more than one window at a time (single in-flight guard, shared by the widget's Connect button and the content ops' `ensureFresh()`) even if sync/connect is triggered rapidly. The Nav **Sync** button is always rendered and `disabled` while Drive is not connected or a sync is in flight. **Restoring an existing portfolio's data now happens only through that Sync button**: syncing compares the local and Drive copies and, on a conflict, opens `SyncConflictDialog` for the user to resolve (remote-wins semantics for encrypted state) — there is no separate "Restore from Drive" button or Picker-based restore inside Settings anymore. Restoring into a *new* portfolio (from a Drive folder or a local backup file) instead happens in the `PortfolioPicker`, before the portfolio is opened (see `PortfolioPicker.product-behavior.md` Flow 2 / Flow 3).
- **Download** (the second card on the Backup tab, card title "Download"): **Download Backup** button (`.btn.btn-primary`) — silent, no password prompt or confirm, downloads an encrypted envelope (`{version, salt, iv, ciphertext}`, encrypted under the current session key/salt) as `ledger-backup-YYYY-MM-DD.json` (today's local date). Download-only — this card has no restore/import control of its own; restoring an already-open portfolio's data goes through the Sync button above, and restoring into a new portfolio goes through the `PortfolioPicker` (see Password gate above and `PortfolioPicker.product-behavior.md`). Below it, two secondary buttons (`.btn.btn-secondary`), both silent (no password prompt, no confirm) and both 2-space pretty-printed JSON via `downloadPrettyJsonAsFile` (Blob+anchor): **Download Portfolio (Unencrypted)** → `ledger-portfolio-YYYY-MM-DD.json` (local date via `localDateStamp`) — flat top-level JSON of `ExportableState` fields, with `priceSync.apiKey` and `mutualFundSync.apiKey` blanked to `''` (`lastRun` kept); **Download Categories (Unencrypted)** → `ledger-categories-YYYY-MM-DD.json` — `{categories, budgetAccountRules}` (`GlobalCategoryState`). Static inline warning under the buttons, verbatim: "Unencrypted — anyone with this file can read your balances and transactions." Export-only: no import/restore path for either file. Excluded (same as encrypted backup): UI/filter state and price caches (`heldPrices`, `lastFetchedDate`, `callBudget`). Encrypted `Download Backup` flow untouched.
- **Change Password** (`settingsSection === 'encryption'`): "Current Password", "New Password", "Confirm New Password" fields + a "Change Password" button. Verifies the current password by attempting a real decrypt of the stored data; wrong current password shows "Current password is incorrect" and stops. New password follows the same 6-char-minimum/must-match rules as the set-password screen. On success: generates a **fresh salt** (rotated on every change, never reused), re-derives a key, re-encrypts and saves the local IndexedDB copy under the new key+salt, then — only if Google Drive is currently connected — re-syncs the Drive backup under the new key too. If that Drive re-sync fails, a non-blocking inline warning is shown ("Password changed locally, but Drive re-sync failed... Sync manually...") but **the local password change is not rolled back**. On success the app adopts the new key as the session-wide key going forward, and also resets the 2-hour auto-lock clock, same as a fresh unlock.
- **Price Sync** (`settingsSection === 'priceSync'`): Polygon.io API Key field (`type="password"`, commits to state on blur, not on every keystroke). **Fetch prices now** button (`.btn.btn-primary`, disabled while a fetch is in flight or no API key set) + adjacent optional `<input type="date">` date-override (disabled while fetching) for fetching a specific trading date instead of latest. **Last run** summary below: `Never run` if no run yet; otherwise timestamp + either the error in red (`#8a3c2e`) or `{marketTickerCount} tickers fetched from Polygon` (total tickers in that day's market-wide response, not just held symbols) plus `{updatedCount} updated` plus `, not found: {symbols}` when any. **Price table** (below the summary): row set = union of every ticker cached locally (`marketDataDb.getAllBars()`, market-wide — thousands of tickers, loaded async and refreshed after each run), `state.priceSync.heldPrices` keys, and the latest run's `notFound` symbols, deduped, sorted ascending by ticker (no sortable headers). Columns: Ticker, Price, Status, Held, Trading Date, Fetched At. Status is "Not found" (red, `#8a3c2e`) if the symbol is in the latest run's `notFound` list — wins even over a stale held-price entry for that symbol — "OK" if it's a held symbol found in the response, otherwise "Market" for a non-held ticker present only in the local bar cache. Held is "Yes" for a symbol that is (or was) a held Equity/ETF position, "No" for a market-only ticker. Price/Trading Date come from the symbol's held-price entry when one exists, else from its cached bar; Fetched At only ever comes from the held-price entry (the bar cache doesn't track a fetch timestamp) and shows "—" for market-only tickers. All show "—" when no data exists. A live, case-insensitive search box above the table filters rows by ticker substring, status text, or "Yes"/"No" — no submit button, no debounce. Table sits in a scrollable container (`overflowY: auto`, `maxHeight: calc(100vh - 480px)`). Empty state: if there are no held prices, no recorded not-found symbols, and no cached bars, the search box and table are replaced by "No prices fetched yet."

Navigation back to the Accounts page occurs via the rail's Positions control (no separate Back button or navigation affordance in Settings page content).

## PWA install & offline behavior

- **Install prompt**: relies entirely on the browser's native install affordance — address bar icon on desktop Chrome/Edge, "Add to Home Screen" on Android/mobile browsers. No custom in-app install button or banner.
- **Offline behavior**: app shell (HTML/JS/CSS, icons, manifest) loads from cache when offline. IndexedDB-backed app data (accounts/positions/transactions) already works offline regardless of PWA status. Drive Connect sign-in and Drive sync (Sync button) require network — the gsi/client script and Drive API calls are intentionally NOT cached/proxied by the service worker, so they fail or hang when offline. This is expected, not a bug.
- **Update behavior**: silent auto-update (`registerType: 'autoUpdate'`). No "new version available" prompt. The next reload or navigation after a new deploy picks up the latest service worker and assets automatically.

## Formatting conventions

- USD: `fmtUSD(n)` → `"$1,234.56"` / `"-$1,234.56"` (no leading `+` on positives; callers that want a `+` prepend it themselves for G/L-style fields).
- Percent: `fmtPct(n)` → always signed, `"+1.20%"` / `"-1.20%"` / `"+0.00%"`.
- Shares: `toLocaleString('en-US', {minimumFractionDigits:2, maximumFractionDigits:2})`.
- Dates in Transactions table: `Date.toLocaleDateString('en-US', {month:'short', day:'numeric', year:'numeric'})` (e.g. "Jan 5, 2026"). Dates in Closed Positions "Closed" column are shown as raw ISO strings.
